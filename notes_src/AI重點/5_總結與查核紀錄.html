AI Agent 研究（五）：做法總結與查核紀錄

整理日期：2026 年 11 月 14 日 · 依前四篇研究整理 · 全文查核版（11 月 14 日補充新研究，標示新增）
一句話總結：agent 的效益取決於你搭的迴路。這篇把前四篇整理成可執行的做法，記錄每次更新改變了哪些策略、查核更正了什麼、刪除了哪些研究與原因。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一整理成做法

以下是整理者依前四篇研究提出的做法，效果仍要在自己的專案上驗證。

  1. 先準備驗證工具：回歸測試、參考輸出、量測腳本、profiler 指令都先備好，再讓 agent 動手；每次修改都跑完整測試，退步就退回。
  2. 驗收看產物，不看報告新增：agent 會朝被檢查的東西最佳化，「測試全過、已完成」不能當證據。確認功能真的在指定的模組裡並被呼叫、沒有針對測試輸入寫死；保留一組 agent 看不到的測試或量測做最後確認。
  3. CLAUDE.md 精簡：只寫建置與測試指令、硬體與即時限制、不可違反的規則；不要自動產生後直接留用。更新長度（500 行內）、位置、拆不拆檔不必糾結；但寫進去的規則只有約六到七成會被遵守，越寫越多程式越容易漏。
  4. 不可違反的規則用機械方式擋新增：例如即時執行緒不可配置記憶體、不可改動校正檔格式，做成 hook、lint 規則、編譯期檢查或 CI 測試；CLAUDE.md 說明原因，檢查負責確保做到。
  5. skill 少而精：只為反覆出現、agent 查不到的流程寫 skill；關鍵警告放最前面，註明版本，驗證寫一次；新增後用真實任務比較有無 skill。
  6. 任務要小、範圍要明：開頭交代目標、限制與要看的檔案；跨模組的修改拆成小任務；一個任務一個對話。
  7. 盯著執行過程：反覆讀同一檔案或改了又改就中斷；明顯超過平常回合數就重新說明。
  8. effort 用預設：日常用 medium，修既有程式的 bug 開 high，max 只在測過確實有效時用。
  9. 單一 agent 優先：子 agent 只用在可以完全切開的工作。
  10. 省錢看帳單，不看 token新增：不裝壓縮工具輸出或代理 API 的外掛；比較做法時看每個成功任務的實際費用。少幾個回合、少掛用不到的 MCP 工具，比壓縮輸出有效。
  11. 效能修改要附數字：要求修改前後的量測結果，並檢查運算在目標硬體上、同步正確。更新平行化前先量 kernel 時間，太短的不值得開執行緒或搬 GPU。CUDA 改寫一定要讓 agent 能編譯、執行、比對結果。
  12. 移植 CPU 手調程式到 GPU新增：直接轉一直失敗時，先請 agent 寫出乾淨、未最佳化、結果相同的參考版本，再從那裡轉 CUDA；直接轉能成功時不必多這一步。
  13. 產出與品質一起量新增：評估 agent 有沒有幫助時，除了完成的任務或 PR 數，也追蹤靜態分析警告、複雜度與之後的修 bug 次數。
  14. 安全：不裝來路不明的 skill；新增相依套件先確認存在；合併前跑 CI、親自審查。

二11 月 14 日更新：新研究改變了什麼新增

這次搜尋 2026 年 5 月到 11 月的新研究，讀了 12 篇全文，收錄 7 篇、刪除 5 篇（原因見第四節）。對策略的影響：

  1. 說明檔：從「怎麼寫」轉向「怎麼強制」：析因實驗顯示 CLAUDE.md 的長度、規則位置、拆檔都沒有可偵測的影響，影響最大的是任務類型與 session 長度。原本「重要的放前面」不算錯，但效果小於 6 個百分點；真正要守的規則要靠機械檢查。詳見（一）第三節。
  2. 說明檔：有提交比沒有好：導入 agent 後，有提交 AI 設定檔的專案品質退化約為沒有的一半。這是觀察性研究、差距未經檢定，但方向和「寫一份精簡的 CLAUDE.md」一致。詳見（一）第三節。
  3. 省 token：壓縮外掛不省錢：Claude Code 的帳單約八成是快取讀寫，工具輸出只佔約 3%；壓縮外掛讓 token 少 38%，帳單卻多 6.8%。原本「減少無效探索、少回合」的建議得到加強，新增「不要裝壓縮外掛」。詳見（二）第二節。
  4. 測試：新增「為測試而做」的風險：能跑驗收測試時，agent 可能交出測試全過、但沒有做出要求架構的東西，完成報告也不可信。這是單一任務的個案研究，但和（四）VibeCodeHPC 偷改條件的觀察一致。詳見（二）第一節。
  5. 生產力：新增 2026 年的正面證據：Microsoft 導入命令列 agent 後合併的 PR 多 24%，四個月沒消退，和 2025 年 Cursor 研究「兩個月後消失」不同；但沒有量品質。詳見（三）第一節。
  6. 平行程式：數字更具體：在真實程式的熱點上，單次生成的 CUDA 改寫只有 38.8% 正確，短 kernel 平行化常常變慢；移植 CPU 手調程式時，「先去最佳化」在部分情況有大幅幫助，但不是預設做法。詳見（四）第二節。

三11 月 2 日查核更正了什麼

  1. SkillsBench 數字依最新版更正：舊筆記寫的 +16.2 個百分點、軟體工程 +4.5、醫療 +51.9、84 題中 16 題變差、自生成 skill「無益」，都來自較早的版本。最新版是 87 題、+16.6 個百分點、軟體工程 +11.6、沒有醫療類、13 題變差、自生成 skill 低 8.1 到 11.5 個百分點。
  2. 多 agent 研究數字更正：舊筆記寫五種流程落後 1.71 到 8.76 個百分點，全文是 2.56 到 11.29。
  3. 「skill 造成的失敗」描述更正：1.6% 是 skill 描述誤導，不是「選錯 skill」；19.2% 是放錯位置，論文沒說是「skill 偏好的位置」。
  4. 說明檔效率研究補上限制：Lulla 等的研究沒有測正確性，只測時間與 token。
  5. 效能 PR 研究已讀全文：先前只讀摘要，數字經核對無誤。

四刪除的研究與原因

  1. 11 月 14 日讀過全文後刪除新增： SpecBench（2605.21384，表格加總對不上：三種 agent 的執行次數加起來是 1,912 次，表上總計寫 2,046 次，長任務數 8 與 9 前後不一；摘要與內文的關鍵斜率也不同）； How Do AI Coding Agents Contribute…Agentic Pull Requests（2607.21832，表格加總對不上、內文與表格多處矛盾，bug 比率只出現在圖中，SZZ 工具精確率僅約 0.39）； Coding or Cheating?（2611.10404，只列出每個模型在每題有沒有出現某類指令，沒有報告比率，也沒說明由誰、如何判定作弊）； Under the Hood of SKILL.md（2605.11418，百分比與樣本數對不上，審查流程是作者自行重建的，不是實際的 registry）； At Equal Inference Cost, Multi-Agent Structure Does Not Beat a Single Frozen Agent（2609.04217，只用一個 7B 模型、測家事與購物模擬任務、每格只跑一次，與程式工作關係遠）。
