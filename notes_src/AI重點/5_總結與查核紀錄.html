AI Agent 研究（五）：做法總結與查核紀錄

一句話總結：agent 的效益取決於你搭的迴路。這篇把前四篇整理成可執行的做法，記錄每次更新改變了哪些策略、查核更正了什麼、刪除了哪些研究與原因，以及工作守則第 3 版依據的專案經驗（第五節）。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一整理成做法

以下是整理者依前四篇研究提出的做法，效果仍要在自己的專案上驗證。

  1. 先準備驗證工具：回歸測試、參考輸出、量測腳本、profiler 指令都先備好，再讓 agent 動手；每次修改都跑完整測試，退步就退回。
  2. 驗收看產物，不看報告新增：agent 會朝被檢查的東西最佳化，「測試全過、已完成」不能當證據。確認功能真的在指定的模組裡並被呼叫、沒有針對測試輸入寫死；保留一組 agent 看不到的測試或量測做最後確認。agent 寫的測試，把程式故意改壞一處確認它會失敗，不要只看覆蓋率。
  3. CLAUDE.md 精簡：只寫建置與測試指令、硬體與即時限制、不可違反的規則；不要自動產生後直接留用。更新長度（500 行內）和拆檔不必糾結，重要規則仍放前面（位置的效果沒被排除）；寫進去的規則只有約五成五到七成會被遵守，越寫越多程式越容易漏。
  4. 不可違反的規則用機械方式擋新增：例如即時執行緒不可配置記憶體、不可改動校正檔格式，做成 hook、lint 規則、編譯期檢查或 CI 測試；CLAUDE.md 說明原因，檢查負責確保做到。
  5. skill 少而精：只為反覆出現、agent 查不到的流程寫 skill；關鍵警告放最前面，註明版本，驗證寫一次；新增後用真實任務比較有無 skill。更新裝太多 skill 會讓 agent 選錯或乾脆不用，用不到的就移除。
  6. 任務要小、範圍要明：開頭交代目標、限制與要看的檔案；跨模組的修改拆成小任務；一個任務一個對話。
  7. 盯著執行過程：反覆讀同一檔案或改了又改就中斷；明顯超過平常回合數就重新說明。
  8. effort 用預設：日常用 medium，修既有程式的 bug 開 high，max 只在測過確實有效時用。
  9. 單一 agent 優先：子 agent 只用在可以完全切開的工作。
  10. 已知會失敗的測試不再列在 CLAUDE.md新增：11 月 18 日守則改為第 3.2 版。原本要求把已知失敗的測試列在 CLAUDE.md，專案大了清單會越積越多，修好了也沒人刪，而且要靠 agent 記得去對照。改為優先用測試框架的標記（例如 pytest 的 xfail，設 strict 後意外通過會報錯，提醒拿掉標記）；框架做不到時用清單檔加比對腳本，把結果分成新失敗、已知失敗、已知但已通過三類。CLAUDE.md 只寫一行怎麼標記、清單在哪。加標記或改清單檔也列入 hook 範本要先問使用者的情況，否則把失敗標成「已知」就能讓結果通過。
  11. hook 的寫法與測試新增：11 月 15 日在 agent-config-writing skill 加了附檔 guard-hooks.md：兩個範本（不准為了過測試而改測試或門檻、寫入裝置前先備份）；hook 靜默失效的陷阱（沒設 onFailure 時腳本崩潰或逾時，大多數情況照樣放行，不限平台；Windows 上另有反斜線路徑比對不到、PowerShell 工具沒被比對、標準輸入輸出的編碼）；以及四層測試（只測 hook 程式、在沙盒裡用陷阱任務實跑並先跑沒裝 hook 的對照組、用作弊 commit 測事後檢查擋得住繞道、試用量誤報）。hook 只看得到單次工具呼叫，所以最後一道檢查要放在 CI。這是做法，還沒在實際專案試用；試點跑過、量過誤報後再補實際腳本。
  12. 重要決定寫成 ADR新增：11 月 15 日加入守則。只寫難以回頭、日後看會意外、而且有真實取捨的決定（三項都符合才寫，避免小決定淹沒紀錄），放在 docs/adr/。agent 寫的 ADR 狀態先是「提議」，使用者看過才改成「已採納」；推翻舊決定時另寫新的，舊的標為被取代。Superpowers 的 Ruling 只在計畫結束時列一次，之後工作區就刪掉，符合條件的也要轉成 ADR 才留得下來。
  13. 搭配外部 skill 集時先定分工新增：11 月 15 日讀過 Superpowers（v7.0.2）與 grill-me 的原文後，守則改為第 3.1 版，最後加一節分工規則。最大的衝突是 Superpowers 執行計畫時「不停下來問、自己裁決繼續」：它禁止為了讓輸出相符而只修表面，但計畫本身有錯時（例如測試的期望值），會自己裁決後繼續。守則規定，核心規則要求先問的事（放寬門檻、沒有獨立依據就改測試、計畫外的外部行為改動、寫入裝置等）照樣要停下來問；期望值本身算錯、能用獨立方法重算的，照核心規則的例外處理。其餘：同類 skill 指定用哪一個（測試與除錯用 Superpowers，需求訪談用 brainstorming 或 grill-me，審查用 reviewer，寫設定檔用 agent-config-writing）、brainstorming 提問照分輪編號附建議、最終審查改用只讀的 reviewer。建議 Superpowers 只裝在要做中大型新功能的專案；grill-me 只裝它和 grilling 兩個 skill，不裝整包。這些分工是讀文件推出來的，還沒在實際 session 驗證；兩者也都是實務經驗，沒有對照實驗。
  14. 省錢看帳單，不看 token新增：不裝壓縮工具輸出或代理 API 的外掛；比較做法時看每個成功任務的實際費用。少幾個回合、少掛用不到的 MCP 工具，比壓縮輸出有效。
  15. 效能修改要附數字：要求修改前後的量測結果，並檢查運算在目標硬體上、同步正確。更新平行化前先量 kernel 時間，太短的不值得開執行緒或搬 GPU。CUDA 改寫一定要讓 agent 能編譯、執行、比對結果。profiler 結果請 agent 先判斷瓶頸再細看，不要只給原始指標。
  16. 移植 CPU 手調程式到 GPU新增：直接轉一直失敗時，先請 agent 寫出乾淨、未最佳化、結果相同的參考版本，再從那裡轉 CUDA；直接轉能成功時不必多這一步。
  17. 產出與品質一起量新增：評估 agent 有沒有幫助時，除了完成的任務或 PR 數，也追蹤靜態分析警告、複雜度與之後的修 bug 次數。
  18. 安全：不裝來路不明的 skill；新增相依套件先確認存在；合併前跑 CI、親自審查。

二11 月 14 日更新：新研究改變了什麼新增

這次搜尋 2026 年 5 月到 11 月的新研究，讀了 12 篇全文，收錄 7 篇、刪除 5 篇（原因見第四節）。對策略的影響：

  1. 說明檔：從「怎麼寫」轉向「怎麼強制」：析因實驗顯示 CLAUDE.md 的長度、規則位置、拆檔都沒有可偵測的影響，影響最大的是任務類型與同一 session 已寫的程式量。位置的效果並沒有被排除（最大的一組差距是第 2 行對第 250 行的 5.9 個百分點，信賴區間約 −12 到 0），所以重要規則仍放前面；真正要守的規則要靠機械檢查。詳見（一）第三節。
  2. 說明檔：有提交比沒有好：導入 agent 後，有提交 AI 設定檔的專案品質退化約為沒有的一半。這是觀察性研究、差距未經檢定，設定檔多半是導入同時或之後才提交的（作者認為這會讓差距被低估），方向和「寫一份精簡的 CLAUDE.md」一致。詳見（一）第三節。
  3. 省 token：壓縮外掛不省錢：在單次任務的跑分中，Claude Code 的帳單約八成是快取讀寫，工具輸出只佔約 3%；壓縮外掛讓 token 少 38%，帳單卻多 6.8%。原本「減少無效探索、少回合」的建議得到加強，新增「不要裝壓縮外掛」，但這只在跑分情境驗證過，真實的長互動 session 中外掛碰得到的內容比例較高（約 30%）。詳見（二）第二節。
  4. 測試：新增「為測試而做」的風險：能跑驗收測試時，agent 可能交出測試全過、但沒有做出要求架構的東西，完成報告也不可信。這是單一任務的個案研究，但和（四）VibeCodeHPC 偷改條件的觀察一致。詳見（二）第一節。
  5. 生產力：新增 2026 年的正面證據：Microsoft 導入命令列 agent 後合併的 PR 多 24%，四個月沒消退，和 2025 年 Cursor 研究「兩個月後消失」不同，作者認為部分可能來自分析單位不同；比較基準是已有 IDE 版 Copilot，而且沒有量品質。詳見（三）第一節。
  6. 平行程式：數字更具體：在真實程式的熱點上，單次生成的 CUDA 改寫只有 38.8% 正確，短 kernel 平行化常常變慢；移植 CPU 手調程式時，「先去最佳化」在部分情況有大幅幫助，但效果因模型而異，不是預設做法。詳見（四）第二節。

三查核更正了什麼

  1. 11 月 14 日補讀 10 篇全文新增：先前因網頁截斷或網站限制，只讀到摘要或部分章節的 10 篇，改為下載 PDF 讀全文。收回 6 篇（More Skills, Worse Agents?、套件幻覺原始研究、Meta 的兩篇測試生成研究、KernelPro、ParBench，見（一）（二）（四）標示新增的條目），維持刪除 4 篇（見第四節）。
  2. 舊筆記與全文不符或漏掉重點的 4 處新增：（1）More Skills, Worse Agents? 舊筆記寫上下文變長的影響「小到與零無法區分」：「與零無法區分」是論文的結論，但「小」不對，點估計一直是正的（約 6 到 7 個百分點），在 skill 庫較小時不小於選錯的影響，作者也說它可能真的存在，只是樣本不夠。（2）ParBench 舊筆記寫「稍微改寫程式就讓表現不穩，顯示部分是記憶」，全文是兩個 GPT 模型維持穩定，只有 Qwen 下降且未達顯著。（3）Meta TestGen-LLM 舊筆記寫「候選測試只有 25% 提高覆蓋率」：評估章節的 25% 是以測試類別計算，討論章節又稱它為每個測試的成功率，論文本身前後不一；部署資料以單一嘗試計算只有約 4% 到 5%。（4）SciCode 舊筆記寫「2024 年最好的模型只解出 7.7%」，摘要寫的其實是 4.6%；7.7% 是表格中提供背景知識後的增幅（另一個模型給背景後的絕對值也剛好是 7.7%，可能因此混淆），最好的模型給背景後是 12.3%。原因不只是只讀摘要：有的是摘要省略了限制，有的是論文本身措辭前後不一，有的是讀表格時混淆。所以「沒讀全文不收錄」的門檻維持不變，而且數字要對照表格與計算單位。
  3. 全部參考文獻重新查核一次新增：先前標「讀過全文」的論文，有些當時用的網頁工具會截掉長論文的後半段，所以不能保證真的讀完。11 月 14 日把其餘 49 篇（含會議版 PDF 與官方網頁）全部重新下載最新版全文，用程式比對筆記每一條的數字是否出現在全文中，再逐篇讀限制章節。結果：（1）程式比對沒有發現編造的數字：82 條中 15 條有程式找不到的數字，逐條查過都是四捨五入、換算，或筆記依的是會議正式版（改完後重跑剩 13 條，同樣都已查過）。12 以下的整數（例如重複次數、模型數）程式沒有比對，只在讀限制與實驗設定時人工核對。（2）2 篇論文在筆記寫成後改版、數字改變：SWE-Skills-Bench（v2 擴充到 98 個 skill，92 個沒有顯著效果）與多 agent 流程比較（v2 改成跑 3 次，一種流程穩定勝出 3 個百分點），已依新版改寫。（3）2 處說法改正：VibeCodeHPC 放大矩陣到 16384 的是沒有監督的單一 agent，不是多 agent；CUDA Agent「每種設定只跑一次」在原文找不到依據，改成原文能支持的寫法。（4）補上十多處漏寫的限制，例如 skill 增益可能部分來自加長 context、軟體工程 skill 研究的檢定力低、說明檔研究只測 Python、多 agent 流程是作者重新實作的版本、限制回合的成本計算關閉了快取、規劃研究沒有測 Claude 或 GPT。這一輪也經過獨立審查，審查抓到我自己的兩處誤改（把 VibeCodeHPC 的重複次數改錯、誤讀 CUDA Agent 的 5% 門檻），已改回。教訓：除了截斷，論文改版也會讓筆記過時，引用時要記下版本；重複次數這類設定要到實驗設定段核對，不能只看限制章節。
  4. 全部條目逐條獨立審查新增：上一條的獨立審查只抽查了 12 篇、而且只看改動的句子，抽查就抓到 2 處錯，所以同一天再把 49 篇每一條引用都交給獨立審查：分 5 批，每條回原文核對數字屬於哪個模型與條件、12 以下的整數、實驗設定與作者自述的限定。審查提出的每一條我再拿原文確認；有 1 條是審查誤讀（把兩種策略的比較當成重跑的變異），沒有採用。改寫後的文字又交給另外 2 位審查者核對，修正了幾處說得比原文強的地方。結果改了約 70 段文字：（1）1 篇的數字已被作者作廢：套件幻覺重現研究（Churilov）11 月的 v4 宣告舊版數字全部作廢，但新版內文仍引用舊數字作說明，所以程式比對誤判為吻合，已依 v4 改寫。（2）2 處歸屬寫錯：設定檔與品質的研究（Denisov-Blanch）分析的是 Agarwal 等的 agent 導入資料，不是 Cursor 研究；去最佳化研究的對照組多出的那次呼叫用在再最佳化，不是重試轉換。（3）1 處統計誤讀：CLAUDE.md 析因實驗的作者寫「可排除 6 個百分點以上的位置效果」，但最大的一組差距就是 5.9 個百分點，信賴區間約 −12 到 0，筆記照抄了，已改正，第二節的摘要與（一）的建議也一併修改。（4）幾處漏寫的限定會改變讀者的結論：壓縮外掛研究的帳單組成只來自單次任務的跑分；效能 PR 研究中 agent 用 benchmark 的比例已追上人；多 agent 研究在唯一的工具使用任務（GAIA）上結果混合，GPT-4.1 下五種固定流程有三種勝過單一 agent；只用 bash 變好只發生在一個模型；整個專案轉換的研究只用了小型或量化模型；多語言基準中 C++ 與 Python 的差距有一部分來自題目來源與 agent 框架。（5）其餘是補上重複次數、模型、樣本組成與作者自述的限定。沒有做到的：會議接受狀態沒有逐一上網查；PDF 轉文字後錯位的圖表數字沒有逐格核對；KernelBench 本機是 arXiv v1，沒確認後續版本的數字是否相同。教訓：程式比對只能證明數字出現在原文裡，不能證明數字屬於誰、是否已被作者作廢；抽查就抓到錯時，應該直接全面審查。

五專案經驗（第 3 版新增）新增

這一節不是研究結論：以下是「AI Agent 工作守則」第 3 版新增條目的依據，來自三個實際專案的回顧（2026 年 11 月 14 日）。每條只有 1 到 6 件案例，樣本小，守則中標為「專案經驗」。第 2 版已有的專案經驗條目（分輪問清楚、量測工具先自我驗證、獨立審查）尚未整理證據；其中第 2 條這次新增的「實驗或操作流程」部分，證據見下方「操作流程也要先問」。

三個專案

  • 專案甲：量測系統。C++ SDK（多個 CPU／GPU 運算後端）、嵌入式韌體、Python GUI、C# 範例。
  • 專案乙：監控系統。C++ 擷取引擎、Python 監控程式與設計工具，多台儀器同時擷取。
  • 專案丙：影像處理 SDK。C++ DLL、C# 範例，加上一個既有的 Python 參考實作。

各條證據

  1. 故意改壞：專案甲用恆等校正測試時，一個係數的正負號寫反、內插權重寫成 0、漏掉一個減半的係數這三種錯全部通過。故意對調兩個字串欄位，只有一支逐欄比對的測試抓到。專案乙的審查故意改壞 21 處，測試全部抓到。
  2. 參考實作也要驗：專案丙第一輪讓新實作跟參考實作逐位元一致，後來才發現參考實作用 float32 逐列累加：在一般解析度的影像上，一項統計值就偏了 2–7.5%，換成解析度高得多的感測器會偏低 70–81%。專案甲的參考模型用 float64、韌體用 float32，模型在部分操作條件下是錯的。另外有一次驗證是先假設了一個參數值，再「量到」同一個值，是循環論證。
  3. 二進位不是當次建的：專案甲 4 次（DLL 比原始碼舊、外部提供的二進位是一個月前編的、服務改了程式碼沒重新安裝）。專案乙 1 次：中文編譯器訊息讓建置工具記不到標頭相依，31／42 個目標檔沒被重編，造成結構的記憶體版面不一致。症狀是停止指令卡住，很難聯想到建置。
  4. 靜默退回與吞掉的例外：專案甲的 GPU 後端因為路徑太長或 DLL 名稱不對而靜默退回；建置只發警告就跳過複製 DLL，到執行時才失敗。專案乙的 watchdog 用了一個其實會開啟裝置的列舉函式，丟出的例外被 catch 吞掉、當成「裝置不在」，結果把正在擷取的裝置關掉：約每 40 次開始／停止就卡死一次，log 裡什麼都沒有。
  5. 測試期望值算錯：專案乙的 agent 心算錯一個邊界值，把測試期望值改成程式的輸出。後來確認程式是對的，但使用者因此擔心其他測試的期望值也有問題。
  6. 先查資料再推測：專案甲的 agent 推測「相機增益可能沒改回」並列進問題清單，但設定紀錄檔裡就有正確的數值。還有一次 agent 要使用者抄下相機設定，而那些設定其實已經記在另一個專案的資料裡。
  7. 操作流程也要先問：專案甲在設計一個操作流程的引導介面時，有 4 個決定是在逐題追問中才被使用者抓到：步驟順序錯了，某項設定必須在放好樣品之後才能做；每天現場取得的資料被設計成打包進校正檔；兩項現場取得的資料被當成固定檔；最後要實作進專案的參考程式被當成留在外部的依賴。
  8. 複述需求：專案甲有 4 次產出物的種類或放的位置跟使用者要的不同（做了中間處理步驟的圖，要的是最終結果的圖；最大最小值算錯對象；要放進壓縮檔的東西差點進 repo；要交接的功能差點實作）。
  9. 範圍外的 repo：專案丙的 agent 在參考實作的 submodule 提交修正，使用者不希望參考實作有變動，那次修改就撤掉了。
  10. 看截圖：專案乙有座標軸沒對齊、三處標籤疊在別的東西上；專案甲有圖片重疊、SVG 文字裡的粗體標籤不會顯示。
  11. 有狀態 API 的並行語意：專案丙新增「處理後暫存、之後查詢」的函式，資料競爭、per-thread 暫存不會清理、thread ID 會被重用，都是使用者追問才出現的。
  12. 模擬與實機：專案甲的 stub 量不到真機每次讀相機屬性要 17 ms，GUI 重畫從幾 ms 變成 100 ms 以上。GPU 跟上即時節奏時會降頻，連續呼叫的數字只是上限。有一支同步檢查用 15.6 ms 才跳一次的時鐘去量比這還短的間隔。所有靜態檢查全綠，實機卻不能正常運作。
  13. 硬體狀態與互斥：專案甲的相機被留在外部觸發模式，之後每支測試都等不到觸發；平行 worker 搶同一台相機；燒韌體前沒有備份，而那塊板子讀不回 flash。專案乙在監控程式運作時跑全套測試，測試連上了真的引擎。
  14. 非英文 Windows 的靜默陷阱（setup 與 skill 的修改）：專案乙遇過 MSVC 用 cp950 讀 UTF-8，中文註解的最後一個位元組被當成續行，吞掉下一行；heredoc 吃掉反斜線；寫檔預設 cp950，遇到 ✓ 就把檔案截斷；還有上面那次標頭相依。專案甲遇過 Python 換行轉換讓 7 行插入變成 4,700 行的 diff，以及 µ 被大寫化變成 M。

第 3.3 版：32 份審查報告的分類新增

怎麼來的：專案甲 2026 年 11 月 17 日至 24 日的 32 份獨立審查報告（26 個 session；同一個 session 的多輪審查各算一份），由子 agent 逐份讀全文，把每個問題歸到「agent 犯錯的行為」。下面的數字是出現該類問題的報告數，含勉強歸入的，只當量級看；審查者只讀程式碼、沒有執行，問題本身也沒有全部經過重現。
  1. 每個條件判斷都要有會失敗的測試（25／32）：拿掉一個 gate 檢查，所有測試照過；接線測試的播放張數剛好等於平均張數，10 張光譜完全相同，分不出對錯；offset 用 0 測，offset 沒接上也抓不到。這些多半是先寫測試的工作，所以「故意改壞」不再只限於事後補的測試。
  2. 規則改了，舊說法要全 repo 掃（20／32）：spec 列了要改的行，實作者只改那幾行；同一份給客戶的 HTML 另一段仍叫人「從第 2 步重來」，照做會白白關燈、多暖機 30 分鐘；示意圖的註腳、列舉的註解、docstring 也留著舊規則。
  3. 失敗路徑（20／32）：還原裝置時丟例外，中繼資料檔沒寫出，已拍的資料全部無法分析，原本的例外也被蓋掉；即時迴圈出一次例外就永久停止，記錄鈕仍可按、記下的是舊資料；開裝置之後的步驟失敗，裝置沒關、觸發模式沒還原。
  4. NaN、空資料與邊界值（19／32）：平均值是 NaN 時 np.abs(d) > 1 為 False，判成通過；all([]) 為 True；分母 ≤ 0 時比例自動綠燈；沒有任何資料時 max() 對空序列直接當掉。
  5. spec 沒寫到或自相矛盾時要問（19／32）：spec 的兩個容許值互相衝突，照字面實作後某一列永遠找不到配對；同一個模組裡「bin」有兩種意思；spec 沒寫的情況，實作者自己決定，再把決定寫進 spec，沒列成問題。規則限定在會影響結果、外部行為或使用者看到的情況，其他實作細節仍由 agent 決定、列在回報。
  6. 狀態作廢與進入路徑（17／32；進入路徑約 10／32）：回到第一步時校正資料被清掉卻沒重新載入，永遠不能下一步；從中間步驟開始的一輪永遠到不了最後一步；原始檔重拍後，建表的結果沒有失效，可能打包出舊資料；重新連線（可能換了一台）沒清掉之前的讀數。
  7. 量測報告說過頭（17／32，資料分析類的報告每份都有）：整幀平均蓋掉以 512 像素分段的偏移；用固定的索引跨資料集比較，比到的不是同一個擷取位置；判準連故意做錯的參考資料也判成沒影響；把模擬相機的數字當成實機現象寫進給客戶的文件；數字只來自主控台輸出，無法重現。
  8. 修審查問題只修被點名的那一條（至少 6／32）：暖機計時的失效條件，連續四輪審查各補一條路，每輪都在相鄰的路徑再找到；為了修一個問題把旗標改成計數器，反而多出一個卡死的退步。
  9. 訊息指錯（約 10／32）：叫人重新建置，但重建修不好；畫面顯示 ZeroDivisionError，而不是「有效幀不足」；常駐警告被下一則訊息蓋掉。併入「看截圖」那條。
  10. 用實際生效的值（約 10／32）：縮短 line period 時相機會自己截短曝光、不報錯，專案文件已經寫了，兩支新程式仍假設值沒變；曝光取自輸入框，不是相機實際套用的值；開關燈的切換指令送出後立刻讀回，沒等狀態穩定。
  11. 現況跟記得的不同先問（使用者更正 2 次）：使用者改了發布資料夾的名稱，agent 當成不一致準備改回；量測資料出現異常時，agent 假設使用者動過樣品，其實沒有。
  12. 測試守門的基準（做法）：專案甲的基準兩週沒前移，落後 27 個 commit，回報前的事後檢查列出 74 筆舊改動要人工挑，這段期間新寫的測試也不受保護。改成每個新 session 開始時由 hook 自動前移，做法記在 skill 附檔 guard-hooks.md。

同一次回顧也檢查了哪些規則用不到：把每條規則對照 32 份審查（有沒有被違反）與最近 30 個 session（情境有沒有出現）。「發現自己在兜圈就停下來」兩邊都是 0，證據又只有預印本，第 3.3 版刪除。「與 Superpowers 並用」一節佔守則約四分之一，但 30 個 session 裡只有 test-driven-development 常用（7 次），執行計畫的流程只出現 1 到 2 次，所以從 6 條縮成 2 條，細節以 /review 指令為準。「新增套件前確認名稱」只出現 1 次，CUDA 與平行化的規則在專案甲沒用到，但它們有正式研究支持、而且守則也給其他 C++ 專案用，保留。
