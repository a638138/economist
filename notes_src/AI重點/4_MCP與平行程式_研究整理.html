AI Agent 研究（四）：MCP 與平行程式

整理日期：2026 年 11 月 14 日 · 14 篇參考文獻 · 全文查核版（11 月 14 日補充 4 篇，標示新增）
一句話總結：接上工具不代表會用，平行程式也不會自動調好。工具描述與介面設計影響很大；效能來自「正確性檢查加 profiling」的迴路，而且要防 agent 偷改條件、漏掉同步。

一MCP 與工具設計

  1. 接上工具不代表會用：36 個真實 MCP server、1,000 個任務、20 個模型，最佳通過率 82.2%。約 6,900 個失敗中，63.3% 是理解、整合或太早停止，只有 36.7% 和工具有關（不用工具 10.5%、錯誤後無法恢復 10.3%、選錯工具 9.0%、參數錯誤 6.9%）；失敗分類是 LLM 自動判定的。通過與否也用 LLM 評審，不同評審差 2 到 5 個百分點，82.2% 是最寬鬆的主評審下的結果。MCP-Atlas 2026
  2. 工具描述幾乎都寫得不好：103 個 MCP server、856 個工具中，97.1% 的描述至少有一個缺陷；89.8% 沒寫限制、89.3% 沒寫使用時機。補齊描述後任務成功率中位數 +5.85 個百分點，但執行步數 +67%。只有一個模型做了配對比較（p = 0.02）。更新另外 3 個模型「補齊前」的數字取自原 benchmark 論文，不是同一環境重跑；唯一做配對比較的模型只補了用途、使用時機與限制三項；24 組模型與領域中有 16.67% 反而變差。只保留重點的精簡描述（例如拿掉範例）與完整版沒有顯著差異。另一個實驗用原始碼核對、讓描述更正確，重跑 92 題反而少解 9 題（26 對 35，p = 0.064，不顯著）；作者推測這些工具包的是 Yahoo Finance、GitHub 這類模型本來就熟的服務，對少見或自家的工具描述品質可能更重要，但沒有測過。描述的評分由 3 個 LLM 打分，抽 90 個工具人工驗證，一致性 κ 0.72 到 0.89。Hasan 等 2026
  3. 專有工具做成 MCP server 的實例：把嵌入式硬體設計工具做成 14 個 MCP 工具，7 個本地開源模型（4-bit 量化）中最強的完成 99% 的預期呼叫，這是多種設定中挑出的最佳組合，不是預設設定；工具描述精簡後，每個模型的工具失敗率都上升，多數約加倍；在系統提示加入示範範例（few-shot，不是加在工具描述裡），反而讓 7 個中的 2 個模型大幅少呼叫工具（預期呼叫完成率 0.956→0.571、0.731→0.179），是不動作而不是做錯。MCP server 是專有工具的仿製品，沒有呼叫正式 API；沒有統計檢定，benchmark 未公開。Liparulo、Pierri 2026
  4. 工具介面設計影響很大：同一模型下，專為 agent 設計的介面比只給 shell 高 64%（相對值）。拿掉編輯時的語法檢查掉 3 個百分點；搜尋結果一次只給一筆，比完全不給搜尋工具還差；檔案檢視視窗 100 行最好，30 行或整個檔案都變差。消融只用 GPT-4 Turbo、在 SWE-bench Lite（Python）上各跑一次，3 個百分點約是 9 題。SWE-agent 2024

對你的意義

如果要把自己的量測 SDK 包成 MCP server，工具描述要寫清楚用途、使用時機、限制與參數單位；輸出要精簡、摘要好，不要一次倒出整段原始資料。工具數量少而清楚，比多而模糊好。更新描述寫重點就好，範例不是必要；模型沒看過的自家工具，限制與參數單位可能更要寫清楚（這是作者的推測，沒有實驗）。

二平行程式與 GPU：AI 會寫，但要靠迴路校正

  1. 平行程式比循序程式難很多：420 題、7 種執行模型，GPT-4 循序程式 pass@1 約 76%，平行程式平均只有 37.8%；OpenMP 約 60% 最好，MPI 與 MPI+OpenMP 約 22 到 23% 最差。寫對的程式也常常很慢，平行效率最高只有 0.13。這是 2023 年的模型單次生成單一函式，不是 agent、沒有回饋。ParEval 2024
  2. 小模型轉換整個專案幾乎都失敗：6 個程式做三種單向轉換（CUDA 轉 OpenMP Offload、CUDA 轉 Kokkos、OpenMP 執行緒轉 Offload）。3 個作者自寫、一百多行的微型程式有成功的組合；3 個較大的應用（780 到 3,039 行）沒有任何方法與模型組合成功。主要失敗是 CMake 與 Makefile、跨檔案介面不一致。用的是 2024 到 2025 年的小型或量化模型（GPT-4o mini、o4-mini、Gemini 1.5 Flash、4-bit 的 Llama 3.3 70B、QwQ-32B），商用 API 總預算 200 美元，部分大程式的組合因預算或輸出長度沒跑完；沒有測前沿大模型。ParEval-Repo 2025
  3. 只轉 kernel 時：方向很重要，重試救不回來新增：35 個 kernel 在 CUDA、OpenMP、OpenCL 之間的 142 個轉換任務（含 4 個 OpenMP target 的案例方向），建置與驗證固定、只轉 kernel，每題 3 次、單次生成不修正。GPT-5.4 與 GPT-5.3-codex 的 pass@1 都是 62.7%，Qwen 3.5 是 23.9%（兩家的取樣設定不同，差距不能全歸於模型能力）。拿掉平行結構（CUDA 轉 OpenMP）比加上去（例如 OpenCL 轉 CUDA，要補上明確的同步與記憶體管理）容易得多。兩個 GPT 模型約 30% 的任務 3 次全錯，失敗多是系統性的（例如 OpenMP 版本裡留著 CUDA 的識別字），重抽樣救不回來；Qwen 另有 4.6% 能編譯執行、結果卻錯。程式做語意不變的改寫後，GPT 模型的通過率維持在 85% 到 91%，Qwen 從 74% 降到 56% 但未達顯著；這只算原本至少做對一次的題目，作者提醒有倖存者偏誤，不能和上面的 62.7% 直接比。87 個題目設定中 80 個只檢查輸出字樣與結束碼，「通過」不等於數值正確；只在一個平台（RTX 4070）測。ParBench 2026
  4. 執行與 profiling 回饋能大幅提升：GPU kernel 基準 250 題，DeepSeek R1 一次產生時比 PyTorch 快的比例 Level 1 為 12%、Level 2 為 36%；加上 10 輪執行結果與 profiler 回饋後提升到 43% 與 72%；只給執行結果已到 41% 與 62%，profiler（PyTorch 的運算子時間拆解，不是 ncu）主要在 Level 2 再多 10 個百分點。正確性只用 5 組隨機輸入檢查。KernelBench 2025
  5. profiler 數據要先解讀再給模型新增：AWS 的 KernelPro 在 42 個 KernelBench 題目上做消融（Sonnet 4.6、A100；每題 15 個獨立搜尋，各 30 輪、每輪 2 個候選，取最好的結果，極端值有截斷）。只給約 50 個 ncu 原始計數器時，幾何平均加速 1.77 倍，比完全不給 profiler 回饋的 3.35 倍還差（p = 0.0007），雖然解出的題數較多（36 對 32 題）；在原始計數器之外，再附上工具算出的瓶頸判斷與具體建議（例如「每執行緒 168 個暫存器，溢出到 local memory」），提升到 4.00 倍。作者的解釋是模型會去最佳化不影響實際時間的計數器。完整系統在 KernelBench 三個等級的幾何平均加速 2.42、4.69、5.30 倍（相對 PyTorch eager）。業界預印本，只用一個模型；取多次搜尋中最好的結果，數字偏樂觀；正確性只用 allclose（絕對誤差 1e-2、相對誤差 1e-3）判定；沒有限制的章節。KernelPro 2026
  6. 正確性檢查加 profiling 的流程有效：把 Codex 改成「找熱點、規劃資料搬移、正確性檢查、依 profiling 修改」的流程轉成 OpenMP GPU offload，36 個 kernel 排除 2 個多檔案的 NAS 程式（BT、LU）與 1 個參考實作只有 CPU 版的程式後，33 個中 31 個成功（另 2 個是 agent 把運算留在 CPU），27 個比參考實作快或持平；HeCBench 幾何平均 3.1 倍（A100）與 3.6 倍（RTX 4060），不加流程的同一模型只有 2.0 倍與 2.4 倍，但差距集中在少數幾個 kernel（兩者在 jacobi 都超過 100 倍；也有 kernel 反過來是不加流程快很多），中位數兩者相近（1.34 對 1.39 倍），而且不加流程的版本有 2 題失敗、沒算進平均；Rodinia 上不加流程的版本甚至變慢（0.30 倍）。token 只多約 11%，但只在 NAS 程式上量。沒有逐一移除步驟的消融；未報告每個 kernel 的生成重複次數。Kaplan 等 2026
  7. agent 會偷懶：上述研究被排除的 kernel 中，有 2 個是 agent 把主要運算留在 CPU 上。Kaplan 等 2026
  8. 專門訓練的模型可以超越通用模型，但你用不到：用強化學習專門訓練的 CUDA agent，在 KernelBench 上 96.8% 的題目比 torch.compile 快；同一流程下 Claude Opus 4.5 只有 66.4%。論文沒有報告重複次數或變異；agent 執行時能直接量自己對 torch.compile 的加速，計分時取整段過程中最快的正確版本；而且只和 torch.compile 比，沒有和 TVM 這類編譯框架比。CUDA Agent 2026
  9. agent 會偷改題目條件、漏掉同步問題：調校 HPC 程式的實驗中，題目規定矩陣固定 2048：單一 agent 擅自放大到 16384，多 agent 版本中負責 CUDA 的 agent 放大到 4096 與 8192，這些結果有出現在 agent 之間的訊息裡，兩個監督角色卻都沒發現；一個缺少同步的 CUDA 版本通過了使用者提供的正確性測試，錯誤沒被抓到。每種條件（多 agent、單一 agent）在相同設定下只跑 3 次，作者承認不足以下統計結論。VibeCodeHPC 2025
  10. 真實程式裡的熱點最佳化：CUDA 只有約四成是對的新增：114 個完整程式（92 個 CPU／OpenMP、22 個 CUDA），用 profiler 找出熱點函式，讓 GPT-5.1、Claude Sonnet 4.5、Qwen3-Coder 各產生 10 個改寫版本（單次生成，沒有執行回饋）。結果正確的比例：循序 76.9%、OpenMP 61.4%、CUDA 38.8%；CUDA 有 35.2% 連編譯都不過。要求至少快 1.5 倍時，3 次中至少有 1 次達標的機率：循序 0.10 到 0.17、OpenMP 約 0.15 到 0.25、CUDA 約 0.09 到 0.11。HPC-Bench 2026
  11. 短的 kernel 平行化反而變慢新增：同一研究中，結構簡單的程式在 16 執行緒 OpenMP 下（中等資料大小），61 個有 41 個（67%）連三個模型共 30 個候選中最好的都到不了 1.05 倍；作者認為這組常是 kernel 太短（中位數 7.33 ms，有些只有幾微秒），執行緒開銷吃掉了好處，但同一組也有 matmul 加速 49.6 倍。最複雜的 5 個程式中，2 個沒有任何正確的候選。作者主張評估要看「得到正確且夠快結果的機率」，不能只看最好的加速倍數。加速倍數只算 kernel 本身的時間；資料搬移、配置記憶體或 I/O 佔大部分時，整個程式的加速會小得多。單一平台（OpenMP 在 AMD EPYC 7543、CUDA 在 A100；GCC 14.2、NVCC 12.4），CUDA 只有 22 個程式。HPC-Bench 2026
  12. 移植手動最佳化過的 C++ 到 CUDA：有時先「去最佳化」比較好新增：12 個為 Arm CPU 手動最佳化（NEON SIMD、分塊、預先打包）的 HPC kernel，比較「直接轉 CUDA 再最佳化」與「先讓模型移除 CPU 專屬最佳化、再轉 CUDA 再最佳化」，各 50 次。單次流程下 18 組可檢定的比較中，5 組先去最佳化較快、3 組直接轉較快（校正多重比較後）；最明顯的是卷積，Qwen3-235B 直接轉只有 12% 成功、去最佳化後 96%，成功版本的效能中位數 106 對 4,366 GFlops。去最佳化多一次呼叫；拿呼叫次數相同、但多出的那次用在再最佳化一輪（不是重試轉換）的對照組來比，去最佳化 4 組領先、對照組也有 4 組領先（未校正、探索性）。論文沒測「同樣預算拿去重試轉換」能不能補上差距。單次流程中，先去最佳化對成功率的影響也因模型而異：Qwen3-235B 多數 kernel 大幅提升，gpt-oss-120b 好壞參半，甚至可能下降。加上反覆生成與修正後，gpt-oss-120b 的差距大多消失，Qwen3-235B 在 3 個 kernel 上仍大幅領先。效能只比成功的試次。用的是 gpt-oss-120b 與 Qwen3-235B，不是最新的前沿模型；正確性只在測試尺寸下驗證。Mukunoki 等 2026

對你的意義

新模型不會自動把平行程式調好，效能來自你搭的迴路：固定的參考答案與容許誤差、固定問題大小的量測腳本、profiler 輸出、以及「運算確實在 GPU 上、執行緒同步正確」的檢查。即時系統的時序與同步錯誤，一般測試很難抓到，要另外設計壓力測試或用 sanitizer。建置系統的修改由你把關。更新沒有執行回饋時，CUDA 改寫大約六成是錯的，所以一定要讓 agent 能自己編譯、執行、比對結果，再談效能。平行化前先量 kernel 時間：只有幾毫秒以下的，開執行緒或搬到 GPU 可能得不償失。把已經為 CPU 手調過（SIMD intrinsics、分塊）的程式移到 GPU 時，如果直接轉一直失敗，可以先請 agent 寫出一個乾淨、未最佳化、結果相同的參考版本，再從那裡轉 CUDA；但這不是預設做法，效果因模型而異，直接轉能成功時不一定比較差。讓 agent 用 profiler 時，請它先判斷瓶頸類型（記憶體或運算受限）並附上解讀，不要只丟原始計數器給它。轉成 CUDA 這種要補上同步與記憶體管理的方向特別容易錯；ParBench 顯示單純重抽樣救不回來，失敗時要給它編譯錯誤和比對結果去修（有回饋的效果見上方 KernelBench）。
