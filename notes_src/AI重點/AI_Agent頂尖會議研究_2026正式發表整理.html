AI Agent 頂尖會議研究：2026 年正式發表論文整理

整理日期：2026 年 11 月 2 日 · 9 篇參考文獻 · 只收已被 ICSE、FSE、ASE、MSR、ICML、ACL 正式接受的論文（另 1 篇預印本已標明）
一句話總結：正式發表的研究和先前預印本的方向一致，而且給了更具體的做法：每次修改後重跑既有測試、限制 agent 的回合數、一開始就把目標與限制講清楚，平行程式則靠「正確性檢查加 profiling」的迴路。skill 與說明檔的效果，正式會議的證據仍然很少。
範圍與限制：ASE、FSE 2026 是掃過會議論文目錄（部分頁面因長度只讀到一部分），其餘會議用搜尋找，可能有遺漏；NeurIPS 2026 的完整清單尚不易搜尋。各研究測的模型多為 2025～2026 年初的版本。「對你的意義」與第六節是整理者的判斷，不是論文內容。
第一部分　省 token 與長對話

一限制回合數就能大幅省錢

  1. 固定上限：把回合上限設在平常所需回合數的第 75 百分位，成本降 24%～68%，解題率幾乎不變。Gao、Peng 2026
  2. 動態追加：需要時才給額外回合，成本再降 12%～24%，解題率持平或更好。Gao、Peng 2026
  3. 沒有一個模型同時最好：不設限制時，沒有一個模型在表現、成本、回合效率上同時領先。測的是 Claude 4 Sonnet、Gemini 2.5 Pro、GPT 4.1。Gao、Peng 2026

對你的意義

agent 跑得比平常久很多時，多半是在繞圈，中斷並重新說明通常比讓它繼續跑划算。

二多輪修改會把原本對的東西改壞

  1. 改越多輪，越容易退步：6 個模型連續修改 8 輪，有 43%～73% 的任務弄壞了先前正確的功能。Huang 等 2026
  2. 每輪重跑舊測試就能擋住：每次修改後用先前的測試檢查，失敗就退回重做，DeepSeek-V3 的最終品質從 75.8% 提升到 87.9%。Huang 等 2026

對你的意義

這是目前直接量到改善幅度最大的做法：讓 agent 每次改完都跑完整的回歸測試，而不是只測這次改的部分。

第二部分　怎麼使用 agent

三把意圖交代清楚，效果差很多

  1. 推測使用者意圖的輔助 agent：主 agent 旁邊加一個專門推測使用者目標、限制和偏好，並記住使用者歷史的輔助 agent，在需要記住使用者歷史的任務上，成功率從 18.1% 提升到 59.7%。Zhou 等 2026
  2. 實際使用的回饋：專業開發者使用三週，86% 的情況認為有幫助、更符合他們的意圖。Zhou 等 2026

對你的意義

任務開頭就寫清楚目標、限制、偏好，常用的偏好放進 CLAUDE.md；論文沒有單獨測「主動說明意圖」的效果，這是推論。

四真實的多檔案工作仍然很難

  1. 換成真實題目，成績大幅下滑：在 SWE-Bench Pro 上，最好的模型公開題目解不到 45%、企業內部題目不到 20%；同一批模型在 SWE-bench Verified 上超過 70%。Deng 等 2026
  2. 題目規模：平均要改 4 個檔案、107 行；一般 benchmark 平均只改 1 個檔案、12 行。主要弱點是跨檔案推理和整合大型系統。Deng 等 2026

對你的意義

跨多個模組的修改，先拆成幾個小任務，每個任務只動少數檔案。

五審查習慣決定品質

  1. 多數 agent PR 直接被接受：9,427 個 agent 送出的 PR 中，74.1% 沒經修改就被接受；有修改時，最常見的是重構 agent 的程式碼。Cynthia 等 2026
  2. 資深與外圍貢獻者的差別：核心開發者審得比較仔細，要求 CI 通過才合併；外圍貢獻者比較常沒跑 CI 就合併。Cynthia 等 2026
第三部分　平行程式

六正確性檢查加 profiling，能穩定產出更快的平行程式

  1. 做法：把 Codex agent 改成「找熱點 → 規劃資料搬移 → 正確性檢查 → 依 profiling 結果修改」的流程，把程式轉成 OpenMP GPU offload。Kaplan 等 2026
  2. 結果：31 個 kernel 全部正確，27 個（87%）比原始參考實作快；HeCBench 幾何平均加速 3.1 倍（A100）與 3.6 倍（RTX 4060），Rodinia 為 1.5 倍與 1.1 倍；全面勝過不加流程的 Codex。Kaplan 等 2026
  3. 限制：論文沒有單獨拆出 profiling 的貢獻。Kaplan 等 2026
  4. agent 的效能修改常缺數據（預印本）：agent 的效能優化 PR 合併率 54.4%，人寫的是 73.3%；兩者都約有一半沒附量化的效能數字。Peng 等 2026

對你的意義

這支持先前「AI Agent 開發效率」筆記的結論：效能調校要靠你搭好的迴路（參考答案、量測腳本、profiler）。要求 agent 每次效能修改都附上量測前後的數字。

第四部分　skill 與說明檔

七正式會議的證據仍然很少

  1. 正式發表的只有兩篇：skill 效益基準 SkillsBench（NeurIPS 2026），以及 skill 憑證外洩研究（ASE 2026）。SkillsBench 2026Chen 等 2026
  2. 說明檔的效果研究只在 workshop：例如 Evaluating AGENTS.md 發表在 ICLR 2026 workshop。skill 和說明檔「怎麼寫」的結論，目前大多仍建立在預印本上。

八整理成做法

以下是整理者依上述研究提出的做法，效果仍要在自己的專案上驗證。

  1. 每次修改後重跑完整回歸測試，失敗就退回重做。
  2. 設回合或時間上限：跑得比平常久很多就中斷，重新說明再繼續。
  3. 任務開頭交代目標、限制、偏好，常用的寫進 CLAUDE.md。
  4. 跨模組的修改拆成小任務，每次只動少數檔案。
  5. 平行程式與效能修改：先有參考答案與量測腳本，要求附上前後數字，並用 profiler 結果引導修改。
  6. 合併前一定跑 CI 並親自審查。
