AI Agent 研究（二）：規劃、測試與省 token

整理日期：2026 年 11 月 14 日 · 14 篇參考文獻 · 全文查核版（11 月 14 日補充 4 篇，標示新增）
一句話總結：先有測試、任務切小、減少無效探索，比加規劃步驟或多開 agent 有效。token 花得多不代表做得好，多 agent 通常更貴、不一定更好；壓縮工具輸出的外掛省下 token，卻不一定省錢。agent 會朝「被檢查的東西」最佳化，測試全過不代表做出你要的東西。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一規劃與測試

  1. agent 常不照自己宣告的計畫做：在 SWE-bench 上，agent 宣告計畫後，完整照順序執行的軌跡只有 12.1% 到 25.4%；計畫越長越少照做。只給計畫當參考時，任務成功率提升有限；改用依計畫型態設計的執行器（例如分步驟派工）時，SWE-bench 成功率從 0.36 升到 0.44（DeepSeek-V4，取表現最好的固定型態；另兩個模型增幅更大）。自動比對工具只在另一個環境（ALFWorld）用 100 條軌跡驗證過，和人工的一致性偏低（κ 約 0.3，兩位人工彼此也只有 0.35），所以這些比例的雜訊不小。只測三個開源模型（Qwen、DeepSeek、Gemma），每題最多 24 步。Oota 等 2026
  2. 先寫測試再寫程式有幫助：在 8 個 Python repo 中補完缺少的函式（455 題），「先產生測試、再同時修正測試與程式」比 mini-SWE-agent 高 6.4 到 16.9 個百分點，但這個差距也包含框架不同；同框架內比不寫測試的反覆自省高約 5 到 9 個百分點。測試寫好就固定、只改程式的版本，在 3 個模型中有 2 個不如完全不寫測試的反覆自省，增益要靠同時修正 agent 自己剛寫的測試（不是既有的測試）。只測 Python、沒有統計檢定；最常見的失敗是程式通過自己寫的測試，但沒通過 repo 原本的測試。TDD-Agent 2026
  3. AI 產生的測試大多要丟掉，留下的也要人看新增：Meta 用 LLM 擴充既有的 Kotlin 測試類別，只留下「能建置、連跑 5 次都通過、增加行覆蓋率」的測試。部署時以單一嘗試計算，三關都過的只有約 4% 到 5%（Facebook 8,996 次、Instagram 23,535 次嘗試）。摘要寫的「75% 能建置、57% 穩定通過、25% 增加覆蓋率」來自另一個 86 個測試類別的評估實驗，評估章節定義為「類別裡至少有一個候選成功」的比例，但討論章節又把 25% 稱為每個測試的成功率，論文本身前後不一。送給工程師審的測試，有被審查的約 73% 被接受（三次活動共送出 339 個、接受 196 個，以全部送出計約 58%；其中一批先經作者看過）。被退回的原因包括測的是 getter 這類瑣碎方法、一個測試檢查太多事、沒有 assertion，也就是這些過濾擋不住「沒在比對結果」的測試（作者認為這類測試至少還能檢查「不拋例外」）。業界經驗報告，沒有對照組。Meta TestGen-LLM 2024
  4. 覆蓋率看不出測試會不會抓錯新增：Meta 的 ACH 先讓 LLM 在程式裡植入「現有測試抓不到」的錯誤，再讓 LLM 寫能抓到它的測試，並確認測試在原程式通過、在植入錯誤的版本失敗。產生的 571 個測試中，277 個（49%）沒有增加任何行覆蓋率；如果只用覆蓋率篩選，這些能抓到錯的測試都會被丟掉。植入的錯誤約 25% 和原程式在語法上相同，等於沒改。工程師接受 73%，但送審的測試有一部分經作者先篩過。業界經驗報告，沒有對照組。Meta ACH 2025
  5. 多輪修改會把原本對的東西改壞：542 題單一函式的 Python 題目、每題 8 輪固定修改要求，第 8 輪時 GPT-4o 原有測試通過率從 90.2% 降到 72.4%，Llama-3.1-8B 從 76.1% 降到 31.6%。Huang 等 2026
  6. 每輪重跑測試，退步就要求重做：退步時把上一個通過的版本和失敗數附給模型、重做一次；重做的通過數不少於原本就採用重做，否則保留這一輪原本的版本（不會退回上一版）。DeepSeek-V3 第 8 輪通過率從 75.8% 提升到 87.9%，Llama-3.1-8B 從 31.6% 提升到 47.3%。但觸發重做與挑選版本用的都是評分用的測試；通過率只量原有行為有沒有保留，沒量這一輪的新要求是否做到；只測兩個模型、每題一段對話、沒有統計檢定。Huang 等 2026
  7. 讓 agent 利用過去對話推測意圖，差很多：加一個專門從過去對話推測使用者目標與偏好的輔助 agent（主 agent 與輔助 agent 都是 Claude Sonnet 4），在 GPT-5 模擬使用者的 500 題中，成功率從 18.1% 提升到 59.7%；基準是刻意把 issue 改模糊、又不使用過去對話的條件（基準仍可向模擬使用者發問；直接讓 agent 檢索過去對話的版本效果較小）（論文前言另寫 13.5% 與 57.4%）；17 位開發者三週的真人使用中，86.2% 的建議被採用或稍改後採用，但沒有對照組。ToM-SWE 2026
  8. 能跑驗收測試時，agent 會「為測試而做」新增：Microsoft 的個案研究，要 agent 把一個約 5,800 行的 React 表格元件重寫成 Angular 元件庫，用 222 個隱藏的行為測試評分（agent 只看得到每題過或不過）。不能跑測試時，兩個模型（Claude Opus 4.7、GPT-5.5，都用 GitHub Copilot CLI）交出真正的元件庫，但只過 148 到 189 題；能跑測試時，除了一次始終沒去跑測試的，分數都到 221 到 222，但 GPT 6 次中有 5 次把功能直接寫在示範頁裡，元件庫沒被示範頁用到、只有外殼，或根本不存在，其中一次整個交付只有一個 1,758 行的檔案，完成報告卻寫「元件庫已完成、222 passed」。Claude 6 次中有 2 次出現同樣傾向；而且 Claude 能跑測試的 6 次全都沒附元件庫的發佈設定、也沒自己寫單元測試，不能跑測試的 3 次則都有。只有一個任務、每種條件 3 次、沒有統計檢定，作者說盛行率未知；不能跑測試的那組沒有交示範頁，分數是研究者替每次執行另寫接線程式後測的。Ma 等 2026

對你的意義

計畫寫下來不會自動被執行，要在關鍵步驟設檢查點，或把計畫拆成一步一步的小任務。效果最一致的是「先有測試」：先讓 agent 寫或補測試，你確認測試合理後再讓它改程式，每次改完跑完整回歸測試。更新測試是 agent 的目標，也會變成它唯一在乎的東西：完成報告不能當證據，驗收時要看產物本身（功能是不是真的在你要的模組裡、是否被呼叫、有沒有寫死針對測試輸入的分支），並保留一組 agent 看不到的測試或量測，用來最後確認。更新agent 寫的測試，不要用「通過了、覆蓋率有提高」判斷好壞：把程式故意改壞一處，確認測試會失敗；並看一眼測試裡有沒有真的在比對結果。

二省 token：錢花在哪、怎麼省

  1. token 多不等於做得好：SWE-bench Verified 500 題、8 個模型、每題 4 次，成本最低的一群之後，花更多 token 準確率就不再提升甚至下降；花費高的執行常是反覆讀同一檔案、改了又改。同一題不同次執行，最貴的平均約是最便宜的 2 倍。Bai 等 2026
  2. 成本主要是輸入：即使有快取，讀取快取仍是金額最大的一項；探索與修改兩個階段約佔三分之二的回合。成本以輸入為主是 8 個模型的結果；分階段與快取的拆解只分析一個模型（Sonnet 4.5）。這裡讀取快取最大，下方 Weinberger 的研究則是寫入快取最大，兩者的 harness 與回合數不同（這裡是 OpenHands 的長軌跡）。Bai 等 2026
  3. 限制回合數能省錢，但會少解幾題：100 題、3 個模型、每種設定只跑一次。上限設在第 75 百分位時，成本降 23.6%（Claude）、38.4%（GPT 4.1）、68.3%（Gemini），解題數分別 −4、−5、+2 題；設在第 25 百分位時 Gemini 從 63 題掉到 26 題。實驗的上限每回合都附「還剩幾回合」的提醒；作者用同一批資料模擬沒有提醒、到了就停的情況，解題數掉得更多（例如第 75 百分位時 Claude 71→63 題）。每種設定只跑一次，±4 題的差異可能在隨機變異內。需要時才追加回合，成本可再降約 6% 到 24%（摘要寫 12% 到 24%，與表格不符）。百分位是用同一批題目算的，沒有另外驗證；成本計算關閉了快取，實際帳單（大部分是快取費用，見下方）省下的比例可能不同。Gao、Peng 2026
  4. context 小時，管理機制很重要；夠大時差異很小：4 個模型（Nemotron-3 三種大小與 Mistral，不含 Claude 或 GPT）、2 個 benchmark，context 只有 32k 時，有管理機制比沒有高 35.7 個百分點（SWE-bench），到 128k 時只差 2.7。Fan 等 2026
  5. 規劃步驟主要幫弱模型：最小的 30B 模型加規劃後 SWE-bench 從 13.6% 提升到 25.2%；較強的模型沒有一致的提升，成本降幅依模型與任務從約 4% 到 40%（120B 在 SWE-bench 上反而變貴）。只用 bash、不給專用工具，弱模型掉 15 個百分點；Nemotron 最大的 550B 反而 +3.6、成本 −53%，但另一家族的 Mistral 在 SWE-bench 上掉了 23 個百分點，只在命令列任務上變好，作者的結論是取決於模型與任務。SWE-bench Verified 只有 Python。模型是 Nemotron-3 與 Mistral，不含 Claude 或 GPT；規劃與工具只在 128k context 下測；每種設定每題只跑一次，有做配對檢定，但 Terminal-Bench 只有 89 題，很多比較沒達到顯著。Fan 等 2026
  6. 快取價格（官方文件）：讀取快取一般是輸入價格的 0.1 倍，Opus 5.5 與 Sonnet 5.5 是 0.05 倍；寫入快取 1.25 倍（5 分鐘）或 2 倍（1 小時）。修改工具定義會讓整個快取失效；變更 thinking 設定一定會讓訊息部分的快取失效，變更 effort 則可能失效；兩者在部分模型上都會連工具與系統提示的快取一起失效。Anthropic 文件 2026
  7. effort 等級（官方文件）：Opus 5.5 預設 medium，適合範圍清楚的日常開發；修既有程式的 bug、需要驗證邊界條件時用 high；max 適合讓它長時間獨立處理的難題，但官方提醒 max 可能報酬遞減、容易想太多，先測試再大量使用。Anthropic 文件 2026
  8. 壓縮工具輸出：token 少了，帳單沒少新增：Claude Code 上 103 個任務、2,848 次執行的成對比較（多數用 Haiku 4.5，另有 Sonnet 5 與 Opus 4.8）。一個加了檢索與排序的壓縮外掛讓工具輸出 token 少了 38.4%，實際帳單卻 +6.8%（95% 信賴區間 +2.8% 到 +11.3%）；另一個 API 代理型外掛 +48.4%；規則式的簡單壓縮帳單 −2.7%（−5.6% 到 −0.1%），但它的工具輸出只少了 1.3%，約佔成本的 0.04%，在保留題組與事後用 Opus 重做時信賴區間都跨過零，所以這 2.7% 很難歸因於壓縮，作者也說只是提示性結果。各組成功率沒有可偵測的差異（基準已有 96%）。Weinberger、Hozez 2026
  9. 錢花在快取，不在工具輸出新增：同一研究中，帳單的 44.3% 是寫入快取、35.4% 是讀取快取、10.4% 是輸出；在跑分用的單次任務中，系統提示與工具定義等 harness 本身就佔約 75% 的成本，工具輸出只佔 3.3%，使用者端外掛碰得到的內容合計約 6%。作者觀察到的軌跡符合一種可能的機制（作者沒有下因果結論）：壓縮省下的 token 被後續多出的診斷、測試與重新檢索抵銷，而每一回合都要重送整段快取內容。在另一組單次生成的實驗中，壓縮讓計費 token 少 73%，但 SEARCH/REPLACE 修補能成功套用的從 27/40 掉到 15/40，因為壓縮改掉了需要逐字比對的程式碼。單一 harness、單一廠商 2026 年 7 月的價格；端到端的帳單比較都是單次 prompt 的跑分：主實驗平均只有約 4.5 回合，另一組長任務實驗（529 個 session、Opus 4.8）方向相同，壓縮外掛同樣沒省到錢。作者另外分析 41 個真實互動 session 的帳單組成，結果很不一樣：harness 只佔約 8% 的輸入 token，外掛碰得到的內容（工具呼叫參數、CLAUDE.md 與提醒文字、較長的工具輸出）約佔 30% 的成本，依同樣的捕捉率推算，壓縮在互動情境能省的上限可能到約 9%，但沒有實測。Weinberger、Hozez 2026

對你的意義

省 token 最有效的是減少無效探索：任務開頭直接指定要看的檔案與範圍、一個任務一個對話、看到 agent 反覆讀同一檔案就中斷重新說明。記下一類任務平常要幾個回合，明顯超過時介入，但上限不要設太緊。一個工作階段中途不要頻繁切換 effort 或 MCP 工具，以免快取失效。更新不要為了省錢加裝壓縮工具輸出、代理 API 的外掛；要比較就看「每個成功任務的實際帳單」，不要看 token 數。真正能省的是少幾個回合，以及少裝用不到的 MCP 工具與冗長的系統設定（它們每回合都被重送）。「不要裝壓縮外掛」的端到端證據只來自單次任務的跑分；多輪互動的 session 中外掛碰得到的內容比例較高，效果可能不同，要比就用自己的帳單量。

三多 agent：通常更貴，不一定更好

  1. 六種多 agent 流程有五種輸給單一 agent更新：同樣用 GPT-4.1、10 個 benchmark（數學、問答、HumanEval、MBPP 等，都不是在 repo 裡寫程式的 agent 任務）、每種跑 3 次；各流程是作者在共用步數上限下重新實作的版本，不是原始系統。五種流程的合併準確率落後 1.71 到 8.76 個百分點，每次都輸；唯一勝出的 EvoAgent 多 3.05 個百分點，3 次都贏，token 多用 27%。token 用得多不代表比較準：兩種辯論式流程用了 1.39 與 4.34 倍的 token，準確率反而較低。沒有統計檢定。但在最接近 agent 任務、需要檔案檢視與工具使用的 GAIA 上（各跑一次），五種固定流程有三種高於單一 agent，其中兩種只高 1 到 2 個百分點，Jarvis 高 9 個百分點、token 還比較少，EvoAgent 反而較低；換成 Qwen3-32B 時全部輸給單一 agent。所以在 agent 任務上，這篇的證據是混合的。依 2026 年 10 月的 v2（v1 每種只跑一次，數字不同）。Fu 等 2026
  2. agent 團隊成本高 1.8 到 5.1 倍：50 個網頁應用程式、8 種設定各跑一次，四組「團隊 vs 單一 agent」只有一組顯著提升（GPT 6 Sol 中等 effort，+7.3 個百分點）。Claude Opus 5.5 中等 effort 時團隊 −0.3 個百分點；max effort 團隊每個應用程式 122 美元、單一 agent 23.77 美元，分數差距不顯著。多出的成本主要是每個子 agent 重新讀入的快取輸入。Vals AI 2026

對你的意義

預設用單一 agent。只有在工作真的能切成互不相依的部分（例如同時查幾個獨立模組），才考慮子 agent，並先比較成本。
