AI Agent 研究（一）：Skill 與說明檔

整理日期：2026 年 11 月 2 日 · 18 篇參考文獻 · 全文查核版
一句話總結：skill 和說明檔平均有幫助，但很不穩定。人工寫、少而精、註明適用條件的才有效；讓模型自己產生的 skill 或說明檔多半沒用甚至扣分，而且公開 skill 約四分之一有安全漏洞。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一Skill 有沒有用：平均有幫助，但很不穩定

  1. 人工寫的 skill 平均有效：87 個任務、18 組模型與 harness、每格 3 次，加上人工 skill 後通過率從 33.9% 提升到 50.5%（+16.6 個百分點）。軟體工程類 +11.6 個百分點，各領域介於 +9.7 到 +28.8。SkillsBench 2026
  2. 有些任務反而變差：87 個任務中有 13 個加了 skill 後變差。SkillsBench 2026
  3. 讓模型自己寫 skill 反而扣分：三組專用 harness 上，自生成 skill 比不用 skill 低 8.1 到 11.5 個百分點。SkillsBench 2026
  4. 真實情境下效益大幅縮水：當 agent 要從 34,198 個真實 skill 中自己檢索，Claude Opus 4.6 的增益從強制載入時的約 20 個百分點降到約 3 個；Kimi 與 Qwen 甚至低於不用 skill。每種設定跑 3 次，沒有信賴區間。Skills in the Wild 2026
  5. 針對任務改寫 skill 能救回一部分：Terminal-Bench 2.0 上，Claude Opus 4.6 從無 skill 的 57.7% 提升到 65.5%，但單靠檢索只有 61.4%，提升主要來自「針對該任務改寫」這一步，而且每題要多跑一次探索。Skills in the Wild 2026
  6. 軟體工程 skill 大多沒差：49 個公開的軟體工程 skill、約 565 個真實 repo 任務，39 個零提升，平均 +1.2%；token 用量從 −78% 到 +451%；7 個專門 skill 最高 +30%；3 個因版本不符最多 −10%。SWE-Skills-Bench 2026
  7. 同一個 skill 換模型就可能變差：9 組配置平均都提升（+4.6 到 +19.5 個百分點），但 36.78% 的任務在某些配置變好、在另一些變差。Downstream Utility 2026
  8. 模型做不來 skill 推薦的方法時，表現低於無 skill：排考程任務中 skill 推薦整數規劃，DeepSeek 搭 Codex 不用 skill 時 3 次全過，用了 skill 3 次全部逾時；GPT 用同一組 skill，求解器失敗後改用允許的啟發式方法，3 次全過。Downstream Utility 2026
  9. 強模型從 skill 得到的增益較大：三種 harness 下 GPT 的增益都比 Qwen 多 3.45 到 8.43 個百分點。只比較兩個模型，不宜當成普遍規律。Downstream Utility 2026
  10. 「有載入」不等於「有照做」：79 個 skill、177 個任務、8 個模型、2 種 harness，最佳綜合分數只有 0.613（GPT-5.5 搭 Claude Code）。觸發率 97% 的配置，照做程度仍只有 0.625；綜合分數低於約 0.5 時，任務表現就低於不用 skill。Skill-Use 2026

對你的意義

skill 值得用在「agent 自己查不到、而且你反覆在做」的流程，例如 SDK 的特定呼叫順序或量測步驟。通用的程式寫法 skill 多半沒效益。新增 skill 後，用幾個真實任務比較有無 skill 的結果，再決定要不要留。

二SKILL.md 怎麼寫

  1. 真實世界的 skill 幾乎都有缺陷：超過 99% 至少有一種「skill smell」，平均每個 10.5 種。最常見的是沒防止 agent 合理化跳過步驟（94%）、關鍵警告埋在內文（81%）、沒有規劃階段（78%）、沒有驗證步驟（69%）；smell 出現後幾乎不會被修掉。Anatomy to Smells 2026
  2. 少量、精簡最好：一次給 2～3 個 skill 增益 +19.0 個百分點，4 個以上只有 +10.1；精簡型 +19.0、標準型 +21.5、詳細型 +14.5，寫成完整文件的只有 +0.7。這是兩組不同的比較（數量、複雜度），不能直接相比。SkillsBench 2026
  3. skill 造成的失敗，多半不是選錯 skill：307 個由 skill 造成的失敗（125 個功能失敗、182 個效率退化）中，skill 的描述誤導只佔功能失敗的 1.6%；68.8% 是 agent 照 skill 做了卻漏掉或填錯任務要求，包括把範例或預設值當成規則；19.2% 把產出放到和任務指定不同的位置。效率退化有 62.6% 來自流程過重，其中過度驗證最多。只測一個模型、一種 harness，標註沒有報告評分者一致性。Agent Skills Can Be Harmful 2026
  4. context 膨脹來自內文：46 個 context 負擔案例中，43 個來自每次都載入的 skill 內文。Agent Skills Can Be Harmful 2026
  5. 壓縮 skill 不太會傷品質：600 個 skill 平均把描述壓縮 48%、內文壓縮 39%，壓縮後分數 0.742 對原版 0.722（p = 0.002，但效果量很小，d = 0.107）；86% 的 skill 壓縮後不低於原版。評分標準同時也是優化目標，數字可能偏樂觀。SkillReducer 2026
  6. 內文多是不必要的內容：抽樣 90 個 skill，只有 38.5% 的條目是核心規則。SkillReducer 2026
  7. 多個 skill 協作時，寫出依賴關係：寫成產物依賴圖（Dependency DAG）比不給組織指示高 6.5 到 11.4 個百分點，也勝過只寫順序。Downstream Utility 2026
  8. 「相關」不等於「有用」：改用「是否支援任務需要的基本操作」排序候選 skill，第一選擇的通過率提升 4.35 到 5.80 個百分點。Downstream Utility 2026

對你的意義

寫 SKILL.md 的檢查清單：關鍵警告放最前面；明寫「不可跳過」的步驟與驗證方式；範例標明「僅供參考，以任務要求為準」；註明適用的 SDK 版本與環境；內文只放核心規則，細節拆到需要時才讀的附檔；驗證寫一次就好，不要要求反覆檢查。

三CLAUDE.md／AGENTS.md：只寫 agent 查不到的事

  1. 讓 LLM 自動產生的說明檔沒幫助，還更貴：4 組 agent 與模型、138 個附說明檔的任務加 SWE-bench Lite 300 題。自動產生的說明檔讓成功率變化 −0.5% 到 −2%（不顯著），步數多 2.45 到 3.92 步，成本增加約 20% 到 23%（顯著）。Evaluating AGENTS.md 2026
  2. 開發者自己寫的說明檔略有幫助，但不顯著：比沒有說明檔平均 +2.4%（p = 0.21），比自動產生的好（p = 0.038），成本仍增加最多 19%。Evaluating AGENTS.md 2026
  3. agent 確實會照說明檔做事：說明檔提到 uv，每題平均用 1.6 次，沒提到時幾乎不用；提到的 repo 專屬工具每題用約 2.5 次。成本增加正是因為它多跑測試、多讀檔。Evaluating AGENTS.md 2026
  4. 說明檔能縮短時間，但沒測正確性：10 個 repo、124 個小型 PR，Codex 加上 AGENTS.md 後執行時間中位數 −28.6%、輸出 token 中位數 −16.6%（都顯著），總 token 沒有顯著差異。每題只跑一次，正確性只抽 50 題做基本檢查。Lulla 等 2026
  5. 小規模實驗看不出差別：17 個真實任務、2 個 agent、每種設定 3 次，「不給說明檔、每次都給、需要時才查」三種做法的通過率沒有顯著差異。作者指出這個規模只能偵測 30 個百分點以上的差距。Khatri 2026
  6. 大家都在寫什麼：2,303 個說明檔中，測試（75.9%）、實作細節（70.8%）、架構（68.1%）最常見；安全只有 14.8%、效能只有 14.5%。檔案中位數 335 到 535 字，大多持續增加內容、很少刪減。Agent READMEs 2025
  7. 指令越多，越容易漏：在「報告中包含指定關鍵字」的人工任務上，最強模型在 500 條指令時只做到 68.9%；靠後的指令較常被忽略，錯誤以完全漏掉為主。這是人工設計的關鍵字任務，不等於真實程式指令。IFScale 2025
  8. 對話被壓縮後，規則會消失：只在對話中講過的規則，長對話被壓縮摘要後，7 個模型合計有 30% 的機率違反（最高 59%），完整保留對話時是 0%。在 3 個模型、5 個軟性規則任務上，規則放在系統訊息時違規增加 0 個百分點，放在使用者訊息時增加 50 個百分點。五模型重複實驗：違規增加 37 個百分點（95% 信賴區間 31 到 43）。Chen 2026

對你的意義

CLAUDE.md 只寫 README 沒有、agent 自己查不到的事：建置與測試指令、SDK 的硬體限制、即時執行緒不可配置記憶體這類規則。不要用 /init 自動產生後直接留用。重要規則寫進 CLAUDE.md，不要只在對話中說，因為長對話壓縮後可能被丟掉。

四Skill 與套件的安全風險

  1. 約四分之一的公開 skill 有漏洞：31,132 個 skill 中 26.1% 至少有一個漏洞（作者估計真實範圍 23% 到 30%）；附帶腳本的 skill 有漏洞的機率是純指令型的 2.12 倍。偵測工具在 200 個人工標註樣本上精確率 86.7%、召回率 82.5%。Skills in the Wild 安全 2026
  2. 憑證最常從輸出外洩：17,022 個 skill 中 3.1% 有憑證外洩問題；73.5% 的漏洞來自把憑證 print 或寫進 log，而 agent 會把這些輸出讀進 context。經實際執行確認，89.6% 可在不提權的情況下利用。Chen 等 2026
  3. 確實有惡意 skill：98,380 個 skill 中確認 157 個惡意（0.16%），70.1% 是竊取資料型；其中 54.1% 來自同一個發布者。揭露後全部下架。作者指出 157 是下限。Malicious Agent Skills 2026
  4. AI 仍會推薦不存在的套件：2026 年 5 個模型、約 20 萬次生成，推薦不存在套件的比例 4.62% 到 6.10%；5 個模型都會幻覺出的 127 個名稱中，53 個仍可被搶註。單一作者的預印本，未測 agent 情境。Churilov 2026

對你的意義

不要直接裝來路不明的 skill，尤其附腳本的；裝之前先讀過腳本。自己寫的 skill 不要 print 金鑰。agent 建議新增的相依套件，先確認名稱真的存在、是你要的那個。

AI Agent 研究（二）：規劃、測試與省 token

整理日期：2026 年 11 月 2 日 · 10 篇參考文獻 · 全文查核版
一句話總結：先有測試、任務切小、減少無效探索，比加規劃步驟或多開 agent 有效。token 花得多不代表做得好，多 agent 通常更貴、不一定更好。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一規劃與測試

  1. agent 常不照自己宣告的計畫做：在 SWE-bench 上，agent 宣告計畫後，完整照順序執行的軌跡只有 12.1% 到 25.4%；計畫越長越少照做。只給計畫當參考時，任務成功率提升有限。自動比對工具和人工的一致性中等（κ 約 0.3）。Oota 等 2026
  2. 先寫測試再寫程式有幫助：repo 層級的 Python 任務上，「先產生測試、再同時修正測試與程式」比 mini-SWE-agent 高 6.4 到 16.9 個百分點；拿掉先寫測試或拿掉同時修正，效果都下降。只測 Python、沒有統計檢定；最常見的失敗是程式通過自己寫的測試，但沒通過 repo 原本的測試。TDD-Agent 2026
  3. 多輪修改會把原本對的東西改壞：542 題單一函式的 Python 題目、每題 8 輪固定修改要求，第 8 輪時 GPT-4o 原有測試通過率從 90.2% 降到 72.4%，Llama-3.1-8B 從 76.1% 降到 31.6%。Huang 等 2026
  4. 每輪重跑測試、退步就退回：DeepSeek-V3 第 8 輪通過率從 75.8% 提升到 87.9%，Llama-3.1-8B 從 31.6% 提升到 47.3%。但修正用的測試就是評分用的測試，等於提前知道答案；只測兩個模型、沒有統計檢定。Huang 等 2026
  5. 把意圖交代清楚，差很多：加一個專門推測使用者目標與偏好的輔助 agent，在 GPT-5 模擬使用者的 500 題中，成功率從 18.1% 提升到 59.7%（論文前言另寫 13.5% 與 57.4%）；17 位開發者三週的真人使用中，86.2% 的建議被採用或稍改後採用，但沒有對照組。ToM-SWE 2026

對你的意義

計畫寫下來不會自動被執行，要在關鍵步驟設檢查點，或把計畫拆成一步一步的小任務。效果最一致的是「先有測試」：先讓 agent 寫或補測試，你確認測試合理後再讓它改程式，每次改完跑完整回歸測試。

二省 token：錢花在哪、怎麼省

  1. token 多不等於做得好：SWE-bench Verified 500 題、8 個模型、每題 4 次，成本最低的一群之後，花更多 token 準確率就不再提升甚至下降；花費高的執行常是反覆讀同一檔案、改了又改。同一題不同次執行，最貴的平均約是最便宜的 2 倍。Bai 等 2026
  2. 成本主要是輸入：即使有快取，讀取快取仍是金額最大的一項；探索與修改兩個階段約佔三分之二的回合。只分析一個模型。Bai 等 2026
  3. 限制回合數能省錢，但會少解幾題：100 題、3 個模型、每種設定只跑一次。上限設在第 75 百分位時，成本降 23.6%（Claude）、38.4%（GPT 4.1）、68.3%（Gemini），解題數分別 −4、−5、+2 題；設在第 25 百分位時 Gemini 從 63 題掉到 26 題。需要時才追加回合，成本可再降約 6% 到 24%（摘要寫 12% 到 24%，與表格不符）。百分位是用同一批題目算的，沒有另外驗證。Gao、Peng 2026
  4. context 小時，管理機制很重要；夠大時差異很小：4 個模型、2 個 benchmark，context 只有 32k 時，有管理機制比沒有高 35.7 個百分點（SWE-bench），到 128k 時只差 2.7。Fan 等 2026
  5. 規劃步驟主要幫弱模型：最小的 30B 模型加規劃後 SWE-bench 從 13.6% 提升到 25.2%；較強的模型沒有一致的提升，但有些能少花 26% 到 32% 的成本。只用 bash、不給專用工具，弱模型掉 15 個百分點，最強模型反而 +3.6、成本 −53%。每種設定看起來只跑一次，但有做配對檢定與多重比較校正。Fan 等 2026
  6. 快取價格（官方文件）：讀取快取一般是輸入價格的 0.1 倍，Opus 5.5 與 Sonnet 5.5 是 0.05 倍；寫入快取 1.25 倍（5 分鐘）或 2 倍（1 小時）。修改工具定義會讓整個快取失效；變更 effort 或 thinking 設定會讓對話部分的快取失效。Anthropic 文件 2026
  7. effort 等級（官方文件）：Opus 5.5 預設 medium，適合範圍清楚的日常開發；修既有程式的 bug、需要驗證邊界條件時用 high；max 適合讓它長時間獨立處理的難題，但官方提醒 max 可能報酬遞減、容易想太多，先測試再大量使用。Anthropic 文件 2026

對你的意義

省 token 最有效的是減少無效探索：任務開頭直接指定要看的檔案與範圍、一個任務一個對話、看到 agent 反覆讀同一檔案就中斷重新說明。記下一類任務平常要幾個回合，明顯超過時介入，但上限不要設太緊。一個工作階段中途不要頻繁切換 effort 或 MCP 工具，以免快取失效。

三多 agent：通常更貴，不一定更好

  1. 六種多 agent 流程有五種輸給單一 agent：同樣用 GPT-4.1、10 個 benchmark，五種固定流程平均落後 2.56 到 11.29 個百分點；唯一勝出的只多 1.44 個百分點，在誤差範圍內。每種只跑一次。Fu 等 2026
  2. agent 團隊成本高 1.8 到 5.1 倍：50 個網頁應用程式、8 種設定各跑一次，四組「團隊 vs 單一 agent」只有一組顯著提升（GPT 6 Sol 中等 effort，+7.3 個百分點）。Claude Opus 5.5 中等 effort 時團隊 −0.3 個百分點；max effort 團隊每個應用程式 122 美元、單一 agent 23.77 美元，分數差距不顯著。多出的成本主要是每個子 agent 重新讀入的快取輸入。Vals AI 2026

對你的意義

預設用單一 agent。只有在工作真的能切成互不相依的部分（例如同時查幾個獨立模組），才考慮子 agent，並先比較成本。

AI Agent 研究（三）：生產力與程式品質

整理日期：2026 年 11 月 2 日 · 10 篇參考文獻 · 全文查核版
一句話總結：AI 不一定讓資深開發者變快，品質下降卻會持續。效能類修改最難被接受，C++ 與多檔案修改仍明顯比 Python 單檔難，所以量測、CI 與人工審查不能省。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一AI 真的讓人變快嗎

  1. 2025 年初：資深開發者在自己的專案上反而變慢：16 位資深開源開發者、246 個真實任務隨機分組，可用 AI 時完成時間增加 19%（信賴區間 +2% 到 +39%）；他們事前預期快 24%，事後仍以為快了 20%。工具主要是 Cursor 搭 Claude 3.5／3.7 Sonnet。METR 2025
  2. 2026 年追蹤：可能變快了，但數據無法確認：57 位開發者、800 多個任務，原參與者 −18%（信賴區間 −38% 到 +9%）、新參與者 −4%（−15% 到 +9%），負數代表變快，但都不顯著。很多人拒絕在不用 AI 的情況下工作，30% 到 50% 的人沒送出不想手寫的任務，METR 認為這是低估。METR 2026
  3. 速度提升短暫，品質下降持續：806 個採用 Cursor 的 GitHub 專案對比 1,380 個配對專案，新增程式碼行數在第一個月增加數倍，約兩個月後消失；靜態分析警告增加約 30%、程式複雜度增加約 41%，而且持續存在，並會拖慢之後的開發。He 等 2026
  4. 用 AI 學新東西，理解會變差：52 位工程師隨機分組學一個新的 Python 非同步函式庫，用 AI 組測驗分數低 17%（d = 0.738，p = 0.010），時間沒有顯著差異；差距最大的是除錯題。只問概念、自己解決錯誤的人分數較高，但這部分樣本很小、是探索性分析。Shen、Tamkin 2026

對你的意義

在你熟悉的大型 C++ 專案上，AI 不一定讓你變快，要自己量。品質下降是持續的，所以靜態分析與審查不能省。學新的 SDK 或演算法時，先自己理解，只把 AI 當成問概念的對象。

二什麼樣的 agent 產出會被接受

  1. 任務類型影響最大：7,156 個 agent 送出的 PR，整體接受率 69.3%；雜務類 84.0%、文件 82.1%，修 bug 66.0%、測試 61.5%，效能類最低只有 55.4%。觀察性資料，不能推論因果。Pinna 等 2026
  2. 效能類的 agent PR 較少附量測：2,260 個效能 PR，agent 寫的有附驗證的比例和人相近（82.3% 對 80.6%），但較多只靠推理說明（51.4% 對 39.3%），較少跑 benchmark（46.1% 對 57.2%）；合併率 54.4% 對 73.3%。約一半有驗證的 PR 沒附任何量化數字。Peng 等 2026
  3. 多數被接受的 agent PR 沒經修改：9,427 個已結案的 agent PR，被接受的中外圍貢獻者 76.5%、核心開發者約 72% 沒經修改。核心開發者審得比較仔細（審查留言 3.6 則對 2.0 則，有統計檢定、效果量小）；沒跑 CI 就合併的比例，外圍 19.1%、核心 11.2%（未檢定）。Cynthia 等 2026
  4. 只有 AI 審查的 PR 合併率較低：只經 AI 審查的 PR 合併率 45.2%，只經人審查的 68.4%；13 個 AI 審查工具中 12 個的有效建議比例低於 60%。沒有控制 PR 大小等因素。Chowdhury 等 2026
  5. 真實的多檔案工作仍然很難：參考解答平均改 4.1 個檔案、107.4 行的題目上，公開題目最佳 43.6%、企業內部題目最佳 17.8%。Claude Sonnet 4 的失敗中 35.6% 是 context 爆掉、17.0% 是不停讀檔。作者指出 C++ 題目偏少。SWE-Bench Pro 2026
  6. C++ 明顯比 Python 難：2025 年的多語言基準中，Python 最佳 52.2%，C++ 最佳只有 14.73%、C 只有 9.38%；改越多檔案、補丁越長，成功率越低。用的是 2025 年的模型，C++ 只有 129 題。Multi-SWE-bench 2025

對你的意義

效能相關的修改，要求 agent 附上修改前後的量測數字，沒數字不合併。跨模組的修改先拆小、直接指定檔案。合併前一定跑 CI 並親自審查，AI 審查只當補充。

AI Agent 研究（四）：MCP 與平行程式

整理日期：2026 年 11 月 2 日 · 10 篇參考文獻 · 全文查核版
一句話總結：接上工具不代表會用，平行程式也不會自動調好。工具描述與介面設計影響很大；效能來自「正確性檢查加 profiling」的迴路，而且要防 agent 偷改條件、漏掉同步。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一MCP 與工具設計

  1. 接上工具不代表會用：36 個真實 MCP server、1,000 個任務、20 個模型，最佳通過率 82.2%。約 6,900 個失敗中，63.3% 是理解、整合或太早停止，只有 36.7% 和工具有關（不用工具 10.5%、錯誤後無法恢復 10.3%、選錯工具 9.0%、參數錯誤 6.9%）。評分用 LLM 評審，不同評審差 2 到 5 個百分點。MCP-Atlas 2026
  2. 工具描述幾乎都寫得不好：103 個 MCP server、856 個工具中，97.1% 的描述至少有一個缺陷；89.8% 沒寫限制、89.3% 沒寫使用時機。補齊描述後任務成功率中位數 +5.85 個百分點，但執行步數 +67%。只有一個模型做了配對比較（p = 0.02）。Hasan 等 2026
  3. 專有工具做成 MCP server 的實例：把嵌入式硬體設計工具做成 14 個 MCP 工具，7 個本地開源模型中最強的完成 99% 的預期呼叫；工具描述精簡後，每個模型的工具失敗率都上升，多數約加倍；加入範例反而讓部分模型停止動作。沒有統計檢定，benchmark 未公開。Liparulo、Pierri 2026
  4. 工具介面設計影響很大：同一模型下，專為 agent 設計的介面比只給 shell 高 64%（相對值）。拿掉編輯時的語法檢查掉 3 個百分點；搜尋結果一次只給一筆，比完全不給搜尋工具還差；檔案檢視視窗 100 行最好，30 行或整個檔案都變差。SWE-agent 2024

對你的意義

如果要把 SD-OCT SDK 包成 MCP server，工具描述要寫清楚用途、使用時機、限制與參數單位；輸出要精簡、摘要好，不要一次倒出整段原始資料。工具數量少而清楚，比多而模糊好。

二平行程式與 GPU：AI 會寫，但要靠迴路校正

  1. 平行程式比循序程式難很多：420 題、7 種執行模型，GPT-4 循序程式 pass@1 約 76%，平行程式平均只有 37.8%；OpenMP 約 60% 最好，MPI 約 23% 最差。寫對的程式也常常很慢，平行效率最高只有 0.13。ParEval 2024
  2. 整個專案的轉換幾乎都失敗：6 個 HPC 應用程式在 CUDA、OpenMP Offload、Kokkos 之間轉換，除了最小的範例外，沒有任何方法與模型組合成功。主要失敗是 CMake 與 Makefile、跨檔案介面不一致。ParEval-Repo 2025
  3. 執行與 profiling 回饋能大幅提升：GPU kernel 基準 250 題，DeepSeek R1 一次產生時比 PyTorch 快的比例 Level 1 為 12%、Level 2 為 36%；加上 10 輪執行結果與 profiler 回饋後提升到 43% 與 72%。正確性只用 5 組隨機輸入檢查。KernelBench 2025
  4. 正確性檢查加 profiling 的流程穩定有效：把 Codex 改成「找熱點、規劃資料搬移、正確性檢查、依 profiling 修改」的流程轉成 OpenMP GPU offload，31 個有效 kernel 全部正確、27 個比參考實作快或持平；HeCBench 幾何平均 3.1 倍（A100）與 3.6 倍（RTX 4060），不加流程的同一模型只有 2.0 倍與 2.4 倍，Rodinia 甚至變慢（0.30 倍）。token 只多約 11%。沒有拆開測各步驟的貢獻。Kaplan 等 2026
  5. agent 會偷懶：上述研究被排除的 kernel 中，有 2 個是 agent 把主要運算留在 CPU 上。Kaplan 等 2026
  6. 專門訓練的模型可以超越通用模型，但你用不到：用強化學習專門訓練的 CUDA agent，在 KernelBench 上 96.8% 的題目比 torch.compile 快；同一流程下 Claude Opus 4.5 只有 66.4%。每種設定只跑一次，且挑最佳解時用了評分指標本身。CUDA Agent 2026
  7. agent 會偷改題目條件、漏掉同步問題：多 agent 調校 HPC 程式的實驗中，agent 擅自把矩陣從 2048 放大到 8192 或 16384，監督角色都沒發現；一個缺少同步的 CUDA 版本通過了測試，錯誤沒被抓到。每種條件只跑 3 次，作者承認不足以下統計結論。VibeCodeHPC 2025

對你的意義

新模型不會自動把平行程式調好，效能來自你搭的迴路：固定的參考答案與容許誤差、固定問題大小的量測腳本、profiler 輸出、以及「運算確實在 GPU 上、執行緒同步正確」的檢查。即時系統的時序與同步錯誤，一般測試很難抓到，要另外設計壓力測試或用 sanitizer。建置系統的修改由你把關。

AI Agent 研究（五）：做法總結與查核紀錄

整理日期：2026 年 11 月 2 日 · 依前四篇研究整理 · 全文查核版
一句話總結：agent 的效益取決於你搭的迴路。這篇把前四篇整理成可執行的做法，並記錄這次全文查核更正了什麼、刪除了哪些研究與原因。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一整理成做法

以下是整理者依前四篇研究提出的做法，效果仍要在自己的專案上驗證。

  1. 先準備驗證工具：回歸測試、參考輸出、量測腳本、profiler 指令都先備好，再讓 agent 動手；每次修改都跑完整測試，退步就退回。
  2. CLAUDE.md 精簡：只寫建置與測試指令、硬體與即時限制、不可違反的規則；不要自動產生後直接留用。
  3. skill 少而精：只為反覆出現、agent 查不到的流程寫 skill；關鍵警告放最前面，註明版本，驗證寫一次；新增後用真實任務比較有無 skill。
  4. 任務要小、範圍要明：開頭交代目標、限制與要看的檔案；跨模組的修改拆成小任務；一個任務一個對話。
  5. 盯著執行過程：反覆讀同一檔案或改了又改就中斷；明顯超過平常回合數就重新說明。
  6. effort 用預設：日常用 medium，修既有程式的 bug 開 high，max 只在測過確實有效時用。
  7. 單一 agent 優先：子 agent 只用在可以完全切開的工作。
  8. 效能修改要附數字：要求修改前後的量測結果，並檢查運算在目標硬體上、同步正確。
  9. 安全：不裝來路不明的 skill；新增相依套件先確認存在；合併前跑 CI、親自審查。

二這次查核更正了什麼

  1. SkillsBench 數字依最新版更正：舊筆記寫的 +16.2 個百分點、軟體工程 +4.5、醫療 +51.9、84 題中 16 題變差、自生成 skill「無益」，都來自較早的版本。最新版是 87 題、+16.6 個百分點、軟體工程 +11.6、沒有醫療類、13 題變差、自生成 skill 低 8.1 到 11.5 個百分點。
  2. 多 agent 研究數字更正：舊筆記寫五種流程落後 1.71 到 8.76 個百分點，全文是 2.56 到 11.29。
  3. 「skill 造成的失敗」描述更正：1.6% 是 skill 描述誤導，不是「選錯 skill」；19.2% 是放錯位置，論文沒說是「skill 偏好的位置」。
  4. 說明檔效率研究補上限制：Lulla 等的研究沒有測正確性，只測時間與 token。
  5. 效能 PR 研究已讀全文：先前只讀摘要，數字經核對無誤。

三刪除的研究與原因

  1. 關鍵章節讀不到：More Skills, Worse Agents?（實驗章節未能讀到，「最多掉 21%」無法核對）、KernelPro（結果表格未能讀到）、ParBench（網站限制連線，無法讀取）。
  2. 論文本身有問題：LLM-HPC++（表格數字前後矛盾）、Evidence Over Plans（「壓縮越多效果越差」的說法沒有報告數字）。
  3. 方法太弱：Tokenomics（只用一個舊的多 agent 框架、30 題、無統計）、Where Do the Tokens Go?（每種設定只跑一次，作者自己承認無法區分方法效果與隨機變異）、Spec-Driven Development（概念分析，沒有自己的資料）。
  4. 與你的工作關係較遠：Context Rot（網頁搜尋任務，不是程式）、ConFixAgent（只測 Java）、CodegenBench（單次生成、非 agent，主要測非 x86 平台）、SkillRouter 與 SkillEval（大型 skill 庫的檢索與評分）、Who Will Become the Next Senior?（14 人訪談，談新人培育）。
  5. 只讀到摘要：Meta 的兩篇測試生成研究、SciCode、FormAI-v2、Lost in the Middle、套件幻覺原始研究（改引用已讀全文的 2026 年重現研究）、Agent Skill 評估綜述。
  6. 非研究資料：Anthropic 子 agent 技術文章、TechCrunch 報導。
