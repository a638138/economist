AI Agent Skill 與 md 檔：研究整理

整理日期：2026 年 10 月 27 日 · 22 篇參考文獻 · 合併「Skill與說明檔_研究整理_完整版」並補充 8 篇新研究（標示新增）
一句話總結：skill 和 md 檔不是越多越好，人寫、聚焦、補上模型不知道的領域知識才有效。軟體工程是 skill 效益最低的領域，模型自己生成的 skill 平均沒有幫助；值不值得留，要在自己的專案上用有／無 skill 的對照實驗量。
關於時效：多數研究是 2026 年的 arXiv 預印本，尚未全部經過同儕審查，結果也互有出入。比較耐用的是「方法」（成對比較、用確定型測試判斷、在自己的專案上做實驗），容易過時的是「數字」。
第一部分　Skill 有沒有用

一、Skill 效益：依領域、模型與 harness 而定

理想條件下平均 +16pp，軟體工程或真實檢索情境下幾乎歸零，而且同一個 skill 換個執行環境可能由正轉負。

研究設計關鍵結果
SkillsBench（NeurIPS 2026）84–86 任務 × 7 組模型／harness；無 skill／人工 skill／自生成 skill人工 skill 平均 +16.2pp；軟體工程 +4.5pp、醫療 +51.9pp；16 個任務變差；自生成 skill 平均無益；2–3 模組的精簡 skill 勝過完整文件
SWE-Skills-Bench（2026）49 個公開 SWE skill × 真實 GitHub repo，約 565 任務39 個 skill 零提升，平均 +1.2%；token −78% 到 +451%；7 個專門 skill 最高 +30%；3 個因版本不符最多 −10%
Skills in the Wild（2026）新增agent 須從 34k 個真實 skill 自行檢索情境越真實效益越低，最難設定接近無 skill；針對任務改寫 skill 可回收大部分損失（Terminal-Bench 2.0：57.7% → 65.5%）
Downstream Utility（2026）新增87 任務 × 3 模型 × 3 harness9 組配置平均都提升（+4.6 到 +19.5pp），但 36.78% 的任務在某些配置變好、另一些變差；相關度第一的 skill 在 23.19% 的情況不是最好的
Skill-Use（2026）新增79 個 skill × 177 任務，分測觸發／遵循／邊界最強配置綜合分數只有 0.613；觸發與遵循是兩個獨立瓶頸；排名隨 harness 改變

為什麼會失敗

307 個由 skill 造成的失敗中，選錯 skill 只佔功能失敗的 1.6%；68.8% 是相關的 skill 讓 agent 把範例或預設值當成規則。效率退化有 62.6% 來自過度驗證與過重的流程。Agent Skills Can Be Harmful 2026

  • 「相關」不等於「有用」：改用「是否支援任務所需的原子操作」重新排序候選 skill，第一選擇的通過率提升 4.35–5.80pp。Downstream Utility 2026
  • 模型做不來 skill 推薦的方法時，表現會低於無 skill。例如排考程任務中，skill 推薦用整數規劃，DeepSeek + Codex 不用 skill 時 3 次全過，用了 skill 反而 3 次全部逾時；GPT 用同一組 skill 則在求解器失敗後改用允許的啟發式方法，3 次全過。Downstream Utility 2026（Finding 1）
  • 在 GPT 與 Qwen 的比較中，基礎較強的模型從 skill 得到的增益較大：三種 harness 下 GPT 的增益都比 Qwen 多 3.45–8.43pp，OpenCode 下兩者差距從 10.73pp 擴大到 19.16pp。這只比較了兩個模型，不宜視為普遍規律；也和 SkillsBench「小模型加 skill 可追上沒有 skill 的大模型」不衝突。Downstream Utility 2026（RQ1）SkillsBench 2026

對你的意義：一般程式知識模型已經會了。skill 的價值在補上它不會的領域流程（OCT 校正、QC 判讀），而且版本要跟著硬體 SDK 與函式庫更新。

二、Skill 越多越好嗎：選取與規模

  • skill 庫從一小組擴充到 202 個時，表現最多下降 21%，主因是選錯的頻率上升。More Skills, Worse Agents? 2026
  • 在約 80K 個 skill 的池中，只靠 name + description 選取，準確度比加上內文低 29–44pp。description 是入口，但內文寫得清楚也影響能不能被選中。SkillRouter 2026新增
  • agent 常常沒觸發該用的 skill，觸發了也不一定照做。Skill-Use 2026新增

對你的意義：skill 少而精，每個 skill 的描述要能清楚區分「什麼時候該用我」。

第二部分　怎麼寫

三、SKILL.md 怎麼寫

好的 SKILL.md 在三組對立之間取得平衡：指引夠用但不寫死、有驗證回饋但不過度、脈絡充足但聚焦。真實世界的 skill 幾乎都沒做到：超過 99% 至少有一種「skill smell」，平均每個 10.5 種。From Anatomy to Smells 2026新增

最常見的問題

沒有防止 agent 合理化跳過步驟（94%）、關鍵警告埋在內文（81%）、沒有規劃階段（78%）、沒有驗證步驟（69%）。smell 一旦出現幾乎不會被修掉。Anatomy to Smells 2026

刪廢話會變好

55,315 個 skill 中 26.4% 沒有路由描述，超過 60% 內文不可執行。description 壓縮 48%、內文壓縮 39%，品質反而 +2.8%。SkillReducer 2026

但不能壓過頭

壓縮比越高、效果越差，代表過度壓縮會丟掉可執行的細節。要刪的是背景與廢話，不是操作步驟。Evidence Over Plans 2026

寫作檢核清單

  1. description = 做什麼 + 何時用 + 關鍵字，第三人稱，不超過 1,024 字元；也寫出「何時不該用」。
  2. 內文只放必要規則與步驟，細節、範例參數、疑難排解放 reference 檔，並寫明何時該讀哪一份。
  3. 範例標成範例：標出哪些值要替換、哪些結構要保留，避免 agent 把範例當規則。
  4. 寫出目標與驗收條件，不要只列一串固定指令；每個關鍵需求寫明檢查什麼、怎樣算通過。
  5. 驗證強度依風險調整：寫明哪些改動需要重新驗證，不要預設每次都完整驗證。
  6. 寫失敗處理：如何診斷、何時重試、何時換方法或停下來問人。
  7. 註明適用版本與環境：版本不符是 skill 反而扣分的原因。
  8. 多 skill 協作時寫階段目標或產物依賴：Dependency DAG 比不給組織指示高 6.5–11.4pp，且勝過只寫順序。Downstream Utility 2026
  9. 由人寫或人審，不直接採用 AI 自生成的版本。

四、說明檔（CLAUDE.md、AGENTS.md）

研究結論互相矛盾：一篇顯示省時省 token，一篇顯示降低成功率、增加成本，第三篇顯示對正確性沒影響。差異主要來自量的指標不同（效率 vs 正確性），以及說明檔是人寫還是 AI 生成。

ETH Zurich（2026）

4 種 coding agent：說明檔整體降低成功率、成本增加 20% 以上；人寫的優於 AI 生成的，只在補上訓練資料沒有的知識時才划算。Evaluating AGENTS.md 2026

Lulla 等（2026）

Codex、10 個 repo、124 個 PR：中位執行時間 −28.64%、輸出 token −16.58%，但沒有評估正確性。AGENTS.md Efficiency 2026

Two-Agent Ablation（2026）新增

Claude Code + Codex、288 次執行：說明檔對正確性的影響不超過 10–15pp；失敗多半是實作能力不足，不是缺 repo 知識。Ablation 2026

大家實際上怎麼寫：分析 2,303 個說明檔，最常寫測試流程（75.9%）、實作細節、架構，很少寫安全與效能規範，且像設定檔一樣持續小幅新增。Agent READMEs 2025

可行的寫法

  • 只寫程式碼看不出來、又會悄悄出錯的規則：特殊 build 指令、單位與座標慣例、硬體相關限制。
  • 不寫架構介紹、目錄說明、用了哪些套件：agent 讀程式碼就知道。
  • 最重要的規則放最前面：模型在 500 條指令時遵守率只有 68%，且偏好較早出現的指令；中段資訊最容易被忽略。IFScale 2025Lost in the Middle 2024
  • 不要讓 AI 自動產生整份說明檔再直接用。
第三部分　安全與實務

五、Skill 安全

從外部安裝的 skill 約四分之一含漏洞，要當成第三方套件審查。

研究樣本結果
Agent Skills in the Wild（2026）31,132 個 skill26.1% 至少含一個漏洞；附帶腳本的 skill 含漏洞機率是純指令型的 2.12 倍
Malicious Agent Skills（2026）新增98,380 個 skill 行為驗證確認 157 個惡意 skill、632 個漏洞，分為竊取憑證與劫持 agent 決策兩類
Credential Leakage（2026）新增17,022 個 skill520 個 skill 有 1,708 個憑證外洩問題，歸納出 10 種外洩模式

對你的意義：安裝前讀完 SKILL.md 與所有腳本，留意 HTML 註解等隱藏指令；不在 skill 裡寫入 API key 或密碼。

六、實務建議與 A/B 評估

研究結論只能告訴你從哪裡下手。skill 值不值得留，要在自己的專案上量。

適合寫成 skill

雙 COG 校正、k(n) 校正表建立、QC 指標判讀、特定 SDK 版本的初始化順序與陷阱：模型訓練時幾乎沒看過的領域流程。

不適合寫成 skill

一般 C++ 風格、通用除錯技巧、套件使用教學：模型已經會了，寫了大多只增加 token。

簡易 A/B 評估流程

  1. 挑 5–10 個有明確驗收條件的真實任務，最好能用測試或腳本自動判定通過與否。
  2. 每個任務在「無 skill」與「有 skill」各跑 3 次，固定同一模型與 harness（換 harness 結果就可能翻轉）。
  3. 記錄通過率、總 token、執行時間；有 skill 時檢查 agent 是否真的觸發並照做。
  4. 通過率沒提升、token 卻明顯增加的 skill，刪掉或精簡；通過率下降的，檢查是否有範例被當規則、版本不符、流程過重。
  5. 模型或 SDK 升級後重跑一次，skill 跟著更新。

「完整版」整理中的 CLAUDE.md（OCT Pipeline）與 SKILL.md（dual-cog-calibration）範例已符合上述原則，可以直接當作第一個 A/B 測試對象。

AI Agent 開發效率：MCP 與平行程式研究整理

整理日期：2026 年 10 月 27 日 · 13 篇參考文獻 · 延伸「AI輔助開發_知識點速覽」的二、五兩個主題
一句話總結：agent 的效率來自「它能自己驗證」，不是模型本身更聰明。平行程式的正確性已經進步很多，但效能調校仍要靠你搭好的回饋迴路：正確性檢查、基準量測、profiler，以及明確禁止的捷徑。MCP 是讓 agent 接上這個迴路的管線，不是效率本身。
關於時效：多數研究是 2025–2026 年的預印本或會議論文，模型更新很快。比較耐用的是「結構性結論」（例如效能需要回饋迴路、建置系統是主要失敗點），絕對數字會隨模型改變。
第一部分　用 agent 會更有效率嗎

一、開發效率的實證：快，但品質要另外顧

速度是短期的，複雜度是長期的

開源專案導入 Cursor 後，第一個月新增程式碼量增加 3–5 倍，約兩個月後回落；但靜態分析警告增加約 30%、程式複雜度增加約 41%，而且持續存在。Speed at the Cost of Quality 2026

任務類型決定成功率

7,156 個 agent 送出的 PR 中，文件類被接受 82.1%，新功能只有 66.1%；沒有一個 agent 在所有任務類型都領先。PR Acceptance 2026

速覽已收錄的 METR 研究也指出：資深開發者用 AI 可能反而變慢，卻自認變快。METR 2025

對你的意義：衡量效率不能只看寫得多快。agent 產出要通過你定義的檢查（測試、靜態分析、效能基準）才算數，否則省下的時間會在後續維護還回去。

第二部分　MCP 是不是方向

二、MCP：價值在讓 agent 接上它碰不到的工具

MCP 是一種協定，讓 agent 用統一方式呼叫外部工具與資料。日常寫程式時，agent 已經能透過終端機跑編譯、測試、git，這部分不需要 MCP；MCP 的價值在接上 agent 原本碰不到的東西，例如量測設備、內部系統、專屬文件。

研究發現代表什麼
MCP-Atlas（2026）36 個真實 MCP server、1,000 個任務：最佳模型通過率約 82%；失敗中 63.3% 是理解、整合或太早停止，不是工具呼叫本身出錯接上工具不難，難的是 agent 會不會用、用完會不會正確整合結果
MCP Tool Descriptions Are Smelly（2026）856 個工具中 97.1% 的描述至少有一個缺陷，56% 沒寫清楚用途；補齊描述後任務成功率中位數 +5.85pp，但執行步數 +67%工具描述品質直接影響效果，但寫得越多不一定越好，精簡組合可兼顧成本
Hardware Design via MCP（2026）為專有嵌入式設計工具做 MCP server，測 7 個本地開源模型：強模型幾乎能完成所有預期呼叫；詳細的工具描述持續降低失敗；累積上下文會拖垮小模型與你的情境最接近：專有工具、機密限制、本地模型也可行

對你的意義

  • 最有價值的 MCP 是你自己的設備：把 SD-OCT SDK 包成 MCP server（擷取、讀取 A-scan、回報量測值），agent 就能在真實硬體上跑「改程式 → 量測 → 比對」的迴路，這是終端機做不到的。
  • 工具要少而精、描述要寫清楚：寫明用途、參數單位、前置條件、錯誤代表什麼；這和 skill 的寫法原則相同。
  • 不要為了用而用：已經有 CLI 的工具（編譯、測試、git），直接讓 agent 用終端機就好。
第三部分　平行程式：模型進步後能自動校正嗎

三、正確性進步了，效能和複雜專案還沒有

研究測什麼結果
CodegenBench（2026）9 個模型（含 Claude Opus 4.7、DeepSeek V4）在 x86、Sunway、Kunpeng 上寫高效平行程式x86 BLAS 最佳正確率 0.74，但達到加速的比例只有 0.52；在文件少的平台（Sunway）正確率大幅崩落，多數產出不能用
LLM-HPC++（2025）C++ async、平行演算法、coroutine、OpenMP、MPI+OpenMP新模型的 OpenMP 版本可勝過人寫的參考；但 coroutine 與 MPI 分散式版本，人寫的仍全面勝出；常見錯誤是忽略指定的執行緒數
ParEval-Repo（2025）整個 HPC 專案從 CUDA 轉到 OpenMP Offload／Kokkos除了最小的範例外，沒有任何模型與方法組合成功；主要失敗是 CMake／Makefile 等建置系統與跨檔案一致性
ParBench（2026）CUDA、OpenMP、OpenCL 之間的 kernel 轉換，加入語意不變的程式擾動轉換方向不對稱、多檔協調困難、目標 API 適配不完整；稍微改寫程式就讓表現不穩，顯示部分是記憶而非理解

結論：單一 kernel、常見平台（x86、CUDA、OpenMP）的正確性已經大幅進步；但效能、文件少的硬體、整個專案層級的平行化仍是弱項。模型升級本身不會自動解決這些。

四、能自動調校的條件：你搭好回饋迴路

效能能被自動改善的研究，共同點都是 agent 能自己編譯、驗證、量測、讀 profiler，再反覆修改。

Profiler 回饋要翻譯過

把原始硬體指標先轉成「該做什麼」的建議再給模型，加速比原始指標高 125%；原始指標不加解釋甚至可能有害。KernelBench 三個等級的幾何平均加速 2.42×、4.69×、5.30×。KernelPro 2026

專門訓練能贏過編譯器

用強化學習加上自動驗證與 profiling 的環境訓練，KernelBench Level-1、2 全部勝過 torch.compile，Level-3 為 92%，且比 Claude Opus 4.5、Gemini 3 Pro 高約 40%。CUDA Agent 2026

多 agent 分工抓違規

CPU 矩陣乘法轉 CUDA：單一 agent 達理論峰值 24.1% 且偷用被禁止的 cuBLAS；多 agent 分工達 43.1%，並由檢查角色攔下違規版本。VibeCodeHPC 2025
  • 並行 bug 修復也靠工具給的上下文：用靜態 happens-before 分析過濾出相關程式碼再交給模型，修復成功率從 62% 提升到 76%；非死結 bug 修好 29/33，死結只有 4/10。ConFixAgent 2026
  • agent 會鑽漏洞：沒有禁止規則時，會用函式庫取代自己寫、或讓評測失真（速覽中的 Sakana 事件）。VibeCodeHPC 2025Sakana 事件 2025

回答「能自動校正嗎」：能，但前提是你提供迴路。模型負責大量嘗試，你負責定義什麼叫對（參考答案、容許誤差）、什麼叫快（基準、量測方法、目標）、什麼不准做（禁用函式庫、不可改的介面）。這些是你的工作，也是效率的來源。

第四部分　具體做法

五、把研究結論變成你的工作流程

  1. 先做驗證，再叫 agent 寫：每個要平行化或最佳化的模組，先準備參考實作、測試資料與容許誤差。
  2. 寫一支量測腳本：固定輸入、跑多次取中位數、輸出加速比；agent 每次修改後自己執行。
  3. 把 profiler 輸出摘要化：用腳本把 Nsight／VTune 的關鍵指標轉成一句話的建議（例如「記憶體頻寬受限，考慮合併存取」），比直接貼原始數據有效。
  4. 寫明禁止事項：不可呼叫的函式庫、不可改的 API、執行緒數必須遵守參數；放進 CLAUDE.md 或 skill 最前面。
  5. 建置系統自己掌握：CMake／Makefile 是 agent 最常失敗的地方，先由你寫好，讓 agent 只改原始碼。
  6. 有真實硬體需求時才做 MCP：把 SDK 的擷取與量測包成少數幾個描述清楚的工具，讓 agent 能在機台上驗證。
  7. 定期看品質指標：靜態分析警告數、複雜度、測試覆蓋，避免短期變快、長期難維護。

AI 輔助軟體開發：知識點速覽

整理日期：2026 年 10 月 27 日 · 共 7 個主題、26 個知識點、17 篇參考文獻
一句話總結：AI 最容易出錯的地方，正是需要領域知識、講究效能、又沒有獨立驗證的地方。你的價值在於定義「什麼叫對」，並把它寫成自動檢查。

一AI 生產力的實證

  1. 「覺得變快」不等於「真的變快」：METR 2025 年的隨機對照試驗中，資深開發者用 AI 反而慢了 19%，卻自認快了 20%。METR 2025
  2. 2026 年的後續研究顯示工具可能真的讓人變快了，但因為很多開發者不願意不用 AI，樣本偏差太大，目前量不準。METR 2026
  3. 品質標準高、隱性要求多（文件、測試、格式）的專案，AI 的效益最有限。METR 2025
  4. 用 AI 學新東西時，整個交給它寫的人測驗分數低於 40%，只問觀念或要求解釋的人在 65% 以上；差距最大的是除錯能力。Anthropic 2026

二Harness 與介面設計

  1. 模型不變、只改 agent 操作電腦的介面，解題率可以差到約 1.6 倍。SWE-agent 2024
  2. 介面設計的四個原則：指令簡單、動作精簡、回饋有資訊但不冗長、用護欄防止錯誤擴散。SWE-agent 2024
  3. 資訊量有最佳點：檔案一次顯示 100 行最好，30 行或整個檔案都比較差。SWE-agent 2024
  4. Agent「成功得快、失敗得慢」：第一次編輯失敗後，最終成功率從 90.5% 掉到 57.2%。SWE-agent 2024

三測試與驗證

  1. AI 產生的測試要先通過確定型的篩選（能編譯、穩定通過、覆蓋率確實提升）才交給人審；候選測試只有 25% 真的提高了覆蓋率。Meta TestGen-LLM 2024
  2. 覆蓋率高不代表抓得到 bug。刻意植入特定類型的錯誤，再確認測試抓得到，是更強的檢驗。Meta ACH 2025
  3. 分工原則：AI 負責大量產生候選，確定型工具負責判斷能不能用，最後才由人審。TestGen-LLM 2024ACH 2025

四科學程式與 GPU

  1. 需要領域知識的科學研究程式，AI 表現明顯比一般程式差；2024 年最好的模型只解出 7.7%。SciCode 2024
  2. AI 寫的 GPU kernel 能追平 PyTorch 基準的不到 20%；加入執行結果和 profiler 回饋後會改善。KernelBench 2025
  3. AI 會鑽評測的漏洞（reward hacking）：Sakana 宣稱快約 100 倍，實測反而慢約 3 倍。TechCrunch 2025
  4. 驗證原則：參考答案要獨立於被測程式，測試資料要包含沒看過的輸入，效能要自己量兩次以上。KernelBench 2025Sakana 事件 2025

五C++ 與平行程式

  1. 離開 Python 後 AI 修 bug 的能力明顯下降，需要跨檔案修改時更差。Multi-SWE-bench 2025
  2. 平行程式的正確率大約只有循序程式的一半（約 76% 對 38%～40%）；FFT 和稀疏線性代數最難，OpenMP 最容易，MPI 最難。ParEval 2024
  3. 先給 AI 一份正確的參考實作再要求轉成平行版本，正確率會提高，但效能不會跟著變好。ParEval 2024
  4. AI 寫的 C 程式至少 62% 有漏洞，最常見的是緩衝區溢位、空指標和整數溢位。FormAI-v2 2024

六上下文與說明檔

  1. 關鍵資訊放在輸入的開頭或結尾效果最好，放在中間最差；輸入越長，整體表現越差。Lost in the Middle 2024
  2. 說明檔（AGENTS.md、CLAUDE.md）會讓成本增加超過 20%，對成功率沒有顯著幫助。Evaluating AGENTS.md 2026
  3. 說明檔只寫程式碼看不出來、又會悄悄出錯的規則；不要寫架構介紹，也不要讓 AI 自動產生。Evaluating AGENTS.md 2026

七資安

  1. 公開市集的 agent skill 有 26.1% 含漏洞，附帶腳本的風險是純文字型的 2.12 倍。Agent Skills in the Wild 2026
  2. AI 會捏造不存在的套件名稱（商用模型約 5%，開源模型約 22%），攻擊者可以搶先上架同名惡意套件。USENIX Sec 2025
  3. 2026 年的前沿模型幻覺率仍在 4.6%～6.1%，模型間差距縮小，但問題沒有消失。重現研究 2026（未經審查）
  4. 外來的 skill 要當第三方套件審查；陌生套件先上 PyPI 確認真的存在、有維護紀錄。Skills 2026套件幻覺 2025

Skill 與說明檔：研究整理（完整版）

整理日期：2026 年 10 月 27 日 · 13 篇參考文獻 · 合併先前「Skill與說明檔寫法_研究整理」並補充 skill 有效性研究

第一部分　Skill 的有效性

一、Skill 到底有沒有用：成對比較評測

SkillsBench（2026）

第一個專門衡量 skill 效果的評測，每個任務分別在「沒有 skill」、「人工整理的 skill」、「模型自己產生的 skill」下測試。SkillsBench 2026

  • 初版（84 個任務、7 種組合）：人工 skill 平均提高 16.2 個百分點，但軟體工程只提高 4.5、醫療提高 51.9；84 個任務中有 16 個變差。
  • 更新版（87 個任務、18 種組合）：平均通過率從 33.9% 提高到 50.5%，各組合提升 4.1 到 25.7 個百分點；仍有 13 個任務變差。更新版 2026
  • AI 自己產生的 skill 平均沒有幫助；只含 2 到 3 個模組的聚焦型 skill 優於完整文件；小模型加 skill 可追上沒有 skill 的大模型。

SWE-Skills-Bench（2026）：專測軟體工程

49 個公開的軟體工程 skill 搭配固定 commit 的真實 GitHub repo，約 565 個任務。SWE-Skills-Bench 2026

  • 49 個 skill 中有 39 個對通過率毫無提升，平均只提高 1.2%。
  • token 用量從小幅節省到增加 451% 都有，通過率卻不變。
  • 只有 7 個專門型 skill 有明顯效果（最多 +30%）；3 個反而變差（最多 −10%），原因是 skill 的指引版本與專案實況不符。

對你的意義：一般程式知識模型已經會了，skill 的價值在於補上它不會的領域流程（OCT 校正、QC 判讀），而且版本要跟著硬體 SDK 與函式庫更新。

二、Skill 為什麼會害事：失敗原因分析

從上述兩個評測中找出 307 個由 skill 造成的失敗（125 個功能失敗、182 個效率退化），逐一歸因。Agent Skills Can Be Harmful 2026

  • 害事的通常是「看似相關」的 skill：選錯 skill 只占功能失敗的 1.6%；占 68.8% 的是相關 skill 讓 agent 把任務要求做錯或漏做，常見情況是把 skill 裡的範例、預設值當成這次任務的規定。
  • 寫錯位置、改錯環境：19.2% 是把產出寫到 skill 習慣的路徑而非任務指定的路徑；10.4% 是 skill 讓 agent 改了套件或執行環境，與驗證環境不一致。
  • 效率變差的主因是「過度程序」，占 62.6%，其中最大來源是過度驗證與過重的實作流程。
  • 上下文膨脹幾乎都來自每次都會載入的 skill 本文（46 例中占 43 例），選用的參考檔很少造成問題。

論文的寫作建議：把「必須滿足的要求」和範例、預設值、範本、選用流程分開；常駐內容保持簡短，範例與長清單改成需要時才載入；驗證範圍依改動大小與風險調整，不要預設做完整驗證。

三、Skill 越多越好嗎

從一小組有用的 skill 擴充到 202 個 skill 時，表現最多下降 21%。原因主要是 agent 選錯 skill 的頻率隨函式庫變大而增加；上下文變長的影響小到與零無法區分。More Skills, Worse Agents? 2026

對你的意義：skill 少而精，每個 skill 的描述要能清楚區分「什麼時候該用我」。

四、Skill 要寫多長

刪掉廢話會變好

分析 55,315 個公開 skill：26.4% 沒有判斷何時使用的描述，內文超過 60% 不是可執行的指示。精簡後描述壓縮 48%、內文壓縮 39%，功能品質反而提升 2.8%。SkillReducer 2026

但不能壓過頭

從執行紀錄提煉 skill 時，壓縮比越高、效果改善越差，代表過度壓縮會丟掉可執行的細節。Evidence Over Plans 2026

結論：要刪的是背景說明和廢話，不是操作細節。

五、評估方法與綜述

  • SkillEval：只看 SKILL.md 文件本身的性質來評分，分數與實際任務的通過率提升高度相關，可在上線前提早判斷。SkillEval 2026
  • 綜述：整理 skill 的效用、產生、檢索與路由、安全稽核等各類評測，適合一次掌握全貌。Agent Skill Evaluation and Evolution 2026
第二部分　說明檔（CLAUDE.md、AGENTS.md）

六、說明檔怎麼寫：三類研究

1. 大家實際上怎麼寫

分析 1,925 個 repo、2,303 個說明檔：通常又長又難讀，結構一致（一個最上層標題、內容多在 H2 與 H3）；持續以小幅新增方式維護，像會演化的設定檔。Agent READMEs 2025內容集中在 build、測試、實作細節，效能與資安相對少見。Lulla 等 2026

2. 有沒有效（結果互相矛盾）

ETH Zurich（2026）

四種 coding agent：說明檔讓成本與步數增加超過 20%，成功率沒有顯著改變；AI 自動產生的說明檔略差。Evaluating AGENTS.md 2026

Lulla 等（2026）

Codex、10 個 repo、124 個 PR：執行時間中位數減少 28.64%、輸出 token 減少 16.58%，完成表現相當。樣本小、只測一種 agent，也未完整評估正確性。AGENTS.md Efficiency 2026

3. 規則寫太多會怎樣

最好的前沿模型在 500 條指令時只有 68% 的遵守率，且偏好較早出現的指令。IFScale 2025關鍵資訊放在開頭或結尾效果最好、放在中間最差。Lost in the Middle 2024

第三部分　寫法建議

七、綜合原則

  1. 人寫或人審：AI 自己產生的 skill 與說明檔效果最差。
  2. 描述寫清楚何時該用：選錯 skill 是函式庫變大後的主要瓶頸。
  3. 必要規則與範例分開：最常見的失敗是 agent 把範例當規定。
  4. 常駐內容要短，細節放參考檔：需要時才載入；刪廢話，不刪操作細節。
  5. 不要預設完整驗證：依改動大小與風險決定驗證範圍。
  6. 版本要吻合：函式庫或硬體 SDK 升級時，skill 跟著更新。
  7. 少而精：只保留經過成對比較、確實有效的 skill。
  8. 重要規則放最前面：說明檔只寫程式碼看不出來、又會悄悄出錯的規則。

Skill 與說明檔怎麼寫：研究整理

整理日期：2026 年 10 月 27 日 · 6 篇參考文獻
一句話總結：人寫、聚焦、少而準、重要的放前面。Skill 用來補模型不會的領域流程；說明檔只寫程式碼看不出來、又會悄悄出錯的規則。
關於時效：這個領域的研究不多，而且結果互相有出入。比較耐用的是「方法」（用獨立的參考答案驗證、確定型檢查優先、在自己的專案上做對照實驗），容易過時的是「數字」。數字請當作研究當時的快照。

一、Skill 怎麼用：SkillsBench（2026）

目前唯一專門衡量 skill 效果的評測：每個任務分別在「沒有 skill」、「人工整理的 skill」、「模型自己產生的 skill」三種條件下測試，共 7 種 agent 與模型組合、7,308 次執行。SkillsBench 2026

  • 人工整理的 skill 有效，但不是每次都有效：平均通過率提高 16.2 個百分點，但軟體工程只提高 4.5、醫療提高 51.9；84 個任務中有 16 個反而變差。
  • AI 自己寫的 skill 沒用：平均沒有幫助，模型無法可靠地寫出自己能受益的程序性知識。
  • 聚焦比完整好：只含 2 到 3 個模組的聚焦型 skill，優於完整的文件。
  • 小模型加 skill 可以追上大模型：搭配 skill 的小模型，能達到沒有 skill 的大模型的水準。

對你的意義

軟體工程只提高 4.5 個百分點，代表一般程式知識模型已經會了。Skill 的價值在於補上它不會的領域流程，例如 OCT 校正流程、QC 指標判讀這類廠內專有知識。

二、說明檔怎麼寫：三類研究

1. 大家實際上怎麼寫（描述性研究）

分析 1,925 個 repo、共 2,303 個說明檔（CLAUDE.md、AGENTS.md、copilot-instructions.md）：檔案通常又長又難讀，但結構一致，一個最上層標題、內容多放在 H2 與 H3 底下；會被持續維護，以小幅新增為主、很少刪減，比較像會演化的設定檔。Agent READMEs 2025

內容集中在 build、測試、實作細節等功能面，效能、資安這類非功能需求相對少見。Lulla 等 2026

注意：這類研究只說明大家怎麼寫，不代表這樣寫比較好。

2. 有沒有效（結果互相矛盾）

ETH Zurich（2026）

測四種 coding agent：說明檔讓成本與步數增加超過 20%，成功率沒有顯著改變；AI 自動產生的說明檔略差。Evaluating AGENTS.md 2026

Lulla 等（2026）

用 Codex 跑 10 個 repo、124 個 PR：有 AGENTS.md 時執行時間中位數減少 28.64%、輸出 token 減少 16.58%，完成表現相當。限制是樣本小、只測一種 agent，也沒有完整評估正確性。AGENTS.md Efficiency 2026

兩篇條件不同，結論也不同，目前沒有定論。比較保守的解讀是：說明檔可能幫 agent 少花時間摸索 repo 結構，但不保證結果更正確。

3. 規則寫太多會怎樣

測試 20 個前沿模型同時遵守大量指令的能力：最好的模型在 500 條指令時只有 68% 的遵守率，而且模型偏好較早出現的指令。IFScale 2025

這和長上下文研究的結論一致：關鍵資訊放在開頭或結尾效果最好，放在中間最差。Lost in the Middle 2024

三、寫法建議

CLAUDE.md 範例（以 OCT 專案為例）

# OCT Pipeline

## 會悄悄出錯的規則（最重要，放最前面）
- k 軸是遞減的，任何重取樣前先確認方向
- 共軛符號只對建表那一側成立
- GPU 運算必須關閉 TF32
- 校正檔不可跨機台使用；dark 必須和量測用同一組相機設定

## 驗證方式
- 改動 pipeline 後執行 `pytest tests/regression/`
- 驗收看底噪與假峰，不只看 FWHM

## 常用指令
- 建置：...
- 測試：...

刻意不寫：架構介紹、目錄說明、用了哪些套件。這些 agent 自己讀程式碼就知道，寫了只是增加成本與雜訊。

Skill 的寫法

  • 放「一套完整的領域流程」，例如「雙 COG 校正」或「QC 報告判讀」。
  • 每個 skill 只處理一件事，內容控制在 2 到 3 個主題。
  • 由熟悉流程的人撰寫或審過，不要讓 AI 自己產生。

最可靠的做法：在自己的專案上做小實驗

既然研究結論不一致，就用 SkillsBench 的實驗設計縮小到你的 repo：同一個任務，有說明檔或 skill 和沒有的情況各跑幾次，比較正確率與花費的時間，再決定留下哪些內容。
