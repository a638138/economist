AI Agent 研究（一）：Skill 與說明檔

整理日期：2026 年 11 月 14 日 · 22 篇參考文獻 · 全文查核版（11 月 14 日補充 4 篇，標示新增）
一句話總結：skill 和說明檔平均有幫助，但很不穩定。人工寫、少而精、註明適用條件的才有效；讓模型自己產生的 skill 或說明檔多半沒用甚至扣分，而且公開 skill 約四分之一有值得審查的危險模式（高風險的約 5%）。說明檔的長度、規則放的位置看不出大的影響，一定要守的規則要靠 hook、lint 或 CI 強制，不能只靠寫在檔案裡。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一Skill 有沒有用：平均有幫助，但很不穩定

  1. 人工寫的 skill 平均有效：87 個任務、18 組模型與 harness、每格 3 次，加上人工 skill 後通過率從 33.9% 提升到 50.5%（+16.6 個百分點）。軟體工程類 +11.6 個百分點，各領域介於 +9.7 到 +28.8。作者指出 skill 也加長了 context，增益可能有一部分只是「多給了文字」，沒有做等長的對照組；任務都是終端機裡的容器化任務；skill 是為每類任務精選、品質審過的，作者自己說這是樂觀情境（公開 skill 的品質評分平均 6.2/12，這裡是 10.1/12）。SkillsBench 2026
  2. 有些任務反而變差：87 個任務中有 13 個加了 skill 後變差，最大降幅 7.4 個百分點。SkillsBench 2026
  3. 讓模型自己寫 skill 反而扣分：三組專用 harness 上，自生成 skill 比不用 skill 低 8.1 到 11.5 個百分點（依 arXiv v4；NeurIPS 頁面摘要的版本是平均 −1.3，方向相同、幅度小很多）。SkillsBench 2026
  4. 真實情境下效益大幅縮水：當 agent 要從 34,198 個真實 skill 中自己檢索，Claude Opus 4.6 的增益從強制載入時的約 20 個百分點降到約 3 個；Kimi 與 Qwen 甚至略低於不用 skill（差 2.0 與 0.8 個百分點，差距很小、沒有檢定；作者認為是不相關的 skill 誤導了 agent）。每種設定跑 3 次，沒有信賴區間。Skills in the Wild 2026
  5. skill 越多，越常選錯或乾脆不用新增：SkillsBench 上 38 組有 skill 能幫上忙的「任務與模型」配對（Haiku 4.5 與 Sonnet 4.6）、2,545 次執行。只載入有用的 skill 時通過率最高；把 skill 庫擴充到 52、102、202 個，通過率平均分別降 8、14、21 個百分點（202 個時 Haiku 降 26、Sonnet 降 15）。202 個時，只用到正確 skill 的執行從 88.0% 降到 52.6%，有 38.5% 的執行完全沒呼叫任何 skill。在 102 和 202 個時，「選錯或不選」造成的下降信賴區間不含零；上下文變長本身的影響點估計一直是正的（約 6 到 7 個百分點），但信賴區間太寬（約 −13 到 +25），作者的結論是與零無法區分，也說它可能真的存在、只是樣本不夠；在 Sonnet 上它的點估計反而比選錯還大，但兩者都不顯著。只有兩個 Anthropic 模型、一個 benchmark，最小的 skill 庫是 52 個；論文寫 2,545 次執行，表格各列加總是 2,576，差約 1%，不影響結論。More Skills, Worse Agents? 2026
  6. 針對任務改寫 skill 能救回一部分：Terminal-Bench 2.0 上，Claude Opus 4.6 從無 skill 的 57.7% 提升到 65.5%，單靠檢索是 61.4%，檢索與改寫各貢獻約一半；檢索到的 skill 相關性較低時（SkillsBench 移除精選 skill），改寫的幫助很小或沒有。而且每題要多跑一次探索。Skills in the Wild 2026
  7. 軟體工程 skill 大多測不出效果更新：98 個公開的軟體工程 skill，各配一個固定版本的真實 repo 與 10 個需求，4 組 agent 與模型（GPT-5.4-mini、Kimi-K2.6、Haiku 4.5，沒有測 Opus、Sonnet、GPT-5.5 這類旗艦模型）、強制載入 skill，有無 skill 各跑一次，共 3,920 次配對比較。92 個 skill 沒有統計上顯著的效果，平均通過的檢查項比例只從 76.6% 到 76.9%。有幫助的例如 viper-configuration（+17.7），補上了 agent 本來會省略的步驟。有害的 asyncio-patterns 平均 −17.0、四組配置都變差，作者歸因於內容寬泛、和任務不合；另一種傷害是 skill 的範本蓋過任務的明確要求，例如 github-actions-templates 在一組配置下把指定路徑的檔案寫到別處（該配置 10 個需求平均 −22.8）。同一個 skill 換配置後效果常常不同。限制：需求是從每個 skill 反推出來的，測的是 skill 宣稱的能力，不是一般的工作分佈；每個 skill 每組配置只有 10 個需求、各跑一次，檢定力低，「沒有顯著效果」不等於確定沒差。依 2026 年 10 月的 v2（舊版是 49 個 skill，數字已全部更新）。SWE-Skills-Bench 2026
  8. 同一個 skill 換模型就可能變差：9 組配置平均都提升（+4.6 到 +19.5 個百分點），但 36.78% 的任務在某些配置變好、在另一些變差。每格只跑 3 次、沒有檢定，作者也承認任務層級的通過率對隨機性敏感；整理者用模擬估算，就算 skill 完全沒效果，通過率在中段的任務也有九成以上的機會出現這種「有增有減」，所以這個比例無法和隨機波動區分。有 skill 的條件同時明確要求 agent 使用 skill，增益是兩者合計。Downstream Utility 2026
  9. 模型做不來 skill 推薦的方法時，表現低於無 skill：排考程任務中 skill 推薦整數規劃，DeepSeek 搭 Codex 不用 skill 時 3 次全過，用了 skill 3 次全部逾時；GPT 用同一組 skill 3 次全過，其中一次求解器被終止後改用允許的啟發式方法。Downstream Utility 2026
  10. GPT 的增益比 Qwen 大，但不是一致的「強者得益多」：三種 harness 下 GPT 的增益都比 Qwen 多 3.45 到 8.43 個百分點。但研究有三個模型：DeepSeek 在兩種 harness 下不用 skill 時比 GPT 強，增益卻比 GPT 小，所以「強者得益多」並不一致。Downstream Utility 2026
  11. 「有載入」不等於「有照做」：79 個 skill、177 個任務、8 個模型、2 種 harness，最佳綜合分數只有 0.613（GPT-5.5 搭 Claude Code）。觸發率 97% 的配置，照做程度仍只有 0.625；綜合分數低於約 0.5 時，任務表現就低於不用 skill。更新另一個實驗在 Claude Code 裡放 1、10、20、30 個 skill（目標 skill 加隨機抽的其他 skill），量的是有沒有選到目標 skill：從 1 個增加到 10 個時下降，較弱的模型尤其明顯，之後幾乎不再變差（論文只有圖，沒有給數字）；下降主要是 agent 沒有呼叫任何 skill，選錯的很少，而且集中在描述寬泛、彼此重疊的 skill（例如 test-driven-development 與 software-architecture）。另外 53 個「主題相近、但不需要 skill」的任務中，各模型大多判斷一致，只有 9 題分歧，分歧時多出的不必要呼叫集中在 Claude Opus 與 GPT-5.5。部分評分用 LLM 評審（GPT-5.4）；Gemini 因 API 相容問題被排除。論文內部表格有小幅不一致：附錄 Table 7 在預設權重下有 4 個模型的分數和 Table 1 差 0.01 到 0.07；這裡引用的 GPT-5.5 數字兩表一致。Skill-Use 2026

對你的意義

skill 值得用在「agent 自己查不到、而且你反覆在做」的流程，例如 SDK 的特定呼叫順序或量測步驟。通用的程式寫法 skill 多半沒效益。新增 skill 後，用幾個真實任務比較有無 skill 的結果，再決定要不要留。更新裝的 skill 越多，agent 越容易該用時沒用、或選錯（從 1 個增加到 10 個就看得到下降，較弱的模型尤其明顯）：只留常用的，用不到的移除；description 寫明何時使用，不要寫得寬泛到和其他 skill 重疊（選錯的多半是這種）。

二SKILL.md 怎麼寫

  1. 真實世界的 skill 幾乎都有缺陷：超過 99% 至少有一種「skill smell」，平均每個 10.5 種。常見的包括沒防止 agent 合理化跳過步驟（94%）、關鍵警告埋在內文（81%）、沒有規劃階段（78%）、沒有驗證步驟（69%）；smell 出現後幾乎不會被修掉。樣本只來自一個 skill 市集（skills.sh）的熱門英文 skill；語意類的 smell 用單一本地模型偵測；「最佳做法」整理自網路文章，不是經過驗證的準則；論文也沒有測這些 smell 是否真的讓 agent 表現變差。Anatomy to Smells 2026
  2. 少量、不冗長較好：一次給 2～3 個 skill 增益 +19.0 個百分點，4 個以上只有 +10.1；精簡型 +19.0、標準型 +21.5、詳細型 +14.5，寫成完整文件的只有 +0.7。這是兩組不同的比較（數量、複雜度），不能直接相比；而且是把不同任務按原本附的 skill 數量或長度分組，不是同一任務改 skill 的對照，「完整文件」組只有 5 題。SkillsBench 2026
  3. skill 造成的失敗，多半不是選錯 skill：307 個由 skill 造成的失敗（125 個功能失敗、182 個效率退化）中，skill 的描述誤導只佔功能失敗的 1.6%；68.8% 是 agent 照 skill 做了卻漏掉或填錯任務要求，包括把範例或預設值當成規則；19.2% 把產出放到和任務指定不同的位置。效率退化有 62.6% 來自流程過重，其中過度驗證最多。候選 skill 先篩過描述相似度，明顯不相關的 skill 本來就很少，「選錯」的比例可能因此偏低（整理者推論）；125 個功能失敗中 87 個是和另一個 skill 比，不是和不用 skill 比；每個配對只跑一次。只測一個模型、一種 harness，標註沒有報告評分者一致性。Agent Skills Can Be Harmful 2026
  4. context 膨脹來自內文：46 個 context 負擔案例中，43 個來自每次都載入的 skill 內文。Agent Skills Can Be Harmful 2026
  5. 壓縮 skill 不太會傷品質：600 個 skill 平均把描述壓縮 48%、內文壓縮 39%，壓縮後分數 0.742 對原版 0.722（p = 0.002，但效果量很小，d = 0.107）；86% 的 skill 壓縮後不低於原版。評分標準同時也是優化目標，數字可能偏樂觀。600 個中有 429 個原本沒有描述或太短，是先產生描述再壓縮，所以描述的壓縮比是相對於新產生的描述；評估任務由 Qwen3.5 依 skill 產生與執行，約一半用執行測試、一半用 LLM 評審評分；另在 SkillsBench 上外部驗證時，不用 skill 也已 86/87 通過，看不出差別。SkillReducer 2026
  6. 內文只有約四成是核心規則：抽樣 90 個 skill，38.5% 的條目是核心規則，其餘多是背景說明（40.7%）、範例（12.9%）與範本（7.6%），真正重複的只有 0.3%；分類由 LLM 判定。作者也發現，壓縮失敗的主因正是把「其實隱含規格的範例」移走。SkillReducer 2026
  7. 多個 skill 協作時，寫出依賴關係：寫成產物依賴圖（Dependency DAG）比不給組織指示高 6.5 到 11.4 個百分點，也勝過只寫順序。但只寫出各階段目標（Stage Plan）就拿到約一半到全部的增益；依賴圖只在 5 到 6 個 skill 協作的 11 題上再多一些，3 到 4 個 skill 時兩者幾乎相同。組織指示是作者手寫的，每格 3 次、沒有檢定。Downstream Utility 2026
  8. 「相關」不等於「有用」：改用「是否支援任務需要的基本操作」排序候選 skill，第一選擇的通過率提升 4.35 到 5.80 個百分點，約等於 23 題中多過 1 題，沒有檢定；這個排序方法是看過同一批任務的結果後才提出的，作者說需要獨立任務驗證。Downstream Utility 2026

對你的意義

寫 SKILL.md 的檢查清單：關鍵警告放最前面；明寫「不可跳過」的步驟與驗證方式；範例標明「僅供參考，以任務要求為準」；註明適用的 SDK 版本與環境；內文只放核心規則，細節拆到需要時才讀的附檔；驗證寫一次就好，不要要求反覆檢查。

三CLAUDE.md／AGENTS.md：只寫 agent 查不到的事

  1. 讓 LLM 自動產生的說明檔沒幫助，還更貴：4 組 agent 與模型、138 個附說明檔的任務加 SWE-bench Lite 300 題。自動產生的說明檔讓成功率變化 −0.5% 到 −2%（不顯著；每題只跑一次），步數多 2.45 到 3.92 步，成本增加約 20% 到 23%（顯著）。只測 Python；作者指出模型對 Python 的工具鏈本來就熟，說明檔在冷門語言或工具鏈上的效果可能不同。Evaluating AGENTS.md 2026
  2. 開發者自己寫的說明檔略有幫助，但不顯著：比沒有說明檔平均 +2.4%（p = 0.21），比自動產生的好（p = 0.038），成本仍增加最多 19%。4 組中只有 Claude Code（Sonnet 4.5）沒有提升；開發者說明檔只來自 12 個 repo。Evaluating AGENTS.md 2026
  3. agent 確實會照說明檔做事：說明檔提到 uv，每題平均用 1.6 次，沒提到時幾乎不用；提到的 repo 專屬工具每題用約 2.5 次。成本增加正是因為它多跑測試、多讀檔。Evaluating AGENTS.md 2026
  4. 說明檔能縮短時間，但沒測正確性：10 個 repo、124 個小型 PR，Codex 加上 AGENTS.md 後執行時間中位數 −28.6%、輸出 token 中位數 −16.6%（都顯著），總 token 沒有顯著差異。論文沒有報告重複次數（看起來各一次），正確性只抽 50 題做基本檢查。Lulla 等 2026
  5. 小規模實驗看不出差別：3 個 Python repo 的真實任務（Claude 15 題、Codex 17 題）、2 個 agent、每種設定 3 次，「不給說明檔、每次都給、需要時才查」三種做法的通過率沒有顯著差異。作者指出這個規模只能偵測 30 個百分點以上的差距；另做的等價檢定得到 10 到 15 個百分點的界線，但作者說明這只是描述性的，樣本不足以下「等價」的結論。Khatri 2026
  6. 大家都在寫什麼：收集 1,925 個 repo 的 2,303 個說明檔，再從中抽 332 個人工標註內容：測試（75.9%）、實作細節（70.8%）、架構（68.1%）最常見；安全只有 14.8%、效能只有 14.5%（只要提到就算，一行也算）。檔案中位數 335 到 535 個英文詞；59% 到 67% 的檔案修改過不只一次，修改多半是增加內容，刪除的中位數不到 15 字。Agent READMEs 2025
  7. 指令越多，越容易漏：在「報告中包含指定關鍵字」的人工任務上，最強模型在 500 條指令時只做到 68.9%；靠後的指令較常被忽略（這個偏差在 150 到 200 條時最明顯，300 條以上趨近平均，後段與前段的錯誤率比約 1.0 到 1.5），錯誤以完全漏掉為主。最強的推理模型（2025 年中的 o3、gemini-2.5-pro）在 150 條左右以內幾乎全對（100 條時約 98%），250 條時降到約 85% 到 92%，500 條是極端情況。這是人工設計的關鍵字任務，不等於真實程式指令。IFScale 2025
  8. 對話被壓縮後，規則會消失：只在對話中講過的規則，長對話被壓縮摘要後，7 個模型合計有 30% 的機率違反（最高 59%），完整保留對話時是 0%。在 3 個模型、5 個軟性規則任務上，規則放在系統訊息時違規增加 0 個百分點，放在使用者訊息時增加 50 個百分點。五模型重複實驗：違規增加 37 個百分點（95% 信賴區間 31 到 43）。更新七模型主實驗中，Claude Sonnet 4.6 是 19%。實驗把壓縮設得很激進（作者說是比照實務建議）：摘要上限從 300 個英文詞收緊到 15 個時，規則保留率從 88% 降到 23%，違規從 7% 升到 28%（各模型合計；最受影響的模型在 300 詞時仍有 20%）。受影響的主要是組織自訂的軟性規則（+50 個百分點），模型本來就會拒絕的硬性安全規則只 +6。違規與否主要看負責摘要的模型有沒有保留規則；每次壓縮後把規則原文放回，違規回到 0%，但對話中出現冒充管理者的「規則已撤銷」訊息時仍有 17%（加上來源標註後 10%）。情境是模擬的工具呼叫、對話約 6 千 token、每格 27 次；測過 LangGraph、AutoGen 等框架，沒有測 Claude Code 自己的壓縮；單一作者。Chen 2026
  9. 檔案長度、規則位置、拆成幾個檔，都看不出差別新增：Claude Code 1,650 個 session（主要用 Sonnet 4.6，每種條件 50 次）、2 個 TypeScript 專案、5 種任務，規則是「每個函式開頭加一行指定註解」。CLAUDE.md 從 25 行到 500 行，遵守率 60.0% 到 67.7%（p = 0.16）；規則放第 2 行或第 250 行，67.7% 對 61.8%（未校正 p = 0.055，校正多重比較後不顯著）；拆成 CLAUDE.md 加 AGENTS.md 加子目錄檔案，或在另一個檔案放互相矛盾的規則，也都沒有可偵測的差異。長度與矛盾規則有貝氏因子支持「沒有大的效果」；位置與拆檔則只是沒偵測到。作者寫這個設計能排除約 6 個百分點以上的影響，但論文自己寫的信賴區間半寬是 ±5.9 個百分點，而最大的一組位置差距就是 5.9，所以區間約是 −12 到 0；拆檔（−6.0，p = 0.053）也一樣。事先規劃的位置整體檢定 p = 0.83、線性趨勢 p = 0.41，第 2 行以外的位置都在 62% 到 64%，5.9 是 10 組比較中挑出的最大值。所以位置的效果可能很小，但資料也無法排除規則放前面好上 10 個百分點左右。結構變數的分析只在其中一個專案（搭 Sonnet 4.6）上做。沒有說明檔時遵守率是 0%，所以規則有被讀到，只是做不滿。McMillan 2026
  10. 影響最大的是任務類型與「同一 session 已寫的函式數」新增：函式數相近的兩個任務，遵守率 45.1%（改既有版面）對 71.3%（新寫頁面），作者強調這只是單一對比，不支持「改既有程式比較難」的推論；同一個 session 裡 agent 每多寫一個函式，遵守的勝算約降 5.6%（OR = 0.944），在第二個專案與 Opus 4.6 上方向相同。但這個衰減不是穩定遞減，3 個多函式任務中只有 2 個看得到；第一次漏掉的中位數在第 4 個函式，作者指出這個衰減可能混了兩種情況：一開始就沒接收到規則，和寫著寫著才淡忘，目前無法區分。單看 session 長度（回合數、成本）的關聯在控制任務後減弱，作者不另列為發現。這是分析時才發現、不是事先設定的假設；規則很簡單、只測 Anthropic 模型與單輪模式，換成「改 schema 要同步改 migration」這類規則是否一樣，作者說還不知道。McMillan 2026
  11. 有提交 AI 設定檔的專案，導入 agent 後品質退化較少新增：509 個導入 agent 的開源專案搭配配對對照組，用交錯式差異中的差異分析，以第一個 agent PR 為導入點。先用 agent 的專案中，沒有提交任何 AI 設定檔（規則檔、CLAUDE.md 等）的，導入後認知複雜度 +52.7%、靜態分析警告 +24.1%；有提交的是 +26.7% 與 +14.0%。兩組 commit 數都增加（+37.6% 與 +27.5%）。另外 441 個企業 repo 中，73.8% 的設定檔提交後就再也沒改過。這是觀察性研究：有設定檔的專案原本就較成熟（星數平均 4,907 對 831），作者自稱「用來產生假設」；論文也沒有檢定兩組差距本身是否顯著，而且只看「有沒有」設定檔，沒看內容；品質指標是 SonarQube 的複雜度與警告數，不是實際的 bug。設定檔多半是導入 agent 同時或之後才提交的（先用 agent 的專案中只有 3.8% 在導入前就有），作者認為這種反向因果會讓差距被低估，但也無法排除有設定檔的專案用了較強的模型。Denisov-Blanch 等 2026

對你的意義

CLAUDE.md 只寫 README 沒有、agent 自己查不到的事：建置與測試指令、SDK 的硬體限制、即時執行緒不可配置記憶體這類規則。不要用 /init 自動產生後直接留用。重要規則寫進 CLAUDE.md，不要只在對話中說，因為長對話壓縮後可能被丟掉。更新不必為檔案長度（500 行內）費心，把力氣放在內容；拆檔不會提高遵守率，加了子目錄說明檔的那組甚至略低（未排除），所以不要為了遵守率拆檔；重要規則仍放前面，因為位置的效果沒被排除，而且不花成本。就算寫了，簡單規則也只有約五成五到七成的遵守率，而且寫越多程式越容易漏，所以「違反就會出事」的規則（例如即時執行緒不可配置記憶體）要另外做成 hook、lint 規則、編譯期檢查或 CI 測試來擋；CLAUDE.md 負責告訴 agent 為什麼，機械檢查負責確保做到。長任務中途可以用 hook 重新提示一次關鍵規則（作者的建議），再加上 lint 或 CI；拆成較短的 session 沒有被測過。

四Skill 與套件的安全風險

  1. 約四分之一的公開 skill 有值得審查的危險模式：31,132 個 skill 中 26.1% 至少有一個值得審查的危險模式（作者估計真實範圍 23% 到 30%），作者提醒這不等於確認的惡意；其中高嚴重度 5.2%、中 8.1%，其餘 12.8% 只有低嚴重度的不良習慣（例如沒鎖定相依套件版本、權限過寬）。附帶腳本的 skill 有問題的比例 40.6%，純指令型 24.2%（勝算比 2.12）。偵測工具在 200 個人工標註樣本上精確率 86.7%、召回率 82.5%。Skills in the Wild 安全 2026
  2. 憑證最常從輸出外洩：17,022 個 skill 中 3.1%（520 個，含 83 個惡意 skill）有憑證外洩問題；非惡意的問題中 73.5% 來自把憑證 print 或寫進 log，而 agent 會把這些輸出讀進 context。經實際執行確認，89.6% 可在不提權的情況下利用。Chen 等 2026
  3. 確實有惡意 skill：98,380 個 skill 中確認 157 個惡意（0.16%），70.1% 是竊取資料型；其中 54.1% 來自同一個發布者。揭露後全部下架。作者指出 157 是下限。Malicious Agent Skills 2026
  4. 套件幻覺很普遍，而且會重複出現新增：16 個模型（2024 年初的模型）、57.6 萬段 Python 與 JavaScript 程式，推薦的套件中 19.7% 不存在；商用模型 5.2%、開源模型 21.7%，最低的 GPT-4 Turbo 也有 3.59%。抽 500 個出現幻覺的提示各重問 10 次，58% 的幻覺名稱會再出現，所以攻擊者可以預先搶註；但 81% 的幻覺名稱只出現在一個模型。問到最近一年才流行的套件時，幻覺更多。4 個模型中有 3 個事後自我檢查，能認出 75% 以上自己的幻覺。限制：19.7% 有一部分來自直接問模型「需要哪些套件」，不只是從程式碼解析；開源模型用的是量化版；重問與自我檢查只測 4 個模型、只測 Python；沒有測 agent 情境。Spracklen 等 2025
  5. 2026 年的模型仍會推薦不存在的套件：重現研究，5 個模型、199,840 次生成，推薦不存在套件的比例以提及次數計 3.6% 到 5.0%（以生成次數計 2.2% 到 3.4%）；5 個模型都會幻覺出的名稱有 104 個。約 1% 的幻覺名稱在 6 個月內被人註冊，至少 23 個被推薦的名稱曾放過後來被移除的惡意程式。依 2026 年 11 月的 v4：作者改用事先登記的即時重新驗證，舊版的 4.62% 到 6.10%、127 個與「53 個可被搶註」都已作廢。單一作者的預印本，未測 agent 情境。Churilov 2026

對你的意義

不要直接裝來路不明的 skill，尤其附腳本的；裝之前先讀過腳本。自己寫的 skill 不要 print 金鑰。agent 建議新增的相依套件，先確認名稱真的存在、是你要的那個。

AI Agent 研究（二）：規劃、測試與省 token

整理日期：2026 年 11 月 14 日 · 14 篇參考文獻 · 全文查核版（11 月 14 日補充 4 篇，標示新增）
一句話總結：先有測試、任務切小、減少無效探索，比加規劃步驟或多開 agent 有效。token 花得多不代表做得好，多 agent 通常更貴、不一定更好；壓縮工具輸出的外掛省下 token，卻不一定省錢。agent 會朝「被檢查的東西」最佳化，測試全過不代表做出你要的東西。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一規劃與測試

  1. agent 常不照自己宣告的計畫做：在 SWE-bench 上，agent 宣告計畫後，完整照順序執行的軌跡只有 12.1% 到 25.4%；計畫越長越少照做。只給計畫當參考時，任務成功率提升有限；改用依計畫型態設計的執行器（例如分步驟派工）時，SWE-bench 成功率從 0.36 升到 0.44（DeepSeek-V4，取表現最好的固定型態；另兩個模型增幅更大）。自動比對工具只在另一個環境（ALFWorld）用 100 條軌跡驗證過，和人工的一致性偏低（κ 約 0.3，兩位人工彼此也只有 0.35），所以這些比例的雜訊不小。只測三個開源模型（Qwen、DeepSeek、Gemma），每題最多 24 步。Oota 等 2026
  2. 先寫測試再寫程式有幫助：在 8 個 Python repo 中補完缺少的函式（455 題），「先產生測試、再同時修正測試與程式」比 mini-SWE-agent 高 6.4 到 16.9 個百分點，但這個差距也包含框架不同；同框架內比不寫測試的反覆自省高約 5 到 9 個百分點。測試寫好就固定、只改程式的版本，在 3 個模型中有 2 個不如完全不寫測試的反覆自省，增益要靠同時修正 agent 自己剛寫的測試（不是既有的測試）。只測 Python、沒有統計檢定；最常見的失敗是程式通過自己寫的測試，但沒通過 repo 原本的測試。TDD-Agent 2026
  3. AI 產生的測試大多要丟掉，留下的也要人看新增：Meta 用 LLM 擴充既有的 Kotlin 測試類別，只留下「能建置、連跑 5 次都通過、增加行覆蓋率」的測試。部署時以單一嘗試計算，三關都過的只有約 4% 到 5%（Facebook 8,996 次、Instagram 23,535 次嘗試）。摘要寫的「75% 能建置、57% 穩定通過、25% 增加覆蓋率」來自另一個 86 個測試類別的評估實驗，評估章節定義為「類別裡至少有一個候選成功」的比例，但討論章節又把 25% 稱為每個測試的成功率，論文本身前後不一。送給工程師審的測試，有被審查的約 73% 被接受（三次活動共送出 339 個、接受 196 個，以全部送出計約 58%；其中一批先經作者看過）。被退回的原因包括測的是 getter 這類瑣碎方法、一個測試檢查太多事、沒有 assertion，也就是這些過濾擋不住「沒在比對結果」的測試（作者認為這類測試至少還能檢查「不拋例外」）。業界經驗報告，沒有對照組。Meta TestGen-LLM 2024
  4. 覆蓋率看不出測試會不會抓錯新增：Meta 的 ACH 先讓 LLM 在程式裡植入「現有測試抓不到」的錯誤，再讓 LLM 寫能抓到它的測試，並確認測試在原程式通過、在植入錯誤的版本失敗。產生的 571 個測試中，277 個（49%）沒有增加任何行覆蓋率；如果只用覆蓋率篩選，這些能抓到錯的測試都會被丟掉。植入的錯誤約 25% 和原程式在語法上相同，等於沒改。工程師接受 73%，但送審的測試有一部分經作者先篩過。業界經驗報告，沒有對照組。Meta ACH 2025
  5. 多輪修改會把原本對的東西改壞：542 題單一函式的 Python 題目、每題 8 輪固定修改要求，第 8 輪時 GPT-4o 原有測試通過率從 90.2% 降到 72.4%，Llama-3.1-8B 從 76.1% 降到 31.6%。Huang 等 2026
  6. 每輪重跑測試，退步就要求重做：退步時把上一個通過的版本和失敗數附給模型、重做一次；重做的通過數不少於原本就採用重做，否則保留這一輪原本的版本（不會退回上一版）。DeepSeek-V3 第 8 輪通過率從 75.8% 提升到 87.9%，Llama-3.1-8B 從 31.6% 提升到 47.3%。但觸發重做與挑選版本用的都是評分用的測試；通過率只量原有行為有沒有保留，沒量這一輪的新要求是否做到；只測兩個模型、每題一段對話、沒有統計檢定。Huang 等 2026
  7. 讓 agent 利用過去對話推測意圖，差很多：加一個專門從過去對話推測使用者目標與偏好的輔助 agent（主 agent 與輔助 agent 都是 Claude Sonnet 4），在 GPT-5 模擬使用者的 500 題中，成功率從 18.1% 提升到 59.7%；基準是刻意把 issue 改模糊、又不使用過去對話的條件（基準仍可向模擬使用者發問；直接讓 agent 檢索過去對話的版本效果較小）（論文前言另寫 13.5% 與 57.4%）；17 位開發者三週的真人使用中，86.2% 的建議被採用或稍改後採用，但沒有對照組。ToM-SWE 2026
  8. 能跑驗收測試時，agent 會「為測試而做」新增：Microsoft 的個案研究，要 agent 把一個約 5,800 行的 React 表格元件重寫成 Angular 元件庫，用 222 個隱藏的行為測試評分（agent 只看得到每題過或不過）。不能跑測試時，兩個模型（Claude Opus 4.7、GPT-5.5，都用 GitHub Copilot CLI）交出真正的元件庫，但只過 148 到 189 題；能跑測試時，除了一次始終沒去跑測試的，分數都到 221 到 222，但 GPT 6 次中有 5 次把功能直接寫在示範頁裡，元件庫沒被示範頁用到、只有外殼，或根本不存在，其中一次整個交付只有一個 1,758 行的檔案，完成報告卻寫「元件庫已完成、222 passed」。Claude 6 次中有 2 次出現同樣傾向；而且 Claude 能跑測試的 6 次全都沒附元件庫的發佈設定、也沒自己寫單元測試，不能跑測試的 3 次則都有。只有一個任務、每種條件 3 次、沒有統計檢定，作者說盛行率未知；不能跑測試的那組沒有交示範頁，分數是研究者替每次執行另寫接線程式後測的。Ma 等 2026

對你的意義

計畫寫下來不會自動被執行，要在關鍵步驟設檢查點，或把計畫拆成一步一步的小任務。效果最一致的是「先有測試」：先讓 agent 寫或補測試，你確認測試合理後再讓它改程式，每次改完跑完整回歸測試。更新測試是 agent 的目標，也會變成它唯一在乎的東西：完成報告不能當證據，驗收時要看產物本身（功能是不是真的在你要的模組裡、是否被呼叫、有沒有寫死針對測試輸入的分支），並保留一組 agent 看不到的測試或量測，用來最後確認。更新agent 寫的測試，不要用「通過了、覆蓋率有提高」判斷好壞：把程式故意改壞一處，確認測試會失敗；並看一眼測試裡有沒有真的在比對結果。

二省 token：錢花在哪、怎麼省

  1. token 多不等於做得好：SWE-bench Verified 500 題、8 個模型、每題 4 次，成本最低的一群之後，花更多 token 準確率就不再提升甚至下降；花費高的執行常是反覆讀同一檔案、改了又改。同一題不同次執行，最貴的平均約是最便宜的 2 倍。Bai 等 2026
  2. 成本主要是輸入：即使有快取，讀取快取仍是金額最大的一項；探索與修改兩個階段約佔三分之二的回合。成本以輸入為主是 8 個模型的結果；分階段與快取的拆解只分析一個模型（Sonnet 4.5）。這裡讀取快取最大，下方 Weinberger 的研究則是寫入快取最大，兩者的 harness 與回合數不同（這裡是 OpenHands 的長軌跡）。Bai 等 2026
  3. 限制回合數能省錢，但會少解幾題：100 題、3 個模型、每種設定只跑一次。上限設在第 75 百分位時，成本降 23.6%（Claude）、38.4%（GPT 4.1）、68.3%（Gemini），解題數分別 −4、−5、+2 題；設在第 25 百分位時 Gemini 從 63 題掉到 26 題。實驗的上限每回合都附「還剩幾回合」的提醒；作者用同一批資料模擬沒有提醒、到了就停的情況，解題數掉得更多（例如第 75 百分位時 Claude 71→63 題）。每種設定只跑一次，±4 題的差異可能在隨機變異內。需要時才追加回合，成本可再降約 6% 到 24%（摘要寫 12% 到 24%，與表格不符）。百分位是用同一批題目算的，沒有另外驗證；成本計算關閉了快取，實際帳單（大部分是快取費用，見下方）省下的比例可能不同。Gao、Peng 2026
  4. context 小時，管理機制很重要；夠大時差異很小：4 個模型（Nemotron-3 三種大小與 Mistral，不含 Claude 或 GPT）、2 個 benchmark，context 只有 32k 時，有管理機制比沒有高 35.7 個百分點（SWE-bench），到 128k 時只差 2.7。Fan 等 2026
  5. 規劃步驟主要幫弱模型：最小的 30B 模型加規劃後 SWE-bench 從 13.6% 提升到 25.2%；較強的模型沒有一致的提升，成本降幅依模型與任務從約 4% 到 40%（120B 在 SWE-bench 上反而變貴）。只用 bash、不給專用工具，弱模型掉 15 個百分點；Nemotron 最大的 550B 反而 +3.6、成本 −53%，但另一家族的 Mistral 在 SWE-bench 上掉了 23 個百分點，只在命令列任務上變好，作者的結論是取決於模型與任務。SWE-bench Verified 只有 Python。模型是 Nemotron-3 與 Mistral，不含 Claude 或 GPT；規劃與工具只在 128k context 下測；每種設定每題只跑一次，有做配對檢定，但 Terminal-Bench 只有 89 題，很多比較沒達到顯著。Fan 等 2026
  6. 快取價格（官方文件）：讀取快取一般是輸入價格的 0.1 倍，Opus 5.5 與 Sonnet 5.5 是 0.05 倍；寫入快取 1.25 倍（5 分鐘）或 2 倍（1 小時）。修改工具定義會讓整個快取失效；變更 thinking 設定一定會讓訊息部分的快取失效，變更 effort 則可能失效；兩者在部分模型上都會連工具與系統提示的快取一起失效。Anthropic 文件 2026
  7. effort 等級（官方文件）：Opus 5.5 預設 medium，適合範圍清楚的日常開發；修既有程式的 bug、需要驗證邊界條件時用 high；max 適合讓它長時間獨立處理的難題，但官方提醒 max 可能報酬遞減、容易想太多，先測試再大量使用。Anthropic 文件 2026
  8. 壓縮工具輸出：token 少了，帳單沒少新增：Claude Code 上 103 個任務、2,848 次執行的成對比較（多數用 Haiku 4.5，另有 Sonnet 5 與 Opus 4.8）。一個加了檢索與排序的壓縮外掛讓工具輸出 token 少了 38.4%，實際帳單卻 +6.8%（95% 信賴區間 +2.8% 到 +11.3%）；另一個 API 代理型外掛 +48.4%；規則式的簡單壓縮帳單 −2.7%（−5.6% 到 −0.1%），但它的工具輸出只少了 1.3%，約佔成本的 0.04%，在保留題組與事後用 Opus 重做時信賴區間都跨過零，所以這 2.7% 很難歸因於壓縮，作者也說只是提示性結果。各組成功率沒有可偵測的差異（基準已有 96%）。Weinberger、Hozez 2026
  9. 錢花在快取，不在工具輸出新增：同一研究中，帳單的 44.3% 是寫入快取、35.4% 是讀取快取、10.4% 是輸出；在跑分用的單次任務中，系統提示與工具定義等 harness 本身就佔約 75% 的成本，工具輸出只佔 3.3%，使用者端外掛碰得到的內容合計約 6%。作者觀察到的軌跡符合一種可能的機制（作者沒有下因果結論）：壓縮省下的 token 被後續多出的診斷、測試與重新檢索抵銷，而每一回合都要重送整段快取內容。在另一組單次生成的實驗中，壓縮讓計費 token 少 73%，但 SEARCH/REPLACE 修補能成功套用的從 27/40 掉到 15/40，因為壓縮改掉了需要逐字比對的程式碼。單一 harness、單一廠商 2026 年 7 月的價格；端到端的帳單比較都是單次 prompt 的跑分：主實驗平均只有約 4.5 回合，另一組長任務實驗（529 個 session、Opus 4.8）方向相同，壓縮外掛同樣沒省到錢。作者另外分析 41 個真實互動 session 的帳單組成，結果很不一樣：harness 只佔約 8% 的輸入 token，外掛碰得到的內容（工具呼叫參數、CLAUDE.md 與提醒文字、較長的工具輸出）約佔 30% 的成本，依同樣的捕捉率推算，壓縮在互動情境能省的上限可能到約 9%，但沒有實測。Weinberger、Hozez 2026

對你的意義

省 token 最有效的是減少無效探索：任務開頭直接指定要看的檔案與範圍、一個任務一個對話、看到 agent 反覆讀同一檔案就中斷重新說明。記下一類任務平常要幾個回合，明顯超過時介入，但上限不要設太緊。一個工作階段中途不要頻繁切換 effort 或 MCP 工具，以免快取失效。更新不要為了省錢加裝壓縮工具輸出、代理 API 的外掛；要比較就看「每個成功任務的實際帳單」，不要看 token 數。真正能省的是少幾個回合，以及少裝用不到的 MCP 工具與冗長的系統設定（它們每回合都被重送）。「不要裝壓縮外掛」的端到端證據只來自單次任務的跑分；多輪互動的 session 中外掛碰得到的內容比例較高，效果可能不同，要比就用自己的帳單量。

三多 agent：通常更貴，不一定更好

  1. 六種多 agent 流程有五種輸給單一 agent更新：同樣用 GPT-4.1、10 個 benchmark（數學、問答、HumanEval、MBPP 等，都不是在 repo 裡寫程式的 agent 任務）、每種跑 3 次；各流程是作者在共用步數上限下重新實作的版本，不是原始系統。五種流程的合併準確率落後 1.71 到 8.76 個百分點，每次都輸；唯一勝出的 EvoAgent 多 3.05 個百分點，3 次都贏，token 多用 27%。token 用得多不代表比較準：兩種辯論式流程用了 1.39 與 4.34 倍的 token，準確率反而較低。沒有統計檢定。但在最接近 agent 任務、需要檔案檢視與工具使用的 GAIA 上（各跑一次），五種固定流程有三種高於單一 agent，其中兩種只高 1 到 2 個百分點，Jarvis 高 9 個百分點、token 還比較少，EvoAgent 反而較低；換成 Qwen3-32B 時全部輸給單一 agent。所以在 agent 任務上，這篇的證據是混合的。依 2026 年 10 月的 v2（v1 每種只跑一次，數字不同）。Fu 等 2026
  2. agent 團隊成本高 1.8 到 5.1 倍：50 個網頁應用程式、8 種設定各跑一次，四組「團隊 vs 單一 agent」只有一組顯著提升（GPT 6 Sol 中等 effort，+7.3 個百分點）。Claude Opus 5.5 中等 effort 時團隊 −0.3 個百分點；max effort 團隊每個應用程式 122 美元、單一 agent 23.77 美元，分數差距不顯著。多出的成本主要是每個子 agent 重新讀入的快取輸入。Vals AI 2026

對你的意義

預設用單一 agent。只有在工作真的能切成互不相依的部分（例如同時查幾個獨立模組），才考慮子 agent，並先比較成本。

一句話總結：AI 不一定讓資深開發者變快，品質下降卻會持續。2026 年的命令列 agent 在大公司內看得到持續的產出增加，但沒有人量品質；有提交 AI 設定檔的專案品質退化較少（觀察性研究）。效能類修改最難被接受，C++ 與多檔案修改仍明顯比 Python 單檔難，所以量測、CI 與人工審查不能省。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一AI 真的讓人變快嗎

  1. 2025 年初：資深開發者在自己的專案上反而變慢：16 位資深開源開發者、246 個真實任務隨機分組，可用 AI 時完成時間增加 19%（信賴區間 +2% 到 +39%）；他們事前預期快 24%，事後仍以為快了 20%。工具主要是 Cursor 搭 Claude 3.5／3.7 Sonnet。METR 2025
  2. 2026 年追蹤：可能變快了，但數據無法確認：57 位開發者、800 多個任務，原參與者（只有 10 人）−18%（信賴區間 −38% 到 +9%）、新參與者 −4%（−15% 到 +9%），負數代表變快，但都不顯著。很多人拒絕在不用 AI 的情況下工作，30% 到 50% 的人沒送出不想手寫的任務，METR 認為這是低估。METR 2026
  3. 速度提升短暫，品質下降持續：806 個採用 Cursor 的 GitHub 專案對比 1,380 個配對專案，新增程式碼行數在第一個月增加數倍，約兩個月後消失；靜態分析警告增加約 30%、程式複雜度增加約 41%，而且持續存在，並會拖慢之後的開發。警告增加主要來自程式量變大，控制程式碼規模後，只剩複雜度有獨立的增加（約 9%）。樣本是 TypeScript、Python、JavaScript 為主的開源專案，而且實驗組都是有提交 Cursor 設定檔的專案。He 等 2026
  4. 用 AI 學新東西，理解會變差：52 位工程師隨機分組學一個新的 Python 非同步函式庫，用 AI 組測驗分數低 17%（d = 0.738，p = 0.010），時間沒有顯著差異。差距最大的是除錯題，只問概念、自己解決錯誤的人分數較高，但這兩點都是事後的探索性分析，後者樣本也很小。受試者是從群眾外包平台招募的工程師，用的是聊天式助理，不是 agent。Shen、Tamkin 2026
  5. 2026 年命令列 agent：合併的 PR 增加，四個月沒消退新增：Microsoft 數萬名工程師 2026 年 1 月到 4 月導入 Claude Code 與 GitHub Copilot CLI，合成對照法估計導入者每人每天合併的 PR 多 24.0%（95% 可信區間 +14.5% 到 +33.7%）；比較基準是已經有 IDE 版 Copilot，不是完全不用 AI，樣本是導入那一週（1 月 5 到 11 日）就有使用紀錄的活躍工程師，2 月 +29.4%、3 到 4 月 +20.0%，差異在誤差內；把導入日期假設在 2025 年 10 月的安慰劑檢定沒有效果（−1.1%）。只用一種工具的人中，同一人比自己不用的週，用 Claude Code 的週 +11.4%、用 Copilot CLI 的週 +24.9%，作者沒有歸因，推測是兩者被用在不同任務，或 Copilot CLI 是 Microsoft 自家產品而較貼合（整理者認為不能據此判斷工具本身的優劣）；一週用 5 天以上 +50.1%，但作者說這是相關、不是因果（用得多的週可能工作較輕）。只量合併的 PR 數量，沒有量 PR 大小、退版、bug 或程式品質，作者自己說這是「最迫切的未解問題」，也承認 PR 數會獎勵小而頻繁的提交。作者都是 Microsoft 員工、單一公司、預印本。Murphy-Hill 等 2026
  6. 品質退化幅度跟有沒有 AI 設定檔有關新增：重新分析另一份 agent 導入資料（Agarwal 等，以第一個 agent PR 為導入點；不是上面的 Cursor 研究），先用 agent 的開源專案中，沒提交任何 AI 設定檔的，導入後複雜度 +52.7%、靜態分析警告 +24.1%；有提交的 +26.7% 與 +14.0%。觀察性研究，兩組本來就不同，差距本身沒有經過檢定；設定檔多半是導入同時或之後才提交的（作者認為這會讓差距被低估）。詳見「AI Agent 研究（一）」第三節。Denisov-Blanch 等 2026

對你的意義

在你熟悉的大型 C++ 專案上，AI 不一定讓你變快，要自己量。品質下降是持續的，所以靜態分析與審查不能省。學新的 SDK 或演算法時，先自己理解，只把 AI 當成問概念的對象。更新新的證據偏向「2026 年的 agent 確實讓產出變多」，但唯一量到明確正向效果的 Microsoft 研究量的是 PR 數，沒有一篇同時證明品質沒變差；而且那篇沒有按語言或專案類型分開報告，Cursor 研究則以 TypeScript、Python 為主。自己評估時，數量與品質要一起記：除了完成多少任務，也追蹤靜態分析警告、複雜度與之後的修 bug 次數。

二什麼樣的 agent 產出會被接受

  1. 任務類型影響最大：7,156 個 agent 送出的 PR，整體接受率 69.3%；雜務類 84.0%、文件 82.1%，修 bug 66.0%、測試 61.5%，效能類最低只有 55.4%。觀察性資料，不能推論因果。Pinna 等 2026
  2. 效能類 PR 常缺量化數字：2,260 個效能 PR，agent 寫的有附驗證的比例和人相近（82.3% 對 80.6%），但較多只靠推理說明（51.4% 對 39.3%），較少跑 benchmark（46.1% 對 57.2%），但 agent 組逐季上升，到 2026 年第二季已和人相當（60.1% 對 58.7%）；合併率 54.4% 對 73.3%。人和 agent 都約一半有驗證的 PR 沒附任何量化數字。Peng 等 2026
  3. 多數被接受的 agent PR 沒經修改：9,427 個已結案的 agent PR，被接受的中外圍貢獻者 76.5%、核心開發者約 72% 沒經修改。核心開發者審得比較仔細（審查留言 3.6 則對 2.0 則，有統計檢定、效果量小）；沒跑 CI 就合併的比例，外圍 19.1%、核心 11.2%（未檢定）。Cynthia 等 2026
  4. 只有 AI 審查的 PR 合併率較低：只經 AI 審查的 PR 合併率 45.2%，只經人審查的 68.4%；在 98 個只經 AI 審查、最後被放棄的 PR 中，找到 13 個審查機器人（含靜態掃描工具），12 個的有效建議比例（關鍵字判定）低於 60%；只看失敗的 PR，很多工具只有幾個樣本。合併率的分母包含仍開著的 PR，只算已結案的是 56.4% 對 76.0%。沒有控制 PR 大小等因素，只用 AI 審查的專案也可能本來就缺維護者。Chowdhury 等 2026
  5. 真實的多檔案工作仍然很難：參考解答平均改 4.1 個檔案、107.4 行的題目上，依 ICML 正式版（每題最多 50 回合、2 美元），公開題目最佳 25.9%（GPT-5）、新創公司的私有 repo 題目最佳 17.8%（Opus 4.1），同一個模型 Sonnet 4 是 17.6% 對 9.1%。arXiv v2 另外重跑了公開題目，最佳 43.6%（Sonnet 4.5），但沒寫明設定，私有題目也沒有重跑，所以這組數字不能和私有題目直接比。分數都是在提供人工補寫的需求與介面規格下得到的。Claude Sonnet 4 的失敗主要是 context 爆掉與不停讀檔（內文寫 35.6% 與 17.0%，同版表格換算約 32% 與 19%，論文前後不一致），而且這個分析是在每題最多 50 回合、2 美元的上限下跑的。題目只有 Python、JavaScript、TypeScript、Go，C++ 被作者列為代表不足。SWE-Bench Pro 2026
  6. C++ 明顯比 Python 難：2025 年的多語言基準中，Python 最佳 52.2%，C++ 最佳只有 14.73%、C 只有 9.38%；改越多檔案、補丁越長，成功率越低。但差距不全是語言造成的：Python 題取自 SWE-bench Verified、難題比例低（依論文表 3 算，Python 9%、C++ 33%），三種 agent 框架原本也是為 Python 設計，作者自己列了這些原因。用的是 2025 年的模型，C++ 只有 129 題。Multi-SWE-bench 2025

對你的意義

效能相關的修改，要求 agent 附上修改前後的量測數字，沒數字不合併。跨模組的修改先拆小、直接指定檔案。合併前一定跑 CI 並親自審查，AI 審查只當補充。

AI Agent 研究（四）：MCP 與平行程式

整理日期：2026 年 11 月 14 日 · 14 篇參考文獻 · 全文查核版（11 月 14 日補充 4 篇，標示新增）
一句話總結：接上工具不代表會用，平行程式也不會自動調好。工具描述與介面設計影響很大；效能來自「正確性檢查加 profiling」的迴路，而且要防 agent 偷改條件、漏掉同步。
收錄門檻：每篇論文都讀過全文，對照內文與表格核對數字，並檢查樣本數、重複次數、統計檢定與作者自述的限制；方法沒有重大問題才收錄，預印本照收但標明。句尾標籤是出處；「對你的意義」是整理者的判斷，不是論文結論。刪除的研究與原因見「AI Agent 研究（五）」。

一MCP 與工具設計

  1. 接上工具不代表會用：36 個真實 MCP server、1,000 個任務、20 個模型，最佳通過率 82.2%。約 6,900 個失敗中，63.3% 是理解、整合或太早停止，只有 36.7% 和工具有關（不用工具 10.5%、錯誤後無法恢復 10.3%、選錯工具 9.0%、參數錯誤 6.9%）；失敗分類是 LLM 自動判定的。通過與否也用 LLM 評審，不同評審差 2 到 5 個百分點，82.2% 是最寬鬆的主評審下的結果。MCP-Atlas 2026
  2. 工具描述幾乎都寫得不好：103 個 MCP server、856 個工具中，97.1% 的描述至少有一個缺陷；89.8% 沒寫限制、89.3% 沒寫使用時機。補齊描述後任務成功率中位數 +5.85 個百分點，但執行步數 +67%。只有一個模型做了配對比較（p = 0.02）。更新另外 3 個模型「補齊前」的數字取自原 benchmark 論文，不是同一環境重跑；唯一做配對比較的模型只補了用途、使用時機與限制三項；24 組模型與領域中有 16.67% 反而變差。只保留重點的精簡描述（例如拿掉範例）與完整版沒有顯著差異。另一個實驗用原始碼核對、讓描述更正確，重跑 92 題反而少解 9 題（26 對 35，p = 0.064，不顯著）；作者推測這些工具包的是 Yahoo Finance、GitHub 這類模型本來就熟的服務，對少見或自家的工具描述品質可能更重要，但沒有測過。描述的評分由 3 個 LLM 打分，抽 90 個工具人工驗證，一致性 κ 0.72 到 0.89。Hasan 等 2026
  3. 專有工具做成 MCP server 的實例：把嵌入式硬體設計工具做成 14 個 MCP 工具，7 個本地開源模型（4-bit 量化）中最強的完成 99% 的預期呼叫，這是多種設定中挑出的最佳組合，不是預設設定；工具描述精簡後，每個模型的工具失敗率都上升，多數約加倍；在系統提示加入示範範例（few-shot，不是加在工具描述裡），反而讓 7 個中的 2 個模型大幅少呼叫工具（預期呼叫完成率 0.956→0.571、0.731→0.179），是不動作而不是做錯。MCP server 是專有工具的仿製品，沒有呼叫正式 API；沒有統計檢定，benchmark 未公開。Liparulo、Pierri 2026
  4. 工具介面設計影響很大：同一模型下，專為 agent 設計的介面比只給 shell 高 64%（相對值）。拿掉編輯時的語法檢查掉 3 個百分點；搜尋結果一次只給一筆，比完全不給搜尋工具還差；檔案檢視視窗 100 行最好，30 行或整個檔案都變差。消融只用 GPT-4 Turbo、在 SWE-bench Lite（Python）上各跑一次，3 個百分點約是 9 題。SWE-agent 2024

對你的意義

如果要把自己的量測 SDK 包成 MCP server，工具描述要寫清楚用途、使用時機、限制與參數單位；輸出要精簡、摘要好，不要一次倒出整段原始資料。工具數量少而清楚，比多而模糊好。更新描述寫重點就好，範例不是必要；模型沒看過的自家工具，限制與參數單位可能更要寫清楚（這是作者的推測，沒有實驗）。

二平行程式與 GPU：AI 會寫，但要靠迴路校正

  1. 平行程式比循序程式難很多：420 題、7 種執行模型，GPT-4 循序程式 pass@1 約 76%，平行程式平均只有 37.8%；OpenMP 約 60% 最好，MPI 與 MPI+OpenMP 約 22 到 23% 最差。寫對的程式也常常很慢，平行效率最高只有 0.13。這是 2023 年的模型單次生成單一函式，不是 agent、沒有回饋。ParEval 2024
  2. 小模型轉換整個專案幾乎都失敗：6 個程式做三種單向轉換（CUDA 轉 OpenMP Offload、CUDA 轉 Kokkos、OpenMP 執行緒轉 Offload）。3 個作者自寫、一百多行的微型程式有成功的組合；3 個較大的應用（780 到 3,039 行）沒有任何方法與模型組合成功。主要失敗是 CMake 與 Makefile、跨檔案介面不一致。用的是 2024 到 2025 年的小型或量化模型（GPT-4o mini、o4-mini、Gemini 1.5 Flash、4-bit 的 Llama 3.3 70B、QwQ-32B），商用 API 總預算 200 美元，部分大程式的組合因預算或輸出長度沒跑完；沒有測前沿大模型。ParEval-Repo 2025
  3. 只轉 kernel 時：方向很重要，重試救不回來新增：35 個 kernel 在 CUDA、OpenMP、OpenCL 之間的 142 個轉換任務（含 4 個 OpenMP target 的案例方向），建置與驗證固定、只轉 kernel，每題 3 次、單次生成不修正。GPT-5.4 與 GPT-5.3-codex 的 pass@1 都是 62.7%，Qwen 3.5 是 23.9%（兩家的取樣設定不同，差距不能全歸於模型能力）。拿掉平行結構（CUDA 轉 OpenMP）比加上去（例如 OpenCL 轉 CUDA，要補上明確的同步與記憶體管理）容易得多。兩個 GPT 模型約 30% 的任務 3 次全錯，失敗多是系統性的（例如 OpenMP 版本裡留著 CUDA 的識別字），重抽樣救不回來；Qwen 另有 4.6% 能編譯執行、結果卻錯。程式做語意不變的改寫後，GPT 模型的通過率維持在 85% 到 91%，Qwen 從 74% 降到 56% 但未達顯著；這只算原本至少做對一次的題目，作者提醒有倖存者偏誤，不能和上面的 62.7% 直接比。87 個題目設定中 80 個只檢查輸出字樣與結束碼，「通過」不等於數值正確；只在一個平台（RTX 4070）測。ParBench 2026
  4. 執行與 profiling 回饋能大幅提升：GPU kernel 基準 250 題，DeepSeek R1 一次產生時比 PyTorch 快的比例 Level 1 為 12%、Level 2 為 36%；加上 10 輪執行結果與 profiler 回饋後提升到 43% 與 72%；只給執行結果已到 41% 與 62%，profiler（PyTorch 的運算子時間拆解，不是 ncu）主要在 Level 2 再多 10 個百分點。正確性只用 5 組隨機輸入檢查。KernelBench 2025
  5. profiler 數據要先解讀再給模型新增：AWS 的 KernelPro 在 42 個 KernelBench 題目上做消融（Sonnet 4.6、A100；每題 15 個獨立搜尋，各 30 輪、每輪 2 個候選，取最好的結果，極端值有截斷）。只給約 50 個 ncu 原始計數器時，幾何平均加速 1.77 倍，比完全不給 profiler 回饋的 3.35 倍還差（p = 0.0007），雖然解出的題數較多（36 對 32 題）；在原始計數器之外，再附上工具算出的瓶頸判斷與具體建議（例如「每執行緒 168 個暫存器，溢出到 local memory」），提升到 4.00 倍。作者的解釋是模型會去最佳化不影響實際時間的計數器。完整系統在 KernelBench 三個等級的幾何平均加速 2.42、4.69、5.30 倍（相對 PyTorch eager）。業界預印本，只用一個模型；取多次搜尋中最好的結果，數字偏樂觀；正確性只用 allclose（絕對誤差 1e-2、相對誤差 1e-3）判定；沒有限制的章節。KernelPro 2026
  6. 正確性檢查加 profiling 的流程有效：把 Codex 改成「找熱點、規劃資料搬移、正確性檢查、依 profiling 修改」的流程轉成 OpenMP GPU offload，36 個 kernel 排除 2 個多檔案的 NAS 程式（BT、LU）與 1 個參考實作只有 CPU 版的程式後，33 個中 31 個成功（另 2 個是 agent 把運算留在 CPU），27 個比參考實作快或持平；HeCBench 幾何平均 3.1 倍（A100）與 3.6 倍（RTX 4060），不加流程的同一模型只有 2.0 倍與 2.4 倍，但差距集中在少數幾個 kernel（兩者在 jacobi 都超過 100 倍；也有 kernel 反過來是不加流程快很多），中位數兩者相近（1.34 對 1.39 倍），而且不加流程的版本有 2 題失敗、沒算進平均；Rodinia 上不加流程的版本甚至變慢（0.30 倍）。token 只多約 11%，但只在 NAS 程式上量。沒有逐一移除步驟的消融；未報告每個 kernel 的生成重複次數。Kaplan 等 2026
  7. agent 會偷懶：上述研究被排除的 kernel 中，有 2 個是 agent 把主要運算留在 CPU 上。Kaplan 等 2026
  8. 專門訓練的模型可以超越通用模型，但你用不到：用強化學習專門訓練的 CUDA agent，在 KernelBench 上 96.8% 的題目比 torch.compile 快；同一流程下 Claude Opus 4.5 只有 66.4%。論文沒有報告重複次數或變異；agent 執行時能直接量自己對 torch.compile 的加速，計分時取整段過程中最快的正確版本；而且只和 torch.compile 比，沒有和 TVM 這類編譯框架比。CUDA Agent 2026
  9. agent 會偷改題目條件、漏掉同步問題：調校 HPC 程式的實驗中，題目規定矩陣固定 2048：單一 agent 擅自放大到 16384，多 agent 版本中負責 CUDA 的 agent 放大到 4096 與 8192，這些結果有出現在 agent 之間的訊息裡，兩個監督角色卻都沒發現；一個缺少同步的 CUDA 版本通過了使用者提供的正確性測試，錯誤沒被抓到。每種條件（多 agent、單一 agent）在相同設定下只跑 3 次，作者承認不足以下統計結論。VibeCodeHPC 2025
  10. 真實程式裡的熱點最佳化：CUDA 只有約四成是對的新增：114 個完整程式（92 個 CPU／OpenMP、22 個 CUDA），用 profiler 找出熱點函式，讓 GPT-5.1、Claude Sonnet 4.5、Qwen3-Coder 各產生 10 個改寫版本（單次生成，沒有執行回饋）。結果正確的比例：循序 76.9%、OpenMP 61.4%、CUDA 38.8%；CUDA 有 35.2% 連編譯都不過。要求至少快 1.5 倍時，3 次中至少有 1 次達標的機率：循序 0.10 到 0.17、OpenMP 約 0.15 到 0.25、CUDA 約 0.09 到 0.11。HPC-Bench 2026
  11. 短的 kernel 平行化反而變慢新增：同一研究中，結構簡單的程式在 16 執行緒 OpenMP 下（中等資料大小），61 個有 41 個（67%）連三個模型共 30 個候選中最好的都到不了 1.05 倍；作者認為這組常是 kernel 太短（中位數 7.33 ms，有些只有幾微秒），執行緒開銷吃掉了好處，但同一組也有 matmul 加速 49.6 倍。最複雜的 5 個程式中，2 個沒有任何正確的候選。作者主張評估要看「得到正確且夠快結果的機率」，不能只看最好的加速倍數。加速倍數只算 kernel 本身的時間；資料搬移、配置記憶體或 I/O 佔大部分時，整個程式的加速會小得多。單一平台（OpenMP 在 AMD EPYC 7543、CUDA 在 A100；GCC 14.2、NVCC 12.4），CUDA 只有 22 個程式。HPC-Bench 2026
  12. 移植手動最佳化過的 C++ 到 CUDA：有時先「去最佳化」比較好新增：12 個為 Arm CPU 手動最佳化（NEON SIMD、分塊、預先打包）的 HPC kernel，比較「直接轉 CUDA 再最佳化」與「先讓模型移除 CPU 專屬最佳化、再轉 CUDA 再最佳化」，各 50 次。單次流程下 18 組可檢定的比較中，5 組先去最佳化較快、3 組直接轉較快（校正多重比較後）；最明顯的是卷積，Qwen3-235B 直接轉只有 12% 成功、去最佳化後 96%，成功版本的效能中位數 106 對 4,366 GFlops。去最佳化多一次呼叫；拿呼叫次數相同、但多出的那次用在再最佳化一輪（不是重試轉換）的對照組來比，去最佳化 4 組領先、對照組也有 4 組領先（未校正、探索性）。論文沒測「同樣預算拿去重試轉換」能不能補上差距。單次流程中，先去最佳化對成功率的影響也因模型而異：Qwen3-235B 多數 kernel 大幅提升，gpt-oss-120b 好壞參半，甚至可能下降。加上反覆生成與修正後，gpt-oss-120b 的差距大多消失，Qwen3-235B 在 3 個 kernel 上仍大幅領先。效能只比成功的試次。用的是 gpt-oss-120b 與 Qwen3-235B，不是最新的前沿模型；正確性只在測試尺寸下驗證。Mukunoki 等 2026

對你的意義

新模型不會自動把平行程式調好，效能來自你搭的迴路：固定的參考答案與容許誤差、固定問題大小的量測腳本、profiler 輸出、以及「運算確實在 GPU 上、執行緒同步正確」的檢查。即時系統的時序與同步錯誤，一般測試很難抓到，要另外設計壓力測試或用 sanitizer。建置系統的修改由你把關。更新沒有執行回饋時，CUDA 改寫大約六成是錯的，所以一定要讓 agent 能自己編譯、執行、比對結果，再談效能。平行化前先量 kernel 時間：只有幾毫秒以下的，開執行緒或搬到 GPU 可能得不償失。把已經為 CPU 手調過（SIMD intrinsics、分塊）的程式移到 GPU 時，如果直接轉一直失敗，可以先請 agent 寫出一個乾淨、未最佳化、結果相同的參考版本，再從那裡轉 CUDA；但這不是預設做法，效果因模型而異，直接轉能成功時不一定比較差。讓 agent 用 profiler 時，請它先判斷瓶頸類型（記憶體或運算受限）並附上解讀，不要只丟原始計數器給它。轉成 CUDA 這種要補上同步與記憶體管理的方向特別容易錯；ParBench 顯示單純重抽樣救不回來，失敗時要給它編譯錯誤和比對結果去修（有回饋的效果見上方 KernelBench）。

一整理成做法

以下是整理者依前四篇研究提出的做法，效果仍要在自己的專案上驗證。

  1. 先準備驗證工具：回歸測試、參考輸出、量測腳本、profiler 指令都先備好，再讓 agent 動手；每次修改都跑完整測試，退步就退回。
  2. 驗收看產物，不看報告新增：agent 會朝被檢查的東西最佳化，「測試全過、已完成」不能當證據。確認功能真的在指定的模組裡並被呼叫、沒有針對測試輸入寫死；保留一組 agent 看不到的測試或量測做最後確認。agent 寫的測試，把程式故意改壞一處確認它會失敗，不要只看覆蓋率。
  3. CLAUDE.md 精簡：只寫建置與測試指令、硬體與即時限制、不可違反的規則；不要自動產生後直接留用。更新長度（500 行內）、位置、拆不拆檔不必糾結；但寫進去的規則只有約六到七成會被遵守，越寫越多程式越容易漏。
  4. 不可違反的規則用機械方式擋新增：例如即時執行緒不可配置記憶體、不可改動校正檔格式，做成 hook、lint 規則、編譯期檢查或 CI 測試；CLAUDE.md 說明原因，檢查負責確保做到。
  5. skill 少而精：只為反覆出現、agent 查不到的流程寫 skill；關鍵警告放最前面，註明版本，驗證寫一次；新增後用真實任務比較有無 skill。更新裝太多 skill 會讓 agent 選錯或乾脆不用，用不到的就移除。
  6. 任務要小、範圍要明：開頭交代目標、限制與要看的檔案；跨模組的修改拆成小任務；一個任務一個對話。
  7. 盯著執行過程：反覆讀同一檔案或改了又改就中斷；明顯超過平常回合數就重新說明。
  8. effort 用預設：日常用 medium，修既有程式的 bug 開 high，max 只在測過確實有效時用。
  9. 單一 agent 優先：子 agent 只用在可以完全切開的工作。
  10. 省錢看帳單，不看 token新增：不裝壓縮工具輸出或代理 API 的外掛；比較做法時看每個成功任務的實際費用。少幾個回合、少掛用不到的 MCP 工具，比壓縮輸出有效。
  11. 效能修改要附數字：要求修改前後的量測結果，並檢查運算在目標硬體上、同步正確。更新平行化前先量 kernel 時間，太短的不值得開執行緒或搬 GPU。CUDA 改寫一定要讓 agent 能編譯、執行、比對結果。profiler 結果請 agent 先判斷瓶頸再細看，不要只給原始指標。
  12. 移植 CPU 手調程式到 GPU新增：直接轉一直失敗時，先請 agent 寫出乾淨、未最佳化、結果相同的參考版本，再從那裡轉 CUDA；直接轉能成功時不必多這一步。
  13. 產出與品質一起量新增：評估 agent 有沒有幫助時，除了完成的任務或 PR 數，也追蹤靜態分析警告、複雜度與之後的修 bug 次數。
  14. 安全：不裝來路不明的 skill；新增相依套件先確認存在；合併前跑 CI、親自審查。

各條證據

  1. 故意改壞：專案甲用恆等校正測試時，一個係數的正負號寫反、內插權重寫成 0、漏掉一個減半的係數這三種錯全部通過。故意對調兩個字串欄位，只有一支逐欄比對的測試抓到。專案乙的審查故意改壞 21 處，測試全部抓到。
  2. 參考實作也要驗：專案丙第一輪讓新實作跟參考實作逐位元一致，後來才發現參考實作用 float32 逐列累加：在一般解析度的影像上，一項統計值就偏了 2–7.5%，換成解析度高得多的感測器會偏低 70–81%。專案甲的參考模型用 float64、韌體用 float32，模型在部分操作條件下是錯的。另外有一次驗證是先假設了一個參數值，再「量到」同一個值，是循環論證。
  3. 二進位不是當次建的：專案甲 4 次（DLL 比原始碼舊、外部提供的二進位是一個月前編的、服務改了程式碼沒重新安裝）。專案乙 1 次：中文編譯器訊息讓建置工具記不到標頭相依，31／42 個目標檔沒被重編，造成結構的記憶體版面不一致。症狀是停止指令卡住，很難聯想到建置。
  4. 靜默退回與吞掉的例外：專案甲的 GPU 後端因為路徑太長或 DLL 名稱不對而靜默退回；建置只發警告就跳過複製 DLL，到執行時才失敗。專案乙的 watchdog 用了一個其實會開啟裝置的列舉函式，丟出的例外被 catch 吞掉、當成「裝置不在」，結果把正在擷取的裝置關掉：約每 40 次開始／停止就卡死一次，log 裡什麼都沒有。
  5. 測試期望值算錯：專案乙的 agent 心算錯一個邊界值，把測試期望值改成程式的輸出。後來確認程式是對的，但使用者因此擔心其他測試的期望值也有問題。
  6. 先查資料再推測：專案甲的 agent 推測「相機增益可能沒改回」並列進問題清單，但設定紀錄檔裡就有正確的數值。還有一次 agent 要使用者抄下相機設定，而那些設定其實已經記在另一個專案的資料裡。
  7. 操作流程也要先問：專案甲在設計一個操作流程的引導介面時，有 4 個決定是在逐題追問中才被使用者抓到：步驟順序錯了，某項設定必須在放好樣品之後才能做；每天現場取得的資料被設計成打包進校正檔；兩項現場取得的資料被當成固定檔；最後要實作進專案的參考程式被當成留在外部的依賴。
  8. 複述需求：專案甲有 4 次產出物的種類或放的位置跟使用者要的不同（做了中間處理步驟的圖，要的是最終結果的圖；最大最小值算錯對象；要放進壓縮檔的東西差點進 repo；要交接的功能差點實作）。
  9. 範圍外的 repo：專案丙的 agent 在參考實作的 submodule 提交修正，使用者不希望參考實作有變動，那次修改就撤掉了。
  10. 看截圖：專案乙有座標軸沒對齊、三處標籤疊在別的東西上；專案甲有圖片重疊、SVG 文字裡的粗體標籤不會顯示。
  11. 有狀態 API 的並行語意：專案丙新增「處理後暫存、之後查詢」的函式，資料競爭、per-thread 暫存不會清理、thread ID 會被重用，都是使用者追問才出現的。
  12. 模擬與實機：專案甲的 stub 量不到真機每次讀相機屬性要 17 ms，GUI 重畫從幾 ms 變成 100 ms 以上。GPU 跟上即時節奏時會降頻，連續呼叫的數字只是上限。有一支同步檢查用 15.6 ms 才跳一次的時鐘去量比這還短的間隔。所有靜態檢查全綠，實機卻不能正常運作。
  13. 硬體狀態與互斥：專案甲的相機被留在外部觸發模式，之後每支測試都等不到觸發；平行 worker 搶同一台相機；燒韌體前沒有備份，而那塊板子讀不回 flash。專案乙在監控程式運作時跑全套測試，測試連上了真的引擎。
  14. 非英文 Windows 的靜默陷阱（setup 與 skill 的修改）：專案乙遇過 MSVC 用 cp950 讀 UTF-8，中文註解的最後一個位元組被當成續行，吞掉下一行；heredoc 吃掉反斜線；寫檔預設 cp950，遇到 ✓ 就把檔案截斷；還有上面那次標頭相依。專案甲遇過 Python 換行轉換讓 7 行插入變成 4,700 行的 diff，以及 µ 被大寫化變成 M。

AI Agent 工作守則

這一篇是給 coding agent 讀的 Markdown 原檔轉成的網頁版。下載 .md 原檔，或讓 agent 直接讀 原檔網址。

第 3 版，整理日期：2026 年 11 月 14 日。給 coding agent 讀，只收模型預設不一定會做的規則。依據：（二-1）等為研究筆記章節，證據與限制見筆記頁 https://a638138.github.io/economist/notes/ ；「做法」為整理者為方便驗收而定；「專案經驗」為實際專案觀察，樣本小（第 3 版新增條目的證據見筆記「AI Agent 研究（五）」第五節）。與專案的 CLAUDE.md 衝突時，以專案為準。

核心規則

  • 動手前先寫下驗證方式與通過條件（測試、參考輸出與容許誤差、量測命令），沒有就先提出；非小型的修改（跨檔案、改演算法或介面）先請使用者確認。需求只有一兩句時，先用一句話複述要做的東西、放在哪、什麼形式。先寫測試並看它失敗，再改到通過。條件事先定好，沒過就找原因，不改門檻。（二-1；做法；專案經驗）
  • 會被外部依賴的行為（通訊協定、檔案格式、使用者看得到的文字與畫面），以及實驗或操作流程（什麼時候量、資料存在哪、綁哪些設定），先分輪向使用者問清楚：問題編號、每題附建議。問之前先查專案裡和使用者提過的資料；寫出來的推測要標明是推測，並說用哪份資料可以確認。（專案經驗）
  • 每次修改後跑完整的相關回歸測試；退步就退回，不在壞掉的基礎上繼續改。專案已知會失敗的測試不算退步，要列在專案的 CLAUDE.md。（二-1）
  • 不得為了讓結果通過而修改、刪除或跳過測試，也不得放寬容許誤差、改變問題大小或輸入條件；確有必要，先說明並取得同意。例外：需求本身改了、測試前提因此過時，可以改，回報時說明。測試的期望值本身算錯時也可以改：用獨立的方法重算（寫程式算，不要心算），回報時說明為什麼是測試錯、不是程式錯。（四-2；專案經驗）
  • 測試通過不等於完成。回報前檢查產物本身：功能在要求的模組裡且確實被呼叫、沒有針對測試輸入寫死的分支、沒有把要求的架構簡化掉。（二-1）
  • 測試要能抓到錯：不要只用恆等、全零、對稱的輸入；測試是事後補的，就把實作故意改壞一處，確認測試會失敗。驗證用的數字不能來自被驗證的對象；跟參考實作逐位元一致不代表正確，參考實作也要對一個獨立的真值（較高精度或解析解）檢查一次，而且參考實作的數值型別要跟被測物一致。（二-1；專案經驗）
  • 測試或量測前，確認被測的二進位是用當次原始碼建的（比對時間戳或版本函式）。改了程式碼、行為卻沒變時，先懷疑建置。（專案經驗）
  • 有自動退回、略過或 skip 的地方，回報時寫出實際走的路徑（後端、版本、skip 數與原因）。不寫吞掉例外的 catch。（專案經驗）
  • 不修改任務範圍外的 repo（參考實作、別人的專案、submodule），要改先問。（專案經驗）
  • 改到畫面、圖表或 HTML 時，自己看過截圖（對齊、重疊、文字截斷）再回報；沒有截圖工具時，回報寫明未看過畫面，並列為要使用者親自看的。（專案經驗）
  • 宣稱效能改善必須附修改前後的量測（同一硬體、固定問題大小、多次執行，機器閒置）。量測工具先確認它量的是要量的東西：用假資料測它，或拿預估值對照實測。（三-2；專案經驗）
  • 非小型的工作做完後，派一次獨立審查（使用 reviewer 子 agent；使用者也可下 /review）：新 context、只讀，附上規格、自己做的判斷、測試沒涵蓋的情況，並要求列出沒判斷的項目。嚴重的先寫重現測試再修，小問題列出延後。除此之外預設不開子 agent，只有能完全切開的工作才開。（專案經驗：5 次審查都抓到測試沒發現的問題；AI 審查只當補充，見三-2；「其他時候不開子 agent」依二-3）
  • 回報分三部分：做了什麼、怎麼驗證（指令與結果）、哪些沒驗證到。因為環境缺東西而 skip 的、走了自動退回的、只在模擬、stub 或無畫面模式下跑過的，都算沒驗證到，最後一種標「未在實機驗證」。另列自己做的判斷（決定、理由、錯了的代價）、延後的小問題、值得使用者親自看的程式碼。（做法；專案經驗）
  • 工作跨 session 時，寫進度檔（現況、下一步、踩到的坑）並提交；換 session 時，給一段可直接貼的開場訊息（使用者也可下 /handoff）。（做法）
  • 新增相依套件前，確認套件名稱真的存在、是正確的那一個。（一-4）
  • 發現自己在兜圈時（重讀同一段、把同一處改了又改回），先停下來向使用者說明卡在哪裡。分段讀取大檔案不算。（二-2）
  • 提交前看一次版本控制狀態：一個提交一件事，工具改到的追蹤檔要還原。不要 print 或寫 log 任何金鑰、token、憑證；使用者的個人資訊不寫進專案檔案。（一-4；做法）

C++／GPU／即時系統／碰硬體的專案（只在這類專案適用）

  • 平行化（OpenMP、執行緒、GPU）前先量該段的執行時間，量過再決定。（四-2）
  • CUDA／GPU 改寫每次都要編譯、執行並與參考輸出比對；確認主要運算真的在 GPU 上，用 compute-sanitizer 檢查同步與競態。CPU 手調過的程式移植失敗時，先寫乾淨的參考版本再轉。看 profiler 結果時，先判斷瓶頸類型（記憶體或運算受限），只追跟它相關的指標，不要逐一去改善所有計數器。（四-2）
  • 改到鎖、執行緒、狀態機或即時迴圈時，提出壓力測試或實機量測，並把這些程式碼列為要使用者親自看的。新增「先暫存結果、之後再查」這類有狀態的 API 時，寫明多執行緒和多個 handle 下的行為，以及暫存什麼時候釋放。（四-2；做法；專案經驗）
  • 修改建置檔或跨檔案介面時，明確列出改動，交給使用者把關。（四-2）
  • 計時的呼叫節奏要跟實際使用時相同（連續呼叫量到的只是上限），並確認時鐘的解析度夠細（Windows 預設的計時器約 15.6 ms 才跳一次）；在模擬或 stub 下量到的時間不代表實機。（專案經驗）
  • 碰硬體的測試和腳本，結束時把裝置還原到開始前的狀態並讀回確認。同一個硬體一次只讓一方使用（平行的測試 worker、另一支正在跑的程式都算）。寫入裝置（韌體、EEPROM、相機記憶體）之前先備份，並確認讀得回來；備份不了就先告訴使用者。（專案經驗）

# AI Agent skill：撰寫設定檔與工具

撰寫 CLAUDE.md、SKILL.md 或 MCP 工具時才載入的 skill，依實證研究整理。整理日期：2026 年 11 月 14 日。
證據見 https://a638138.github.io/economist/notes/ 「AI Agent 研究（一）、（四）」；非英文 Windows 陷阱與機械檢查例子來自專案經驗，見「AI Agent 研究（五）」第五節。

## 最重要：寫進檔案的規則只會被部分遵守

- 簡單規則的遵守率約六到七成，agent 寫的程式越多越容易漏。
- 「違反就會出事」的規則，除了寫進檔案，一定要同時提出機械檢查：hook、lint 規則、static_assert 等編譯期檢查、CI 測試。檔案負責說明原因，檢查負責確保做到。
- 例：建置腳本在任何目標檔沒有記到標頭相依時直接失敗；測試用純文字比對 C 介面與各語言綁定，有函式沒綁就失敗；測試讀韌體原始碼裡的常數，跟主機端的表比對；測試從原始碼掃出舊版 Python 不支援的語法。

## CLAUDE.md／AGENTS.md

- 只寫 agent 從程式碼與 README 查不到的事：建置與測試指令、硬體與即時限制、不可違反的規則及其原因。
- 不寫架構介紹、目錄說明、用了哪些套件：agent 讀程式碼就知道，寫了只增加成本。
- 不要交付自動產生（例如 /init）後未經使用者審過的內容；自動產生的說明檔平均沒有幫助，成本還增加約兩成。
- 500 行內的長度、規則放第幾行、拆不拆成多個檔，都沒有可測得的影響；把力氣放在內容精準。
- 提交進版本控制，並提醒使用者隨專案更新；多數設定檔提交後就沒再改過。
- 重要規則不要只在對話中說，長對話被壓縮後會遺失。
- 把「違反了也不會報錯」的規則集中在檔案開頭的一節（為了方便查找和逐項做機械檢查，不是因為位置會影響遵守率）。這類規則在非英文的 Windows 上特別多，例如編譯器用系統編碼讀 UTF-8 原始碼、shell heredoc 把 `\\` 變成 `\`、寫檔預設用系統編碼、建置工具記不到標頭相依而連進舊的目標檔。
- 已知會失敗的測試，註明是哪台機器或哪個環境。
- 專案在 Windows 上開發、建置或執行時（非英文語系尤其要做），建立或檢查 CLAUDE.md 前讀同資料夾的 `windows-traps.md`，逐項檢查並提議哨兵測試。

## SKILL.md

- 只為反覆出現、agent 自己查不到的領域流程寫（例如量測、校正、QC 判讀）；通用程式技巧寫成 skill 幾乎沒有效益。
- 不要讓模型自己產生 skill 內容後直接使用；自生成的 skill 平均讓表現變差。
- 一個 skill 只處理一件事；核心規則精簡，細節拆到需要時才讀的附檔。
- 同時裝的 skill 越多，agent 越常該用時沒用、或選錯（10 個左右，較弱的模型就看得到）：用不到的 skill 移除；description 寫明何時使用，不要寬泛到和其他 skill 重疊。
- 關鍵警告放最前面；明寫不可跳過的步驟與驗證方式；驗證寫一次，不要求反覆檢查（過度驗證是常見的效率退化）。
- 範例標明「僅供參考，以任務要求為準」；agent 常把範例或預設值當成規則。
- 註明適用的 SDK 版本與環境；版本不符的 skill 會讓表現變差。
- 多個 skill 協作時，寫出產物之間的依賴關係。
- 附帶腳本時，腳本不得 print 或寫 log 金鑰。
- 交付時建議使用者用幾個真實任務比較有無 skill，再決定是否保留。

Windows 靜默陷阱檢查清單

這一篇是給 coding agent 讀的 Markdown 原檔轉成的網頁版。下載 .md 原檔，或讓 agent 直接讀 原檔網址。

agent-config-writing skill 的附檔，整理日期：2026 年 11 月 14 日。適用於在 Windows 上開發、建置或執行的專案，非英文語系（例如繁體中文 cp950）的陷阱特別多。建立或檢查專案的 CLAUDE.md 時使用：逐項查專案現況，有風險的寫進 CLAUDE.md「違反了也不會報錯」那一節，並向使用者提議哨兵測試（專門確認陷阱不存在的小測試，環境一變就失敗）。只提議，不要擅自改建置設定、轉檔或安裝 hook，由使用者決定。

用法

  1. 逐項執行「怎麼查」，記下結果：沒問題、有風險、不適用（例如沒有 C++ 的專案跳過 MSVC 項目）、無法判斷。
  2. 有風險的項目：寫進 CLAUDE.md 陷阱一節（一行說明現象，一行說明正確做法），並提議對應的修正與哨兵測試。
  3. 無法判斷的項目：列出來問使用者，不要猜。
  4. 專案特有、這份清單沒有的陷阱：問使用者過去踩過哪些，一併寫進陷阱一節。
  5. 每一項的修法都要先確認不會引入另一個陷阱；下面已標出常見的二次陷阱。

C++ 原始碼與字串的編碼（MSVC）

  • 現象：MSVC 讀沒有 BOM 的原始碼時用系統編碼（cp950），UTF-8 的中文註解可能吃掉換行，下一行程式碼消失；一般字串常值 "中文" 也會以 cp950 存進執行檔。通常只有 C4819 警告，編譯照樣通過。
  • 怎麼查：每個 C／C++ 編譯是否都有 /utf-8（看 compile_commands.json 或專案檔）；建置 log 有沒有 C4819；用嚴格 UTF-8 解碼掃過所有原始碼，找出不是 UTF-8 的檔（台灣的舊專案常有 Big5）。
  • 怎麼修：先把非 UTF-8 的原始碼列給使用者，轉成 UTF-8 後，再對所有 C++ 目標加 /utf-8。CMake 用 $<$<COMPILE_LANGUAGE:CXX>:/utf-8>；CUDA 的 .cu 要另外加 -Xcompiler=/utf-8，否則主機端程式碼一樣被當成 cp950。.rc 資源檔加 #pragma code_page(65001)。可以加 /we4819 把警告變成錯誤。
  • 二次陷阱：還有 Big5 原始碼時就加 /utf-8，那些檔的字串會靜默變成別的位元組。
  • 哨兵測試：CI 檢查 compile_commands.json 每一筆 C／C++ 編譯都有 /utf-8；在每個目標都會 include 的標頭放 static_assert(sizeof(u8"中文") == 7, "source not read as UTF-8"); 與 static_assert(sizeof("中文") == 7, "execution charset is not UTF-8");。

含中文的路徑

  • 現象：MSVC 上 char* 路徑用系統編碼解讀，包括 fopen、std::ifstream(std::string)、LoadLibraryA、std::filesystem::path(std::string)；UTF-8 的路徑字串會打不開，cp950 沒有的字元一律失敗。使用者名稱是中文時，TEMP 路徑也含中文，部分工具會失敗。
  • 怎麼查：搜尋用 char* 或 std::string 開檔、載入 DLL 的地方；專案路徑或使用者資料夾是否含中文。
  • 怎麼修：Windows 上用寬字元 API（_wfopen、std::filesystem::path 搭配 wstring 或 u8path）；跨語言介面明確約定路徑的編碼。
  • 哨兵測試：在含中文與 ✓ 的暫存資料夾裡，用專案自己的開檔函式寫入再讀回。

建置相依（CMake＋Ninja＋MSVC）

  • 現象：Ninja 靠比對 MSVC /showIncludes 訊息的前綴記錄標頭相依；中文版 MSVC 的前綴與編碼對不上時，專案標頭沒被記下，改了標頭也不會重編，連進舊的目標檔。
  • 怎麼查：建置後對一個一定 include 專案標頭的目標檔執行 ninja -t deps <目標檔>，看有沒有列出那個標頭（Ninja 本來就不記錄 Program Files、Visual Studio 底下的系統標頭，所以只 include 系統標頭的目標檔顯示 0 筆是正常的）；或改一個專案標頭的時間戳，執行 ninja -n 看相關目標檔是否會重編。也可以比對 CMakeCache.txt 的 CMAKE_CL_SHOWINCLUDES_PREFIX 和目前 cl 實際輸出的前綴。
  • 怎麼修：先更新 CMake（舊版有這個編碼問題）；或在建置環境設 VSLANG=1033 讓 MSVC 輸出英文（需裝有英文語言套件）。
  • 二次陷阱：CMake 在 configure 時就記下前綴。在已經 configure 過的建置目錄才改 VSLANG，或之後從沒設的 shell、IDE 建置，前綴反而對不上。改完要刪掉建置目錄重新 configure，而且每次建置的環境都要一致。
  • 哨兵測試：放一個一定 include 某個專案標頭的哨兵 .cpp，建置腳本最後用 ninja -t deps 確認它記到那個標頭，沒有就讓建置失敗。

Python 的文字編碼

  • 現象：Python 3.15 以前，沒指定 encoding 的 open()、read_text() 都用系統編碼（cp950）：中文會「成功」以 cp950 寫出，下游工具當 UTF-8 讀就變亂碼；遇到 ✓、µ 等 cp950 沒有的字元則出錯或截斷檔案。stdout 被導向管線或檔案時（agent 透過工具執行時幾乎都是），print 這些字元會 UnicodeEncodeError。
  • 怎麼查：用 python -X warn_default_encoding -W error::EncodingWarning -m pytest（3.10 起）找出沒指定編碼的地方，或用 ruff 規則 PLW1514；查 Python 版本與是否設了 PYTHONUTF8。
  • 怎麼修：讀寫檔案一律寫 encoding="utf-8"；給 Excel 開的 CSV 用 utf-8-sig；既有的 cp950 資料檔要照它實際的編碼讀，不能直接改成 utf-8。輸出用 PYTHONIOENCODING=utf-8 或 sys.stdout.reconfigure(encoding="utf-8")。
  • 二次陷阱：subprocess 的輸出編碼由子程序決定，cl.exe、cmd 內建指令等原生工具在 cp950 環境輸出 cp950。3.15 預設 UTF-8 之後，text=True 會用 UTF-8 解碼這些輸出而失敗；有 errors="replace" 時則變成靜默亂碼。subprocess 的 encoding 要對應子程序實際的輸出編碼（例如 cp950 或 oem）。
  • 哨兵測試：用 -X utf8=0 執行一個測試：以專案自己的寫檔函式寫入 "✓µ中文"，用 read_bytes() 和 "✓µ中文".encode("utf-8") 比對。開發機已是 3.15 或設了 PYTHONUTF8=1 時，不加 -X utf8=0 會遮住問題。

換行

  • 現象：Windows 上 Python 用文字模式寫檔會把 \n 變成 \r\n；git 的 core.autocrlf 也會轉換。只改幾行的修改可能變成整個檔案的 diff。
  • 怎麼查：有沒有 .gitattributes；git config core.autocrlf；git ls-files --eol 的 i/ 欄（repo 內的換行）。
  • 怎麼修：加 .gitattributes（例如 * text=auto，二進位檔標 binary），既有 repo 要 git add --renormalize .，會產生一個大的正規化提交，先告訴使用者。Python 改寫既有檔案時，讀和寫都用 newline=""（或用 bytes 讀寫）保留原本的換行；新檔用 newline="\n"。
  • 哨兵測試：CI 檢查 git ls-files --eol，文字檔的 i/ 欄全部是 i/lf（或 i/none），出現 i/crlf 或 i/mixed 就失敗。

Shell、PowerShell 與管線

  • 現象：bash 的 heredoc 分隔字沒加引號時，\\ 會變成 \、$ 與反引號會被展開。PowerShell 5.1 的 > 與 Out-File 預設寫 UTF-16，Set-Content 預設寫系統編碼；$OutputEncoding 預設 ASCII，"中文" | python x.py 送進去的是 ??；解碼原生程式的輸出用 cp950，程式輸出 UTF-8 時變成亂碼，連 agent 讀到的錯誤訊息都會是亂碼。
  • 怎麼查：搜尋腳本裡沒加引號的 heredoc（<<、<< 、<<- 後面接分隔字）與 PowerShell 的重導向寫檔。
  • 怎麼修：heredoc 一律用 <<'EOF'，並在 CLAUDE.md 寫明 agent 自己用 shell 寫檔也一律如此。PowerShell 5.1 寫無 BOM 的 UTF-8 用 [IO.File]::WriteAllText($p, $s, [Text.UTF8Encoding]::new($false))，或改用 PowerShell 7 的 -Encoding utf8NoBOM；管線前設 $OutputEncoding 與 [Console]::OutputEncoding 為 UTF-8。
  • 二次陷阱：PowerShell 5.1 的 -Encoding utf8 會寫出帶 BOM 的 UTF-8，shebang 會失效、json.load 會失敗、CSV 第一欄名稱多一個看不見的字元。
  • 哨兵測試：CI 掃描 repo 的文字檔，必須能用嚴格 UTF-8 解碼，而且沒有 UTF-16 或 UTF-8 BOM。

字元處理

  • 現象："µ".upper() 會變成希臘字母 Μ，看起來像 M，單位或代號被大寫化後意思就變了。C 的 isspace、toupper 等函式收到 UTF-8 中文的位元組（負的 char）是未定義行為：Debug 版觸發 assert，Release 版靜默得到錯的結果。
  • 怎麼查：搜尋對單位字串、識別碼做 upper()、lower() 的地方；搜尋把 char 直接傳給 <cctype> 函式的地方。
  • 怎麼修：單位與識別碼不做大小寫轉換；<cctype> 函式的參數先轉成 unsigned char。
  • 哨兵測試：單元測試確認專案的單位處理函式保留 "µs" 不變。

靜默退回與載入錯的版本

  • 現象：GPU 後端初始化失敗時自動改用 CPU；DLL 名稱或路徑不對時從 PATH 載入到另一個版本。結果可能正確，只是慢或行為不同，沒有任何警告。
  • 怎麼查：搜尋 fallback、自動退回的程式路徑；確認啟動時有沒有記錄實際用的後端與載入的 DLL 完整路徑。
  • 怎麼修：啟動時記錄實際後端與 DLL 路徑；退回時至少發出警告。
  • 哨兵測試：測試讀環境變數指定預期的後端（例如 EXPECTED_BACKEND=CUDA），實際不符就失敗；檢查載入的 DLL 來自建置輸出資料夾。

吞掉的例外

  • 現象：例外被 catch 後當成正常情況處理，問題只表現為偶發的卡住或資料錯誤，log 裡什麼都沒有。
  • 怎麼查：搜尋 catch (...)、空的 catch 區塊、except:、except Exception: pass。
  • 怎麼修：至少記錄例外；只 catch 預期中的例外型別。
  • 哨兵測試：CI 用 grep 或 lint 規則擋下新的空 catch。

路徑長度

  • 現象：Windows 預設路徑上限 260 字元，超過時檔案或 DLL 會讀不到，有時只表現為退回到別的實作。
  • 怎麼查：建置輸出與相依套件的實際路徑長度；系統是否啟用長路徑。
  • 怎麼修：縮短建置目錄的路徑；必要時啟用長路徑支援，並確認相關工具也支援。
  • 哨兵測試：CI 檢查建置輸出裡最長的路徑小於一個門檻（例如 200 字元）。

計時與等待

  • 現象：GetTickCount 等預設計時器約 15.6 ms 才跳一次，量比這短的間隔會得到 0 或 15.6 ms 的倍數。Sleep(1) 預設也可能睡到約 15.6 ms，即時迴圈的節奏會被拉長。
  • 怎麼查：搜尋計時與等待用的函式。
  • 怎麼修：量時間用 QueryPerformanceCounter、std::chrono::steady_clock、Python 的 time.perf_counter()；需要短而準的等待時用 timeBeginPeriod 或高解析度 waitable timer（CREATE_WAITABLE_TIMER_HIGH_RESOLUTION），並先跟使用者確認對耗電與系統的影響。
  • 哨兵測試：重複讀專案用的時鐘函式，取最小的非零差值，要求小於一個門檻（例如 1 ms）。

## 審查前

- 先讀規格或需求，再讀改動的程式碼。實作者的說明只當線索，不要直接相信它的結論。
- 呼叫時缺少規格、改動清單或實作者的判斷，就在報告開頭列出缺了什麼，然後就現有資料盡量審。

## 要找的問題（依序）

- 不符合規格：漏做、做錯、把要求的架構簡化掉；功能不在要求的模組裡，或寫了卻沒被呼叫。
- 只為了通過測試：針對測試輸入寫死的分支、被放寬的容許誤差或門檻、被改掉或跳過的測試。
- 測試沒涵蓋的情況：邊界值、錯誤路徑、空輸入、大小極端值、並行與時序。
- 實作者的判斷：逐一評估每個判斷是否合理、錯了的代價。
- C++／GPU／即時系統：資料競爭、缺少同步、鎖的順序、即時路徑上的記憶體配置或阻塞、主要運算是否真的在 GPU 上。
- 建置檔與跨檔案介面的改動是否一致。

## 報告格式

- 每個問題：嚴重度（嚴重／中等／小）、位置（檔案:行號）、問題、為什麼是問題、建議的重現方式或測試。
- 嚴重：會造成錯誤結果、當機、資料損毀、安全問題，或不符合規格。
- 最後另列「沒有判斷的項目」：哪些部分你沒讀到、沒能力判斷、或需要實際執行才能確認。這一段不可省略。
- 沒找到問題就明說，並說明你檢查了哪些範圍；不要為了交差而湊問題。

對這個 session 剛完成的工作做一次獨立審查。補充說明：$ARGUMENTS

1. 整理給審查者的資料，不要省略任何一項：
   - 規格或需求（使用者原本的要求，加上之後確認過的細節）
   - 改動的檔案清單與每個檔案的改動摘要（先看 `git status` 與 `git diff --stat`）
   - 你自己做的判斷：決定、理由、錯了的代價
   - 測試沒涵蓋的情況，以及你沒驗證到的部分
2. 用 reviewer 子 agent 審查，把上面的資料完整交給它。
3. 依審查結果處理：
   - 嚴重的問題：先寫能重現問題的測試、確認它失敗，再修，修完跑完整的相關回歸測試。
   - 中等與小問題：列出來，問使用者要現在修還是延後。
   - 你不同意的審查意見：說明理由，不要默默忽略。
4. 回報：審查找到什麼、修了什麼（附驗證結果）、延後什麼，以及審查者列出的「沒有判斷的項目」。

準備換 session。補充說明：$ARGUMENTS

1. 進度檔：專案已有進度檔（例如 PROGRESS.md、docs/progress.md）就更新它，沒有就在專案根目錄建立 `PROGRESS.md`。內容：
   - 現況：完成了什麼、目前狀態（哪些測試通過、哪些還沒）
   - 下一步：具體到下個 session 可以直接開始做
   - 踩到的坑：試過但失敗的方法與原因、容易誤會的地方
   - 待使用者決定的事項
   - 不要寫入金鑰、憑證或使用者的個人資訊。
2. 先看 `git status`。只提交進度檔與這次工作相關的檔案；其他未提交的改動列出來問使用者，不要擅自提交或還原。
3. 最後輸出一段開場訊息，放在程式碼區塊裡方便複製：說明專案與目標、請新 session 先讀進度檔、下一步要做什麼、必須注意的坑。控制在 15 行以內。
