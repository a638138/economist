# AI Agent 工作守則

給 coding agent 讀的工作規則，依「AI Agent 研究（一）～（五）」整理。整理日期：2026 年 11 月 14 日。
只收模型預設不一定會做的規則。句尾括號是依據的筆記章節，證據與限制見 https://a638138.github.io/economist/notes/ ；標「做法」的是整理者為了方便驗收而定，沒有直接研究支持。與專案的 CLAUDE.md 衝突時以專案為準。

## 核心規則

- 動手前先確認驗證方式（測試、參考輸出與容許誤差、量測腳本），沒有就先提出。非小型的修改（跨檔案、改演算法或介面）先請使用者確認驗證方式合理，再改程式。（二-1）
- 每次修改後跑完整的相關回歸測試；退步就退回，不要在壞掉的基礎上繼續改。（二-1）
- 測試通過不等於完成。回報前檢查產物本身：功能在要求的模組裡且確實被呼叫、沒有針對測試輸入寫死的分支、沒有把要求的架構簡化掉。（二-1）
- 不得為了讓結果通過而修改、刪除或跳過測試，也不得放寬容許誤差、改變問題大小或輸入條件；確有必要先說明並取得同意。（四-2）
- 回報分三部分：做了什麼、怎麼驗證（指令與結果）、哪些沒驗證到。（做法：讓使用者能驗收上一條）
- 宣稱效能改善必須附修改前後的量測（同一硬體、固定問題大小、多次執行）。（三-2）
- 新增相依套件前，確認套件名稱真的存在、是正確的那一個。（一-4）
- 同一個檔案準備讀第三次、或同一處準備改第三次時，先停下來向使用者說明卡在哪裡，不要繼續兜圈。（二-2）
- 預設不開子 agent；只有能完全切開、互不相依的工作才開。（二-3）
- 不要 print 或寫 log 任何金鑰、token、憑證。（一-4）

## C++／GPU／即時系統（只在這類專案適用）

- 平行化（OpenMP、執行緒、搬到 GPU）前先量該段的執行時間；只有幾毫秒以下的段落，開銷可能大於收益，量過再決定。（四-2）
- CUDA／GPU 改寫每次都要編譯、執行並與參考輸出比對；未經執行驗證的 CUDA 改寫大多是錯的。（四-2）
- 確認主要運算真的在 GPU 上，沒有留在 CPU；用 compute-sanitizer 等工具檢查同步與競態。（四-2）
- 移植已為 CPU 手調過（SIMD intrinsics、分塊、預先打包）的程式到 GPU：先嘗試直接轉；若一再失敗，先寫一個乾淨、未最佳化、結果一致的參考版本，再從它轉。（四-2）
- 即時路徑的時序與同步錯誤，一般測試抓不到；改到這類程式時，提出壓力測試或 sanitizer 檢查。（四-2）
- 修改 CMake／Makefile 或跨檔案介面時，明確列出改動，交給使用者把關。（四-2）
