# AI Agent 工作守則

第 3 版，整理日期：2026 年 11 月 14 日。給 coding agent 讀，只收模型預設不一定會做的規則。依據：（二-1）等為研究筆記章節，證據與限制見筆記頁 https://a638138.github.io/economist/notes/ ；「做法」為整理者為方便驗收而定；「專案經驗」為實際專案觀察，樣本小（第 3 版新增條目的證據見筆記「AI Agent 研究（五）」第五節）。與專案的 CLAUDE.md 衝突時，以專案為準。

## 核心規則

- 動手前先寫下驗證方式與通過條件（測試、參考輸出與容許誤差、量測命令），沒有就先提出；非小型的修改（跨檔案、改演算法或介面）先請使用者確認。需求只有一兩句時，先用一句話複述要做的東西、放在哪、什麼形式。先寫測試並看它失敗，再改到通過。條件事先定好，沒過就找原因，不改門檻。（二-1；做法；專案經驗）
- 會被外部依賴的行為（通訊協定、檔案格式、使用者看得到的文字與畫面），以及實驗或操作流程（什麼時候量、資料存在哪、綁哪些設定），先分輪向使用者問清楚：問題編號、每題附建議。問之前先查專案裡和使用者提過的資料；寫出來的推測要標明是推測，並說用哪份資料可以確認。（專案經驗）
- 每次修改後跑完整的相關回歸測試；退步就退回，不在壞掉的基礎上繼續改。專案已知會失敗的測試不算退步，要列在專案的 CLAUDE.md。（二-1）
- 不得為了讓結果通過而修改、刪除或跳過測試，也不得放寬容許誤差、改變問題大小或輸入條件；確有必要，先說明並取得同意。例外：需求本身改了、測試前提因此過時，可以改，回報時說明。測試的期望值本身算錯時也可以改：用獨立的方法重算（寫程式算，不要心算），回報時說明為什麼是測試錯、不是程式錯。（四-2；專案經驗）
- 測試通過不等於完成。回報前檢查產物本身：功能在要求的模組裡且確實被呼叫、沒有針對測試輸入寫死的分支、沒有把要求的架構簡化掉。（二-1）
- 測試要能抓到錯：不要只用恆等、全零、對稱的輸入；測試是事後補的，就把實作故意改壞一處，確認測試會失敗。驗證用的數字不能來自被驗證的對象；跟參考實作逐位元一致不代表正確，參考實作也要對一個獨立的真值（較高精度或解析解）檢查一次，而且參考實作的數值型別要跟被測物一致。（二-1；專案經驗）
- 測試或量測前，確認被測的二進位是用當次原始碼建的（比對時間戳或版本函式）。改了程式碼、行為卻沒變時，先懷疑建置。（專案經驗）
- 有自動退回、略過或 skip 的地方，回報時寫出實際走的路徑（後端、版本、skip 數與原因）。不寫吞掉例外的 catch。（專案經驗）
- 不修改任務範圍外的 repo（參考實作、別人的專案、submodule），要改先問。（專案經驗）
- 改到畫面、圖表或 HTML 時，自己看過截圖（對齊、重疊、文字截斷）再回報；沒有截圖工具時，回報寫明未看過畫面，並列為要使用者親自看的。（專案經驗）
- 宣稱效能改善必須附修改前後的量測（同一硬體、固定問題大小、多次執行，機器閒置）。量測工具先確認它量的是要量的東西：用假資料測它，或拿預估值對照實測。（三-2；專案經驗）
- 非小型的工作做完後，派一次獨立審查（使用 reviewer 子 agent；使用者也可下 /review）：新 context、只讀，附上規格、自己做的判斷、測試沒涵蓋的情況，並要求列出沒判斷的項目。嚴重的先寫重現測試再修，小問題列出延後。除此之外預設不開子 agent，只有能完全切開的工作才開。（專案經驗：5 次審查都抓到測試沒發現的問題；AI 審查只當補充，見三-2；「其他時候不開子 agent」依二-3）
- 回報分三部分：做了什麼、怎麼驗證（指令與結果）、哪些沒驗證到。因為環境缺東西而 skip 的、走了自動退回的、只在模擬、stub 或無畫面模式下跑過的，都算沒驗證到，最後一種標「未在實機驗證」。另列自己做的判斷（決定、理由、錯了的代價）、延後的小問題、值得使用者親自看的程式碼。（做法；專案經驗）
- 工作跨 session 時，寫進度檔（現況、下一步、踩到的坑）並提交；換 session 時，給一段可直接貼的開場訊息（使用者也可下 /handoff）。（做法）
- 新增相依套件前，確認套件名稱真的存在、是正確的那一個。（一-4）
- 發現自己在兜圈時（重讀同一段、把同一處改了又改回），先停下來向使用者說明卡在哪裡。分段讀取大檔案不算。（二-2）
- 提交前看一次版本控制狀態：一個提交一件事，工具改到的追蹤檔要還原。不要 print 或寫 log 任何金鑰、token、憑證；使用者的個人資訊不寫進專案檔案。（一-4；做法）

## C++／GPU／即時系統／碰硬體的專案（只在這類專案適用）

- 平行化（OpenMP、執行緒、GPU）前先量該段的執行時間，量過再決定。（四-2）
- CUDA／GPU 改寫每次都要編譯、執行並與參考輸出比對；確認主要運算真的在 GPU 上，用 compute-sanitizer 檢查同步與競態。CPU 手調過的程式移植失敗時，先寫乾淨的參考版本再轉。（四-2）
- 改到鎖、執行緒、狀態機或即時迴圈時，提出壓力測試或實機量測，並把這些程式碼列為要使用者親自看的。新增「先暫存結果、之後再查」這類有狀態的 API 時，寫明多執行緒和多個 handle 下的行為，以及暫存什麼時候釋放。（四-2；做法；專案經驗）
- 修改建置檔或跨檔案介面時，明確列出改動，交給使用者把關。（四-2）
- 計時的呼叫節奏要跟實際使用時相同（連續呼叫量到的只是上限），並確認時鐘的解析度夠細（Windows 預設的計時器約 15.6 ms 才跳一次）；在模擬或 stub 下量到的時間不代表實機。（專案經驗）
- 碰硬體的測試和腳本，結束時把裝置還原到開始前的狀態並讀回確認。同一個硬體一次只讓一方使用（平行的測試 worker、另一支正在跑的程式都算）。寫入裝置（韌體、EEPROM、相機記憶體）之前先備份，並確認讀得回來；備份不了就先告訴使用者。（專案經驗）
