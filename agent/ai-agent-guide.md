# AI Agent 工作守則（實證整理版）

給 coding agent 讀的工作規則，依「AI Agent 研究（一）～（五）」整理。整理日期：2026 年 11 月 14 日。
完整證據、數字與研究限制：https://a638138.github.io/economist/notes/

- 這些規則是整理者依研究做的判斷；研究多為預印本，效果仍要在專案上驗證。
- 與專案自己的 CLAUDE.md／AGENTS.md 衝突時，以專案為準。
- 括號內是依據的筆記章節，例如（二-1）＝「AI Agent 研究（二）」第一節。
- 這是完整版，適合查閱。實際給 agent 用的是拆分版：全域核心 `agent/core.md`、C++／GPU 專案用 `agent/cpp-gpu.md`、撰寫設定檔時才載入的 skill `agent/skills/agent-config-writing/SKILL.md`。

## 1. 驗證與回報（最常出錯，優先遵守）

- 動手前先確認驗證方式：回歸測試、參考輸出與容許誤差、量測腳本。沒有就先提出或補上，請使用者確認測試合理後再改程式。（二-1）
- 每次修改後跑完整回歸測試；退步就退回，不要在壞掉的基礎上繼續改。多輪修改會悄悄改壞原本對的地方。（二-1）
- 測試通過不等於完成。回報前檢查產物本身：功能在要求的模組或檔案裡、確實被呼叫；沒有針對測試輸入寫死的分支；沒有把要求的架構簡化掉。（二-1）
- 不得為了讓結果通過而修改、刪除或跳過測試，也不得放寬容許誤差、改變問題大小或輸入條件。確有必要時，先說明理由並取得同意。（四-2）
- 回報分成三部分：做了什麼、怎麼驗證（指令與結果）、哪些沒驗證到。不確定就明說。

## 2. 任務範圍與進行方式

- 開始前確認目標、限制與相關檔案；意圖不清楚時先問一句，不要猜。（二-1）
- 跨模組的大改動拆成可單獨驗證的小步驟。寫下的計畫要逐步照做，偏離時說明原因。（二-1）
- 從使用者指定的檔案與範圍開始，避免漫無目的地探索。發現自己反覆讀同一檔案、改了又改同一處時，停下來整理現況並向使用者說明。（二-2）
- 預設單一 agent。只有能完全切開、互不相依的工作（例如同時查幾個獨立模組）才開子 agent，並先說明預期成本。（二-3）

## 3. C++、效能與平行程式

- 宣稱變快必須附修改前後的量測：同一硬體、固定問題大小、多次執行。沒有數字不宣稱效能改善。（三-2）
- 平行化（OpenMP、執行緒、搬到 GPU）前先量該段的執行時間。只有幾毫秒以下的段落，開銷可能大於收益，量過再決定。（四-2）
- GPU／CUDA 改寫：每次都要編譯、執行並與參考輸出比對；確認主要運算真的在 GPU 上；用 compute-sanitizer 等工具檢查同步與競態。未經執行驗證的 CUDA 改寫大多是錯的。（四-2）
- 移植已為 CPU 手調過（SIMD intrinsics、分塊、預先打包）的程式到 GPU：先嘗試直接轉；若一再失敗，先寫一個乾淨、未最佳化、結果一致的參考版本，再從它轉。（四-2）
- 即時路徑的時序與同步錯誤，一般測試抓不到。改到這類程式時，提出壓力測試或 sanitizer 檢查。（四-2）
- 修改 CMake／Makefile 或跨檔案介面時，明確列出改動，交給使用者把關。（四-2）

## 4. 成本與 context

- 一個任務一個對話。重要規則不要只存在對話裡：長對話被壓縮後規則會遺失，要寫進 CLAUDE.md 或任務檔。（一-3）
- 不要建議或自行安裝「壓縮工具輸出」「代理 API」類的省 token 外掛：實測帳單反而增加。評估省錢做法時看每個成功任務的實際費用，不看 token 數。（二-2）
- 工作中途不要增減 MCP 工具或切換 effort／thinking 設定，會讓快取失效。（二-2）

## 5. 安全與相依套件

- 新增相依套件前，確認套件名稱真的存在、是正確的那一個；模型推薦不存在套件的比例約 5%。（一-4）
- 不安裝來路不明的 skill 或外掛；需要時先讀過其中的腳本與指令。（一-4）
- 不要 print 或寫 log 任何金鑰、token、憑證。（一-4）
- 合併前要跑 CI；AI 審查只當補充，不取代人工審查。（三-2）

## 6. 被要求撰寫 CLAUDE.md／AGENTS.md 時

- 只寫 agent 從程式碼與 README 查不到的事：建置與測試指令、硬體與即時限制、不可違反的規則及其原因。不寫架構介紹、目錄說明、用了哪些套件。（一-3）
- 不要交付自動產生（例如 /init）後未經使用者審過的內容。（一-3）
- 500 行內的長度、規則放第幾行、拆不拆檔都不是重點，內容精準才是。（一-3）
- 寫進去的規則只會被部分遵守，而且程式寫越多越容易漏。不可違反的規則，同時提出機械檢查：hook、lint 規則、static_assert 等編譯期檢查、CI 測試。（一-3）
- 提交進版本控制，並在專案改變時更新；多數設定檔提交後就沒再改過。（一-3）

## 7. 被要求撰寫 SKILL.md 時

- 只為反覆出現、agent 自己查不到的領域流程寫（例如量測、校正、QC 判讀）；通用程式技巧不必寫成 skill。（一-1）
- 一個 skill 只處理一件事；核心規則精簡，細節拆到需要時才讀的附檔。（一-2）
- 關鍵警告放最前面；明寫不可跳過的步驟與驗證方式；驗證寫一次，不要求反覆檢查。（一-2）
- 範例標明「僅供參考，以任務要求為準」；註明適用的 SDK 版本與環境。（一-2）
- 多個 skill 協作時，寫出產物之間的依賴關係。（一-2）
- 建議使用者用幾個真實任務比較有無 skill，再決定是否保留。（一-1）

## 8. 被要求設計 MCP 工具時

- 每個工具寫清楚用途、何時使用、限制、參數單位與範圍。（四-1）
- 輸出精簡、先給摘要，不一次傾倒原始資料；錯誤訊息要讓 agent 知道怎麼修正。（四-1）
- 工具少而清楚，優於多而模糊。（四-1）
