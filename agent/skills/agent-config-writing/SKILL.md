# AI Agent skill：撰寫設定檔與工具

撰寫 CLAUDE.md、SKILL.md 或 MCP 工具時才載入的 skill，依實證研究整理。整理日期：2026 年 11 月 18 日。
證據見 https://a638138.github.io/economist/notes/ 「AI Agent 研究（一）、（四）」，其中 skill 的研究多數是預印本；非英文 Windows 陷阱與機械檢查例子來自專案經驗，見「AI Agent 研究（五）」第五節。

## 最重要：寫進檔案的規則只會被部分遵守

- 簡單規則的遵守率約五成五到七成，agent 寫的程式越多越容易漏。
- 「違反就會出事」的規則，除了寫進檔案，一定要同時提出機械檢查：hook、lint 規則、static_assert 等編譯期檢查、CI 測試。檔案負責說明原因，檢查負責確保做到。
- 要做 hook 或事後檢查時，先讀同資料夾的 `guard-hooks.md`（範本、hook 靜默失效的陷阱、四層測試）；hook 與測試寫好、測過，經使用者同意才啟用。
- 例：建置腳本在任何目標檔沒有記到標頭相依時直接失敗；測試用純文字比對 C 介面與各語言綁定，有函式沒綁就失敗；測試讀韌體原始碼裡的常數，跟主機端的表比對；測試從原始碼掃出舊版 Python 不支援的語法。

## CLAUDE.md／AGENTS.md

- 只寫 agent 從程式碼與 README 查不到的事：建置與測試指令、硬體與即時限制、不可違反的規則及其原因。
- 不寫架構介紹、目錄說明、用了哪些套件：agent 讀程式碼就知道，寫了只增加成本。
- 不要交付自動產生（例如 /init）後未經使用者審過的內容；自動產生的說明檔平均沒有幫助，成本還增加約兩成。
- 500 行內的長度看不出影響；拆成多個檔不會提高遵守率，不要為此拆檔。規則位置的效果沒被排除，重要規則放前面。把力氣放在內容精準。
- 提交進版本控制，並提醒使用者隨專案更新；多數設定檔提交後就沒再改過。
- 重要規則不要只在對話中說，長對話被壓縮後會遺失。
- 把「違反了也不會報錯」的規則集中在檔案開頭的一節（方便查找和逐項做機械檢查，放前面也可能提高遵守率）。這類規則在非英文的 Windows 上特別多，例如編譯器用系統編碼讀 UTF-8 原始碼、shell heredoc 把 `\\` 變成 `\`、寫檔預設用系統編碼、建置工具記不到標頭相依而連進舊的目標檔。
- 已知會失敗的測試不要列在 CLAUDE.md（會越積越多、修好了也沒人刪）：優先用測試框架的標記（例如 pytest 的 `xfail(strict=True)`，意外通過時會報錯，清單不會過時）；做不到時用已知失敗清單檔加比對腳本，把結果分成新失敗、已知失敗、已知但已通過。都要註明是哪台機器或哪個環境。CLAUDE.md 只寫一行怎麼標記、清單在哪。
- 專案在 Windows 上開發、建置或執行時（非英文語系尤其要做），建立或檢查 CLAUDE.md 前讀同資料夾的 `windows-traps.md`，逐項檢查並提議哨兵測試。

## SKILL.md

- 只為反覆出現、agent 自己查不到的領域流程寫（例如量測、校正、QC 判讀）；通用程式技巧寫成 skill 幾乎沒有效益。
- 不要讓模型自己產生 skill 內容後直接使用；自生成的 skill 平均讓表現變差。
- 一個 skill 只處理一件事；核心規則精簡，細節拆到需要時才讀的附檔。
- 同時裝的 skill 越多，agent 越常該用時沒用、或選錯（10 個左右，較弱的模型就看得到）：用不到的 skill 移除；description 寫明何時使用，不要寬泛到和其他 skill 重疊。
- 關鍵警告放最前面；明寫不可跳過的步驟與驗證方式；驗證寫一次，不要求反覆檢查（過度驗證是常見的效率退化）。
- 範例標明「僅供參考，以任務要求為準」；agent 常把範例或預設值當成規則。
- 註明適用的 SDK 版本與環境；版本不符的 skill 會讓表現變差。
- 多個 skill 協作時，寫出產物之間的依賴關係。
- 附帶腳本時，腳本不得 print 或寫 log 金鑰。
- 交付時建議使用者用幾個真實任務比較有無 skill，再決定是否保留。

## MCP 工具

- 每個工具的描述寫清楚：用途、何時使用、限制、參數單位與範圍（多數現有工具都缺限制與使用時機）。
- 輸出精簡、先給摘要，不一次傾倒原始資料；錯誤訊息要讓 agent 知道怎麼修正。
- 工具少而清楚，優於多而模糊。
