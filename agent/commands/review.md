---
description: 對剛完成的工作做一次獨立審查（reviewer 子 agent），並依結果處理問題
argument-hint: [要審查的範圍或補充說明，可省略]
---

對這個 session 剛完成的工作做一次獨立審查。補充說明：$ARGUMENTS

1. 整理給審查者的資料，不要省略任何一項：
   - 規格或需求（使用者原本的要求，加上之後確認過的細節）
   - 改動的檔案清單與每個檔案的改動摘要（先看 `git status` 與 `git diff --stat`）
   - 你自己做的判斷：決定、理由、錯了的代價
   - 測試沒涵蓋的情況，以及你沒驗證到的部分
   - 這是複審（修正前一輪審查的問題之後）時：前一輪的審查報告，以及每個問題怎麼修、同一類還找了哪些路徑
   - diff 檔：reviewer 沒有 Bash，看不到 git，只能讀檔。用 `git -c core.quotepath=false diff <這次工作開始時的 commit> --stat --patch --output=<repo 外的暫存檔>` 產生（已提交和未提交的改動都涵蓋；用 --output 而不是 shell 導向，避免編碼被改）。新增、還沒追蹤的檔案不在 diff 裡，另外附上 `git status --short` 的未追蹤清單，標明哪些打算提交，讓 reviewer 直接讀。
2. 用 reviewer 子 agent 審查，把上面的資料完整交給它。
3. 依審查結果處理：
   - 每條意見先對照程式碼確認是對的再動手；有看不懂的，先整理起來一次問使用者，問清楚再改，各條可能彼此相關。
   - 嚴重的問題：先寫能重現問題的測試、確認它失敗，再修，修完跑完整的相關回歸測試。
   - 修的時候先列出同一類的所有路徑一起修，修法本身新開的路也要找；只修被點名的那一條，下一輪審查會在隔壁路徑找到同一個洞。
   - 中等與小問題：列出來，問使用者要現在修還是延後。
   - 你不同意的審查意見：說明理由，不要默默忽略。
4. 回報：審查找到什麼、修了什麼（附驗證結果）、延後什麼，以及審查者列出的「沒有判斷的項目」。
